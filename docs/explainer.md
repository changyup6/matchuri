```

               crawler/  카카오맵 수집 (로컬에서만 돌린다)
               analysis/ 추천 실험·검증 + 트렌드 수집 (로컬에서만 돌린다)
```

## 2. 서버 — 한 대에 전부 들어 있다

`api.example.com` EC2 **한 대**가 전부다. Jenkins 도 그 위의 컨테이너 하나일 뿐,
별도 장비가 아니다. "서버에서 실행해라" = `ssh my-server` 로 들어가서.

**Jenkins 는 앱과 별도 compose 스택이다**(`BE/infra/jenkins/`). 파이프라인이 배포 중에
앱 스택을 재시작하는데, 같은 스택에 있으면 **Jenkins 가 자기 자신을 죽인다.** 두 스택은
`web` 이라는 외부 네트워크로 이어져 nginx 가 `jenkins:8080` 을 이름으로 찾는다.

```
EC2 (Ubuntu 24.04 · 4 vCPU · 15 GiB · 309 GB)
│
├── backmock-nginx-1        리버스 프록시   :80  ← 외부에 열린 유일한 문
│     ├ location /             → app:8000      (레이트 리밋)
│     ├ location = /users      → app           (발급 전용 + 더 좁은 리밋)
│     ├ location /admin        → app           (Basic 인증 + 리밋)
│     ├ location /grafana/     → grafana
│     ├ location /jenkins      → jenkins
│     ├ location = /metrics       **return 404** — 밖에서는 없는 것처럼 막는다
│     └ location = /nginx_status  allow 127.0.0.1 + 172.16.0.0/12, deny all
├── backmock-app-1          FastAPI (expose 8000, 호스트에 열지 않는다)
├── backmock-prometheus-1   지표 수집 (30일 보관)
│     └ 앱 지표는 nginx 를 거치지 않고 컨테이너 네트워크로 app:8000/metrics 를 직접 긁는다
│       (그래서 엣지에서 /metrics 를 404 로 막아도 수집에 지장이 없다)
├── backmock-grafana-1      대시보드
├── backmock-node-exporter-1 / nginx-exporter-1
├── jenkins                 CI/CD
└── hub-caddy · hub-label-studio · hub-filebrowser   ← 팀의 다른 스택(443 점유)
```

**앱의 8000 을 호스트에 열지 말 것.** 열면 nginx 의 인증과 레이트 리밋을 우회하는 문이
생겨 `/admin` 이 그대로 노출된다.

### 상태는 어디에 있나

```
Docker 볼륨 backmock_state  →  /app/state
  users.jsonl        사용자와 설정(위치·필터)
  preferences.jsonl  스와이프 기록 ← 취향 모델의 원본
  exposures.jsonl    어떤 카드를 어느 정책이 보여줬나
  bookmarks.jsonl    찜
  directions.jsonl   길찾기(방문 의사)
  surveys.jsonl      설문 응답
```

로컬에서 서버를 띄우면 같은 파일들이 `BE/state/` 에 쌓인다(gitignore 대상).
`MATCHURI_STATE` 로 경로를 바꿀 수 있고, 테스트는 매번 임시 디렉토리를 쓴다.

**DB 가 없다.** 추가 전용 로그 한 벌로 버틴다. 취향 모델은 선호 기록을 순서대로 접은
결과이므로, 로그만 있으면 재시작 때 복원된다(numpy 가중치를 직렬화하지 않는다).
볼륨이라 재배포해도 살아남는다 — 검증됨.

## 3. CI/CD — master 가 곧 서버다

```
feat/… 브랜치 → push → GitLab MR → master 머지
                                      ↓ 최대 2분 (SCM 폴링)
                             Jenkins matchuri-be-deploy
                                      ↓ 약 3분
              Checkout → Deploy → nginx reload → Health check
```

| 알아야 할 것 | |
|---|---|
| 감시 대상 | `master` 뿐이다. 브랜치에 push 해도 배포되지 않는다 |
| 경로 제한 | `BE/.*` 만 트리거한다. TIL·FE 커밋은 배포를 일으키지 않는다. ⚠️ **이 설정은 레포가 아니라 서버의 Jenkins 작업 설정에만 있다** (`/var/jenkins_home/jobs/matchuri-be-deploy/config.xml`) |
| 파이프라인 | `BE/Jenkinsfile`. `dir('BE')` 안에서만 돌아 FE 를 건드리지 않는다 |
| 배포 소스 | `/var/jenkins_home/workspace/matchuri-be-deploy/BE` |
| 인증 | GitLab **Deploy token**(HTTPS). 사내 GitLab 의 22번 포트 가 막혀 SSH 키를 못 쓴다 |
| 롤백 | 이미지 태그. 팀 관례가 `backmock-app:<기능>-<날짜>` 다 |

**MR 을 만드는 것과 브랜치를 push 하는 것은 다르다.** push 하면 GitLab 이 "MR 을 만들려면
여기로" 링크를 주는데, 그건 안내일 뿐이다. 링크를 열고 `Create merge request` 를 눌러야
MR 이 생긴다.

## 4. 지금 하고 있는 것 — 추천 검증 설문

### 왜

스와이프 `like` 는 **카드를 보고 오른쪽으로 넘긴 것**일 뿐이다. 그 가게가 실제로 좋았는지는
모른다. 지금 두 정책(`legacy` / `taste`)을 팀-드래프트 인터리빙으로 비교하는데, 판정 기준이
like 율이라 **대리 지표**다. 실제로 가서 어땠는지를 재려는 것이 이 기능이다.

### 어떻게

```
길찾기를 누름 → POST /users/{id}/directions        (방문 의사로 기록)
앱이 열림     → GET  /users/{id}/surveys/pending    (아직 답 안 한 목록)
배너에서 선택 → POST /users/{id}/surveys            (방문 여부 + 만족도)
집계          → GET  /admin/api/surveys             (정책별 방문율·만족도)
```

같은 키 `(user_id, card_id)` 로 `exposures.jsonl` 과 조인되므로 **정책 라벨이 퍼널 끝까지
따라온다**: 노출 → 길찾기 → 설문 → 방문 → 만족.

### 결정과 근거

| 결정 | 왜 |
|---|---|
| **GPS 를 쓰지 않는다** | 백그라운드 위치 권한이 필요하고, 역삼동은 반경 100m 안에 가게가 수십 곳이라 어디에 갔는지 특정할 수 없다. 길찾기는 사용자가 그 가게를 **직접 지목한 순간**이라 정확하다 |
| **자유 리뷰가 아니라 체크리스트** | 목적이 추천 정확도 **측정**이다. 자유 텍스트는 집계되지 않는다 |
| **후기는 `user_reviews` 가 아니라 `store.reviews` 에 섞어 내보낸다** (2026-09-21) | 앱에 그 배열을 파싱하는 코드가 한 줄도 없고 가게 상세는 `store.reviews` 만 그린다 — 서버에는 정상으로 쌓이는데 화면에는 한 건도 안 떴다. `FE/` 는 팀 규정상 못 고치니 **앱이 이미 그리는 자리에 서버가 넣는다.** 신고·삭제 대상을 가릴 수단은 `source_platform: "matchuri"` 와 id ≥ 10¹² 대역으로 남겼다 |
| **추천 모델을 건드리지 않는다** | 여기서 모델이 움직이면 인터리빙의 like 율이 오염돼 정책 비교가 무의미해진다. 찜(`bookmarks`)과 같은 원칙이고, 테스트가 호출 전후를 통째로 비교해 잠근다 |
| **시점 판단은 클라이언트가** | 서버가 3시간을 막으면 개발 중에 흐름을 확인할 수 없고 값을 바꿀 때마다 배포해야 한다. `pending` 은 전부 주고 앱이 `hours_ago` 로 고른다. 서버 필터가 필요하면 `?after_hours=N` |
| **`soso` 는 만족이 아니다** | `satisfied_rate` 의 분자는 `good` 뿐이다. `soso` 를 넣으면 지표가 무뎌져 정책 비교를 못 한다 |
| **`card_id` 와 `store_id` 를 둘 다 남긴다** | 조인은 `card_id`(노출·선호가 그 키), 장기 보관은 `store_id`. `card_id` 는 데이터가 갱신되면 다시 매겨진다 |
| **`hours_after` 와 `source` 를 기록한다** | 3시간이 적절한 값인지 나중에 데이터로 검증하기 위해. `source` 는 나중에 다른 후보 소스가 생겨도 구분하기 위해 — **소급이 안 되는 정보다** |

상세 명세는 [`docs/API.md`](API.md) 5.7 절,
프론트 작업 지시서는 [`BE/server/HANDOFF-survey.md`](../BE/server/HANDOFF-survey.md).
후기가 가게 화면으로 돌아가는 경로와 그 결정의 근거는
[`BE/server/app/user_reviews.py`](../BE/server/app/user_reviews.py) 머리말에 있다.

## 5. 함정 — 실제로 당한 것들

새로 들어온 사람이 같은 데서 막히지 않도록 적는다.

### `/admin` 이 401 이 아니라 403 이면 `.htpasswd` 가 없는 것이다

`nginx/.htpasswd` 는 `.gitignore` 대상이라 **체크아웃에 없다**. nginx 는 그 파일을 못 열면
403 을 준다. 자격증명 없이 오면 401 로 물어보고, 실제로 넣으면 403 이 되므로 권한 문제로
오해하기 쉽다. 재생성 절차는 `BE/nginx/.htpasswd.example` 에 있다.

### 컨테이너는 호스트 시간대를 상속하지 않는다

호스트는 `Asia/Seoul` 인데 컨테이너 기본은 UTC 다. 그대로 두면 기록이 `+00:00` 으로 나가
문서·로그·앱과 9시간 어긋나 보인다. 순간 자체는 같지만 **오프셋을 무시하고 파싱하면
그대로 틀린다**.

`BE/docker-compose.yml` 의 `app` 에 `TZ=Asia/Seoul` 을 준 이유다. 새 컨테이너를 더할 때도
같은 함정에 빠진다 — 기본은 UTC 다.

### `card_id` 는 고정 키가 아니다

`store_id` 를 정렬해 매긴 번호다. **데이터가 바뀌면 번호도 바뀐다.** 오래 보관할 것은
`store_id` 로 가리켜야 한다. (`bookmarks.jsonl` 이 `card_id` 만 쓰고 있어 같은 위험을
안고 있다 — 알려진 빚이다.)

### 서버 파일이 CRLF 인 경우가 있다

Windows 에서 편집한 흔적이다. 서버와 저장소를 비교할 때 **줄바꿈을 정규화하지 않으면
"코드가 다르다"고 오판한다**. 실제로 그렇게 오판한 적이 있다.

### 지오펜스로는 2,795곳을 감시할 수 없다

Android 는 앱당 100개, iOS 는 20개가 한도다. 위치 기반을 다시 검토한다면 이 제약을
먼저 기억할 것.

### 파일 하나만 bind mount 하면 inode 가 고정된다

git 체크아웃이 파일을 교체해도 컨테이너는 예전 내용을 계속 본다. 디렉토리를 마운트해야
한다(`./nginx:/etc/nginx/conf.d:ro`).

## 6. 성능 — 재 보고 "지금은 고치지 않는다"로 결론 낸 것

> **이 절의 요점: 아래 셋은 실제로 측정했고, 역삼동 규모에서는 문제가 아니다.**
> 고치려 들면 추천 결과가 달라져 재평가가 필요하고, 그 재평가가 지금 병목이 된다.
> **지금은 넘긴다.** 다시 볼 시점을 각 항목에 적어 뒀다.

### 6.1 점수를 필터 **전에** 낸다 (구조상 맞지만 지금은 손해)

지금 흐름은 이렇다.

```
① allow = 필터 통과 집합           cat · tag · within_m 이 전부 하드 컷이다
② z     = 성분 점수, 후보 1,629곳 전부에 대해 계산
③ pick  = allow 안에서만 고른다
```

②가 ①을 안 쓴다. "1km로 잘랐는데 왜 역삼 전체를 계산하나"가 자연스러운 의문이고,
범위가 넓어지면 맞는 지적이 된다. **그런데 역삼동에서는 자를 것이 없다.**

```
역삼역 기준, 추천 풀 1,629곳
   300m →   225곳 (14%)
   500m →   467곳 (29%)
  1000m → 1,434곳 (88%)   ← 거의 그대로다
  2000m → 1,629곳 (100%)

풀 퍼짐: 중앙 661m · 90% 1,017m · 최대 1,528m   (동이 1.5km 밖에 안 된다)
```

게다가 열을 좁히면 **오히려 느려진다.** numpy fancy indexing 때문이다 —
`sim[like]` 는 행을 연속 메모리로 가져오는데 `sim[np.ix_(like, cols)]` 는 흩어진
위치를 하나씩 모은다.

```
후보 열     ms      전체 대비
  1629    0.51     1.00x
  1433    1.09     0.46x    ← 1km: 2배 느려진다
   472    0.47     1.07x    ← 500m: 차이 없다
   228    0.18     2.74x    ← 300m: 여기서만 이득
```

실제 사용 분포도 같은 방향이다. 사용자 109명 중 **70명이 반경을 아예 안 걸고**,
거는 사람 중 500m가 17명, 나머지 21명은 1,500m 이상(= 풀 전체)이다.

**다시 볼 시점**: 300m급 좁은 반경이 주요 사용 패턴이 되면. 그때는 "줄어드는 비율이
30% 이하일 때만 프리필터" 라는 임계값 방식이어야 한다.

**손대게 되면 반드시 지킬 선 둘.**

1. **필터는 서빙에만, 학습에는 절대 넣지 않는다.** 지금 `taste.record` 는
   `component_scores` 를 `allow` 없이 부른다. 여기에 필터가 새면 `m` 이 "그때 어떤
   필터를 걸었는지"에 따라 달라져, `preferences.jsonl` 을 다시 먹여도 같은 모델이
   나오지 않는다 — `tests/test_replay.py` 가 지키는 계약이 깨진다. 재시작마다 추천이
   조용히 달라지는 종류의 사고다.
2. **후보가 적을 때 z 는 무의미하다.** 20곳이면 노이즈, 5곳이면 뜻이 없다. 최소
   개수 미달이면 전체 풀 기준으로 되돌리는 안전장치가 있어야 한다.

### 6.2 스와이프 1건 반영 비용은 **그 사람의 이력에 비례**한다

사람 사이에는 상관관계가 없다. 각자 자기 세션(`m`·`v`·`like_ids`)을 갖고
`policy.record` 는 그 하나만 건드린다. 누적은 **한 사람 안에서** 일어난다.

`taste.record` 가 쌍 비교(최대 5쌍)를 하는데, 쌍마다 `component_scores` 를
**그 사람의 이력 전체**로 다시 낸다. leave-one-out 이라 쌍마다 빼는 대상이 달라
캐시가 안 된다.

```
이력      ms/건
   1      0.39
  50      3.14
 100      6.58
 200     14.39
 300     22.38     ← 한 사람 총비용은 n² 로 간다
```

**그런데 22ms는 체감이 안 된다.** 네트워크 왕복보다 작다. 1,000회여도 75ms다.
"많이 쓸수록 느려진다"는 표현은 숫자에 맞지 않는다.

**다시 볼 시점**: 사용자 체감 민원이 실제로 들어오면. 고치는 방법은 이력 상한
(예: 최근 200건만)인데, 그러면 "오래된 취향을 잊는" 모델이 되어 추천 품질이
달라진다 — 성능 문제가 아니라 제품 결정이다.

### 6.3 기동 복원 27초 (배포 마진이 없다)

```
{"event": "state.restore", "preferences": 2808, "exposures": 16853, "ms": 27199.3}
```

파일 읽기가 느린 것이 아니다. 2,808줄을 **줄마다 두 정책에 다시 먹이는** 비용이다
(약 10ms/줄). 선호 2,808건은 사용자 수가 아니라 **스와이프 횟수**다 — 75명이 평균
37회씩 넘긴 결과이고, 상위 5명(326·246·226·195·168회)이 27초의 절반을 차지한다.

파일이 추가 전용이라 **줄지 않고**, 사용자가 안 늘어도 쓰던 사람이 계속 쓰면 쌓인다.

```
     2,808줄  →  27초 (실측)
    10,000줄  →  약 100초
    50,000줄  →  약 8분
```

**DB로 옮겨도 고쳐지지 않는다.** 27초 중 파일 읽기는 1초도 안 되고 나머지가 numpy
재계산이다(`card_id` 때와 같은 구조다).

지금 실제 위험은 하나뿐이다. `Jenkinsfile` 의 `sleep 8` 이 복원 27초보다 짧다.
컨테이너 헬스체크는 `start_period: 180s` 라 여유가 있고, 빌드 11개 전부 SUCCESS 라
**아직 깨진 적은 없다** — 이미지가 안 바뀌면 앱을 재생성하지 않아 넘어가고 있다.

**지금 할 것**: `sleep 8` 을 준비될 때까지 재시도하는 루프로 바꾼다. 5줄이고 위험이
없다. 체크포인트(모델 스냅샷)는 그 뒤에, 복원 시간이 실제로 문제가 될 때.

### 6.4 범위를 넓히면 **먼저 터지는 것은 메모리**다

위의 셋은 전부 CPU 얘기다. 강남구로 넓히면 CPU보다 RAM이 먼저 죽는다.

```
지금  1,629곳     41 MB     float16, 1,629² 행렬 5개 + 리뷰 벡터
      5,000곳    0.4 GB
     16,000곳    3.9 GB
     25,000곳    9.5 GB     ← 서버 RAM 15GB. 기동 때 float32로 펴면 약 2배
```

`N²` 이라서 그렇다. **그러니 범위를 넓힐 때 고칠 것은 점수 계산 순서가 아니라
유사도 행렬의 표현이다.**

```
지금:   sim_menu[i][j]  모든 쌍의 유사도        →  N²
바꾸면: neighbors[i]     i 와 가장 닮은 50곳     →  N × 50

25,000곳 × 50 = 125만 항목 ≈ 10MB      N 에 비례. N² 이 아니다
```

검색·추천의 표준 해법(top-k 이웃 목록 / ANN 인덱스)이고, 부수 효과로 6.1의
"후보 열이 많다" 문제도 같이 사라진다 — 애초에 후보가 적어진다.

**다시 볼 시점**: 역삼동을 벗어나기로 결정할 때. 그때는 이 절 전체를 다시 읽을 것.

## 7.1 배포마다 카드가 안 나가던 4~8분 — 준비 게이트 + 취향 모델 스냅샷으로 닫았다

**2026-09-17 13:12 에 `/healthz` 가 502 였다. 13:17 에 200 이 됐다.** 그 5분 동안
사용자는 nginx 기본 502 페이지를 봤다. 장애가 아니라 **정상 기동 중**이었다.

### 무엇이 일어나나

`server/main.py` 가 복원을 **import 시점**에 한다.

```python
33  loader.load_all()                    # 79MB + 유사도 행렬을 float32 로 펴기(+98MB)
56  state.restore(...)                   # preferences.jsonl 을 처음부터 다시 먹이기
80  app = FastAPI(...)                   # ← 여기까지 와야 uvicorn 이 포트를 연다
```

uvicorn 은 `import main` 이 끝난 뒤에 소켓을 만든다. 즉 **복원하는 동안 8000 포트가
아예 안 열려 있고**, nginx 는 연결에 실패해 502 를 낸다.

재생 시간은 기록 수에 **선형**이다.

| 선호 기록 | 재생 시간 | 출처 |
|---|---|---|
| 1,476건 | 20초 | `docker-compose.yml` 옛 주석 |
| 약 4,800건 | 4분 이상 | `22c082c` (2026-09-16, 서버에서 만든 커밋) |
| **8,718건** | (측정 중) | 2026-09-18 준비 게이트 배포 때 `/readyz` 가 보여 준 분모. 이틀에 1.8배다 |
| 그다음 | 계속 늘어난다 | — |

Jenkins 가 master 를 2분마다 폴링해 `BE/.*` 가 바뀌면 배포한다. **배포할 때마다**
이 공백이 생긴다(BE 커밋: 09-14 31건 · 09-15 14건 · 09-16 19건).

### 왜 기존 장치가 못 막나

`docker-compose.yml` 의 `nginx.depends_on: app.condition: service_healthy` 는
"502 를 보여 주는 것보다 잠깐 안 뜨는 것이 낫다" 는 판단으로 넣은 것이다(9/10,
`52d3425`). 그런데 그건 **`compose up` 으로 nginx 까지 같이 뜰 때** 순서를 잡아 주는
장치다. nginx 가 이미 떠 있고 앱만 재시작하면 기다려 줄 방법이 없다.

`start_period: 600s`(9/16 에 180s 에서 늘림)도 다른 문제를 고친 것이다 — **기동을
실패로 판정하는 것**을 막았지 502 가 보이는 것은 못 막는다.

그리고 도커 헬스체크는 **컨테이너를 재시작하지 않는다.** 상태를 `unhealthy` 로
표시만 한다. 재시작은 `restart: unless-stopped` 가 프로세스 **종료**에 대해 하는 일이다.
`autoheal` 같은 감시자도 없다. 그러니 정기 검사가 502 의 원인이 될 수는 없다 —
프로세스가 살아 있으면 포트는 열려 있고 nginx 는 프록시에 성공한다.

### 한 것 ① — 화면 (2026-09-17)

`nginx/default.conf` 에 `error_page 502 503 504 =503 /maintenance.html` 을 넣어
점검 화면을 준다(`nginx/maintenance.html`, 15초마다 자동 재시도). 상태를 503 으로
바꾸는 이유는 502 가 "클라이언트가 할 것이 없다" 인 반면 503 은 "다시 오라" 이기
때문이다(`Retry-After: 15`).

### 한 것 ② — 준비 게이트: 포트를 먼저 열고, 복원은 뒤에서 (2026-09-18, `app/boot.py`)

복원 블록을 `main._restore_all()` 로 묶어 **데몬 스레드**로 띄우고 즉시 돌아온다.
그러면 `import main` 이 곧 끝나 uvicorn 이 포트를 열고, 복원이 끝날 때까지
`boot.Gate` 미들웨어가 준비 전 요청을 503 으로 돌려준다.

| 복원 중 | 응답 | 뜻 |
|---|---|---|
| `/healthz` | **200** | 프로세스가 살아 있다 — 원래 이 뜻이었다. 이제 '기동 중' 과 '죽음' 이 갈린다 |
| `/readyz` | **503** + `restore: {phase, preferences_done/total, seconds}` | 몇 건 남았나. nginx 가 이 둘만 가로채지 않아 **JSON 그대로** 나간다 |
| `/docs` `/openapi.json` `/filters` `/admin/trends` `/metrics` | 200 | 기동 때 동기로 올린 것만 읽는 경로 — 세션·취향은 안 만진다 |
| 그 밖의 전부 | 503 `Retry-After: 15` | nginx `proxy_intercept_errors` 가 위 점검 화면으로 바꿔 준다 — 사용자가 보는 것은 예전과 같다 |

합성 선호 3,600건으로 실제 프로세스를 띄워 확인했다: 기동 3초 뒤 포트가 열려
`/healthz` 200, 복원 29초 동안 `/readyz` 503 에 진행률이 55→3,600 으로 움직이고 가린
경로는 0.2ms 에 503, 끝나면 전부 200.

지켜야 했던 것 둘. `lifespan` 으로 옮기면 **효과가 없다**(`uvicorn/server.py:107` 이
`lifespan.startup()` 을 소켓 생성 `:145` 보다 먼저 한다) — 그래서 import 시점에 스레드다.
그리고 테스트 700개가 `TestClient(app)` 를 `with` 없이 쓰므로 스레드로 돌면 첫 요청이
503 을 받는다 — `MATCHURI_RESTORE_SYNC=1` 이면 같은 자리에서 동기로 도는 옛 경로를
두고 `tests/conftest.py` 가 그 값을 넣는다. 스레드 모드에서 복원이 실패하면 옛 동작
(import 실패 = 프로세스 종료)대로 `os._exit(3)` 한다 — 503 만 내는 좀비가 되면 안 된다.
`matchuri_ready` 게이지가 `/metrics` 에 추가됐다.

게이트만으로는 공백이 그대로였다 — 그날 배포에서 8,718건 복원에 **8분 5초**가 걸렸다.

### 한 것 ③ — 취향 모델 스냅샷: 공백 자체를 없앤다 (2026-09-18, `app/snapshot.py`)

살아 있는 학습 상태를 **통째로** 5분마다 pickle 로 적어 두고(`state/snapshot.pkl`),
부팅 때 그것을 올린 뒤 **그 뒤에 쌓인 기록만** 재생한다. 그러면 재생할 것이 5분치라
부팅이 상수 시간에 가까워진다.

| | 3,600건 · 로컬 실측 | 뜻 |
|---|---|---|
| 스냅샷 없이 | 준비까지 **44초** | 전부 재생 |
| 스냅샷 있음 | 준비까지 **17초** · 복원 187ms | 3,600건 전부 건너뜀. 남은 17초는 재생이 아니라 산출물 로드다 |
| 스냅샷 파일 | 708KB / 30세션 · 쓰기 17.7ms | 요청을 막는 시간이 이 정도다 |

운영(8,718건)에서는 8분짜리 재생이 **산출물 로드 시간만**으로 준다.

**왜 '숫자 부분만 건너뛰기' 가 아니라 상태 전체인가.** `remember` 가 사용자별 기억
모델을 따로 학습하고 `apply_created` 가 그 기억에서 새 세션의 사전값을 파생하고
`apply_boundary` 가 현재 세션을 복사해 보관한다 — 전부 순서에 묶여 있어 일부만
건너뛰면 어긋난다. 그래서 `policy`·`taste`·`swipe` 세션, 기억, 초기값, 현재 세션,
등록부를 한 절단점에서 다 담는다. **재생 결정성이 근거다** — 살아 있는 상태 = 그 시점까지
재생한 상태(`test_replay.py`)이므로 스냅샷 뒤 재생 = 전체 재생이다
(`tests/test_snapshot.py` 가 비트 단위로 잰다).

**절단점이 정확해야 한다.** `post_preference` 가 메모리 적용 뒤에 파일을 써서, 그 사이에
찍으면 재시작 뒤 한 건이 두 번 학습된다. 파일에 쓰는 세 지점(선호·`session_start`·
`session_create`)과 그 적용을 `state.PREF_LOCK` 으로 묶고 스냅샷도 그 안에서 센다.

**스냅샷이 거짓이 되는 두 경우는 도장으로 잡는다.** 학습 **동작 지문**(고정된 가게 열두
곳에 고정된 좋아요/싫어요를 먹인 새 세션의 `m`·`v` 해시, 30ms)과 `data/kakao`·`serving/` 의
mtime. 어느 쪽이든 바뀌면 `snapshot.stale` 을 남기고 버린 뒤 **그 부팅만** 전체를
재생한다(주간 배치 뒤 첫 배포, 학습식을 고친 뒤 첫 배포). 그 다음 부팅부터 다시 빠르다.
처음엔 학습 모듈의 **소스 해시**였는데 이 팀은 그 파일들을 매일 건드려서(09-21 아침 두 배포
사이 `policy.py` 6줄) 배포마다 버리고 12분 전체 재생을 했다 — 주석이 바뀌어도 버렸다.
동작 지문은 학습식이 바뀔 때만 바뀐다(`test_snapshot.py`). `/readyz` 의 `restore.snapshot_rows` 가 스냅샷이 대신한 행 수다 —
`null` 이면 전체 재생이었다는 뜻이다.

`MATCHURI_SNAPSHOT_EVERY`(초, 기본 300). 0 이면 주기 스냅샷을 끈다(있는 파일은 읽는다).
종료 때도 한 번 찍는다 — 배포 직전 상태가 가장 값지다.

### 남은 것

`start_period: 600s`(docker-compose) 는 이제 과하다 — `/healthz` 가 즉시 200 이라
헬스체크는 기동 직후 통과한다. 급하지 않다.

### 함께 미뤄 둔 것 (2026-09-17)

**③ Jenkins 헬스 체크가 배포마다 빨간불이 된다.** `Jenkinsfile` 의 마지막 단계가
`sleep 8` 뒤에 `curl -fsS http://nginx/` 다. 앱은 4~5분 걸리므로 그 시점에는 아직
준비 전이고, `-f` 는 5xx 를 실패로 본다. **배포는 성공하는데 빌드 이력에는 실패로
남는다** — 그러면 진짜 실패와 구분이 안 된다. 준비 게이트가 들어갔으니 이제
`/readyz` 가 진행률까지 주는 JSON 을 폴링하는 루프 5줄이면 된다.

**④ HTTPS 가 없다 — `/admin` 비밀번호가 평문으로 흐른다.** `https://api.example.com`
는 연결되지 않고 HTTP 만 열려 있다. Basic 인증은 자격증명을 **base64 로 인코딩해서
매 요청에 보낸다**(암호화가 아니다). 같은 망에 있는 사람이 그대로 읽는다.

    Authorization: Basic BASE64_OF_USER_PASSWORD   ← 디코드하면 user:password

인증 자체는 제대로 걸려 있다(`/admin` 이 401 을 준다 — nginx 가 앱까지 보내지 않는다).
문제는 그 자격증명이 암호화 없이 간다는 것이다. 교육기관이 제공 도메인 에 인증서를
어떻게 발급하는지 확인이 필요하다. **이 넷 중 유일한 보안 문제다.**
