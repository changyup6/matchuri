# 맛추리 API 가이드 (클라이언트용)

[클라이언트 연동: 기존 API 유지·필요할 때 수치 조회](../BE/server/DECISION-CLIENT.md)

역삼동 맛집 스와이프 추천 백엔드. 이 문서는 **앱을 만드는 사람**을 위한 것이다 — 어떤 순서로
부르고, 무엇이 오고, 어떤 값이 `null` 인지, 어디서 실패하는지를 전부 적었다.

| | |
|---|---|
| 서버 | `http://api.example.com` (nginx → FastAPI). 로컬은 `http://127.0.0.1:8000` |
| 문서 | `/docs` (Swagger, 이 문서와 같은 내용) · `/openapi.json` (타입 생성용) |

| 인증 | 기존과 같이 로그인 인증은 없다. 신규 사용자 ID는 `POST /user`, 추천 상태는 그 사용자 소유 세션에 저장한다. |

| 데이터 | 카카오맵 역삼동 가게 2,795곳. 추천 후보는 사진·리뷰가 있는 **2,216곳** |

## 0. 신규 연동: 실제 사용자와 추천 세션

`user_id`는 실제 사용자, `session_id`는 한 번의 탐색입니다. 사용자를 만든다고 추천 세션이 생기지는 않습니다.

```text
POST /user {"name":"사용자"} → {user_id, name, created_at}
POST /user/{user_id}/session {"request_id":"선택적인 재시도 키"}
  → {user_id, session_id, swipes:0}
GET  /user/{user_id}/session → 세션 목록
GET  /user/{user_id}/session/{session_id} → 해당 세션의 ID·swipes
```

아래 `S`는 `/user/{user_id}/session/{session_id}`입니다.

| API | 용도 / 응답 |
|---|---|
| `GET S/cards?limit=10` | 기존 카드 배열 그대로 |
| `GET S/cards/{card_id}` | 같은 세션 위치·사용자 찜을 반영한 카드 상세 |
| `POST S/preferences` | 본문 **`{card_id, prefer}`만**. `count`는 이 세션의 스와이프 수 |
| `GET S/preferences?prefer=all` | 이 세션의 반응 카드만 시간순 조회 |
| `PUT S/location`, `PUT S/filter`, `DELETE S/filter` | 세션의 위치·필터 설정. 본문은 기존과 같음 |
| `GET S/settings` | `{user_id, session_id, location, filter}` |
| `GET S/decision?n=4` | 점수와 무관하게 직접 요청. 기존5필드, n 기본4. 자동 권유는 `mode=auto` |
| `POST S/decision/feedback` | 기존 select/continue 본문. 해당 세션 제안만 접수 |
| `GET S/decision/metrics/summary?n=4` | 기존 가벼운 판단 수치. 점수는 개인화 검증 근거이며 추천 진입과 분리 |
| `GET S/decision/metrics` | 기존 상세 수치와 근거 조회 |
| `GET S/taste?detail=1` | 세션 취향 궤적과 단계별 지형. 1=cat2(기본), 2=cat3, 3=가게 |

찜·길찾기·설문은 `/user/{user_id}/bookmarks`, `/directions`, `/surveys` 아래에서
기존 본문·응답을 그대로 사용합니다. 같은 사용자의 세션들이 공유합니다.
`GET /cards/{card_id}`, `/cards/{card_id}/reviews`, `/filters`, `/taste/map`은 공통입니다.

새 세션을 만들어도 이전 세션을 덮어쓰지 않으며, 이전 세션에서 계속 스와이프할 수 있습니다.
다른 사용자의 세션 ID를 경로에 넣으면404입니다. 사용자 ID를 세션용 기존 `/cards` 등에 넣으면400입니다.
새 세션은 생성 시점까지 **그 사용자에게 속한 모든 세션의 반응을 시간순으로 학습한 참고값**을
약하게 상속합니다. 생성된 세션은 서로 독립적이며 이후 다른 세션의 변경을 실시간으로 섞지 않습니다.
현재 세션 반응 수·검증·노출·decision 거절 이력은0부터 시작하고 최근 반응 우선 규칙을 유지합니다.
상속한 취향은 첫 스와이프 카드부터 점수에 반영합니다. 이전에 싫어요한 **같은 가게**는
두 추천 정책 모두 다른 허용 후보보다 뒤에 제공합니다. 다른 후보를 다 보았거나 필터 안에
대안이 없으면 다시 나올 수 있으며, 필터를 넓히거나 가게를 영구 차단하지 않습니다.
새 평가가 과거 평가를 대체하며 같은 업종·브랜드 전체를 제외하지 않습니다.
이 순서 규칙은 스와이프 카드에 적용하며 최종 decision의 후보 자격은 기존대로 유지합니다.

### 기존 클라이언트와 데이터

기존 `user_id`는 이제 **기존 탐색 세션 ID**로 보존됩니다.
`GET /session/{기존_user_id}` → `{user_id: "새 실제 사용자 ID", session_id: "기존 ID", swipes}`로
연결을 확인한 후 그 사용자 아래에 새 세션을 만들면 됩니다. 원본 로그는 수정하지 않습니다.
기존 ID마다 별도 사용자를 연결하며, 이름이 같다고 같은 사람으로 합치지 않습니다.
과거 session_start로 구분되었던 이전 구간도 독립 세션으로 보존합니다.

기존 `/users`, `/cards?user_id=...`, `/preferences`는 **호환용 세션 API**로 유지합니다.
이하 옛 경로 설명의 `user_id`는 실제 사람이 아닌 기존 세션 키를 의미합니다.
신규 연동은 위 경로를 사용하세요. 앱 코드는 이번 변경에서 수정하지 않습니다.

## 1. 공통 규칙

- **id.** `user_id` 는 문자열(`"u_3f2a1b4c5d6e"`), `card_id` 는 정수(0 부터, 서버를 껐다 켜도 같다). 가게의
  카카오 id 는 `store.id`(문자열)로 따로 온다 — 클라이언트는 `card_id` 만 쓰면 된다.
  `user_id` 에 쓸 수 있는 문자는 **영문·숫자와 `. _ : -` 이고 1~64자**다(그 밖이면 422). 발급받은 id 는 당연히 통과한다.
- **요청 id.** 모든 응답에 `X-Request-ID` 헤더가 온다. 보내면 그 값을 그대로 쓰고(영문·숫자·`. _ -`, 64자 이하),
  안 보내면 서버가 만든다. **버그 리포트에는 이 값을 적어라** — 서버 로그를 그 id 하나로 전부 찾을 수 있다.
- **null / [].** 값이 없으면 `null`, 목록이 없으면 `[]`. `-1`·`0`·`""` 로 결측을 표현하지 않는다.
- **시각.** ISO 8601 + 오프셋(`2026-09-10T14:24:53+09:00`). 리뷰 `date` 만 카카오 원문 그대로(`"2026-08-19 09:57:16"`).
- **에러.** 본문은 항상 `{"detail": "…"}`. 422 는 FastAPI 검증 오류 형식(`detail` 이 배열)이거나, 어휘 오류일 때는
  한국어 문장 하나다.

| 코드 | 언제 |
|---|---|
| 400 | `prefer` 가 like/dislike 가 아님 · 저장된 반경(`within_m`)은 있는데 저장된 위치가 없음 |
| 404 | 없는 `card_id` · 기록도 발급도 없는 `user_id`(`GET /users/{id}`, `GET /users/{id}/taste`) |
| 422 | 본문 형식 오류 · 위도/경도 범위 밖 · `within_m < 1` · `cat`/`tag` 가 어휘 밖 |
| 500 | 서버 잘못. 본문은 `{"detail": "internal error", "request_id": "…"}` 뿐이다(내부 정보를 주지 않는다) — 그 `request_id` 를 서버에 알려 주면 된다 |
| 503 | 취향 지형 산출물이 없음(`/taste/*`) — 배포 문제, 앱은 그 화면만 숨기면 된다 |

- **재시작.** 사용자·설정·스와이프 기록은 파일에 남아 서버를 재시작해도 복원된다. 앱은 `user_id` 만 잃지 않으면 된다.
- **사진.** 수집 완료한 사진은 서버의 축소 JPEG 주소를 전달한다. 목록 화면에서는 `image` 한 장을 먼저 그리고
  `images` 의 나머지 사진은 필요한 시점에 불러오면 된다.

### 사진 표시

카드 `image`·`images`, 메뉴 `menus[].image`, 리뷰 `store.reviews[].images`와 리뷰 목록의
`images`는 기존처럼 URL입니다. 수집이 완료된 외부 사진은 서버가 저장한
`http://api.example.com/media/catalog/v2/…/*.jpg` **절대 URL**을 반환하므로
앱은 받은 값을 이미지 위젯에 그대로 전달하면 됩니다. 응답 필드는 늘어나지 않습니다.

카드 `image`·`images`는 긴 변 최대 **640px / quality72**, 메뉴와 리뷰 사진은
**320px / quality70**의 progressive JPEG입니다. 종횡비 유지·확대 없음, 회전 반영·메타데이터 제거를
적용합니다. progressive 형식이어도 파일 전체를 받으므로, 데이터 절약은 작은 파일과 필요한 사진만
로딩하는 데서 나옵니다. 메뉴를 펼치기 전에 메뉴 사진 전체를 미리 받지 마세요.

사진을 눌러 확대할 때만 **`GET /cards/{card_id}?original_images=true`**를 요청합니다.
기존 `image`·`images`·`menus[].image`·`store.reviews[].images`에 **수집 원본 URL**을 반환합니다.
리뷰 전체 조회도 `GET /cards/{card_id}/reviews?original_images=true`를 지원합니다.
기본값은 `false`이며, 원본 옵션은 추천·정렬·사진 개수·다른 필드를 바꾸지 않습니다.
원본 사진은 사용자가 실제로 확대할 때만 다운로드하세요. 서버가 원본을 복제하거나 프록시하지는 않습니다.

v2가 아직 준비되지 않은 사진은 저장된 v1(1280px)으로, v1도 없으면 기존 외부 URL로 대체합니다. 사진 순서·개수·
`null`/빈 배열 규칙은 그대로입니다. 사용자 업로드 사진은 기존 `/media/…` 주소를 유지합니다.

사진 GET/HEAD는 `Content-Type: image/jpeg`, 성공 응답의 장기 캐시·ETag와 공개 CORS를
지원합니다. URL을 직접 조립하지 말고, 원본은 위 옵션으로 받은 URL을 사용하세요.

## 2. 사용자

### `POST /users` — 사용자 만들기

본문은 선택. `{"name": "김철수"}` 을 주면 관리자 화면에서 구분하기 쉽다.

```json
→ {"user_id": "u_874482db9e51", "name": "김철수", "created_at": "2026-09-10T10:39:37+09:00",
   "location": null, "filter": null}
```

`user_id` 를 앱에 저장해 두고 모든 호출에 쓴다. 발급받지 않은 아무 문자열을 써도 동작은 하지만(옛 방식),
짧고 뻔한 id 는 남이 그 사람의 추천을 넘겨볼 수 있으니 발급을 권한다.

### `GET /users/{user_id}` — 사용자 정보와 설정

```json
→ {"user_id": "u_7373bd0fa56e", "name": "설정검증", "created_at": "2026-09-10T05:28:58+00:00",
   "location": {"lat": 37.5006, "lon": 127.0366, "at": "2026-09-10T05:28:58+00:00"},
   "filter": null,
   "registered": true, "swipes": 1, "likes": 1,
   "learned": { … }}
```

| 필드 | 뜻 |
|---|---|
| `location` | 저장된 위치. 없으면 `null` |
| `filter` | 저장된 필터 `{cat: [], tag: [], within_m, at}`. 없으면 `null` |
| `registered` | `POST /users` 로 발급된 id 인가. 발급 없이 스와이프만 한 id 는 `false` |
| `swipes` / `likes` | 누적 스와이프 수 / 그중 like |
| `learned` | 학습 상태(디버깅용). **모양이 바뀔 수 있으니 의존하지 말 것**. 세션이 없으면 `null`. 무거운 `prototypes`·`hist` 는 담지 않는다 — 관리자 화면(`/admin`)에서만 받는다 |

발급도 기록도 없으면 404.

### `PUT /users/{user_id}/location` — 위치 저장

```json
PUT /users/u_7373bd0fa56e/location   {"lat": 37.5006, "lon": 127.0366}
→ {"user_id": "u_7373bd0fa56e", "name": "…", "created_at": "…",
   "location": {"lat": 37.5006, "lon": 127.0366, "at": "2026-09-10T05:28:58+00:00"}, "filter": null}
```

- 위도 −90~90, 경도 −180~180 밖이면 422.
- GPS 가 바뀌면 다시 부른다. 이 값이 `GET /cards` 의 거리 필터와 카드의 `distance_m` 에 쓰인다.
- 발급하지 않은 `user_id` 도 받는다(이름 없는 레코드가 생긴다).
- `at`(잰 시각, ISO 8601)을 함께 줄 수 있다. 주면 **더 오래된 위치가 현재 위치를 덮지
  않는다** — 지하에서 못 보낸 것을 모아 올릴 때 순서가 뒤섞여도 안전하다. 못 읽는 값은 422.
- **자주 불러도 된다.** 파일에 줄을 더하는 것은 **마지막으로 적은 지점에서 100m 이상
  움직였을 때만**이다 — 부를 때마다 적으면 등록부가 GPS 궤적이 된다. 메모리의 값은 매번
  갱신되므로 응답과 거리 필터는 늘 최신이고, 파일만 거칠어진다(재시작 뒤 최대 100m 오차).
- **도착 판정에는 쓰이지 않는다.** 그건 앱이 하고 결과만 설문에 실어 보낸다
  (아래 '방문 근거' 절).

### `PUT /users/{user_id}/filter` — 필터 저장

```json
PUT /users/u_7373bd0fa56e/filter   {"cat": ["일식"], "tag": ["혼밥"], "within_m": 500}
→ {…, "filter": {"cat": ["일식"], "tag": ["혼밥"], "within_m": 500, "at": "2026-09-10T05:28:58+00:00"}}
```

| 필드 | 값 | 결합 |
|---|---|---|
| `cat` | `GET /filters` 의 업종 9개 중 0개 이상 | **OR** — 여러 개면 "이 중 하나" |
| `tag` | `GET /filters` 의 태그 12개 중 0개 이상 | **OR** — 여러 개면 "하나라도 가진 곳" |

`cat`·`tag` 는 **각각 OR** 이고(칩을 더 누르면 넓어진다), **차원 사이는 AND** 다 —
`{"cat":["일식","한식"],"tag":["혼밥"],"within_m":500}` 은 *(일식 또는 한식) 이면서 혼밥 되고
500m 안* 이라는 뜻이다.
| `within_m` | 정수 m (≥ 1) 또는 `null` | 저장된 위치에서 이 거리 안 |

- 셋 다 선택. 빈 목록·`null` 은 "그 조건 없음". 셋 다 비우면 필터 없음과 같다.
- 어휘 밖 값은 **422**: `{"detail": "cat '초밥' 은 없는 값입니다. 허용: 한식, 카페, 일식, 술집, 양식, 중식, 간식, 분식, 기타"}`
- 거절되면 기존 필터는 그대로다.
- `within_m` 을 저장했는데 위치가 없으면 `GET /cards` 가 400 을 낸다 — 위치를 먼저 저장하거나 반경을 빼라.

### `DELETE /users/{user_id}/filter` — 필터 해제

```json
→ {…, "filter": null}
```
없는 필터를 지워도 200(이미 원하는 상태). 이후 `GET /cards` 는 전체 후보에서 추천한다.

## 3. 필터 어휘

### `GET /filters` — 필터 UI 를 만들 값

```json
→ {"cats": [{"name": "한식", "count": 710}, {"name": "카페", "count": 460}, {"name": "일식", "count": 188},
            {"name": "술집", "count": 187}, {"name": "양식", "count": 143}, {"name": "중식", "count": 121},
            {"name": "간식", "count": 93}, {"name": "분식", "count": 87}, {"name": "기타", "count": 227}],
```

- **순서 그대로 그리면 된다.** 목록과 순서는 서버가 고정한 것이다(데이터가 바뀌어도 칸은 그대로, 개수만 바뀐다).

  정확히 2,216(모든 후보가 한 업종에 속한다).
- 업종 = 후보가 많은 상위 8개 + `기타`(나머지 전부: 샐러드·치킨·패스트푸드·아시아음식·샤브샤브…). 카드의
  `store.category_group` 이 같은 라벨이라 필터와 카드 표시를 같은 어휘로 맞출 수 있다.
- 태그 12개는 원본 태그를 뜻으로 묶은 것이다: `친절` = 친절·친절한, `단체모임` = 단체모임·회식장소·친목모임,
  `분위기` = 분위기·감성적, `데이트` = 데이트·데이트코스·소개팅. 클라이언트는 묶음 이름만 알면 된다.
- `within_m` 은 권장값이다. 다른 정수도 저장된다.

## 4. 카드(추천)

### `GET /cards?user_id=…&limit=10&reviews=1` — 추천 카드

| 쿼리 | 기본 | 뜻 |

| `user_id` | 없음 | 주면 그 사람의 취향·저장된 필터·위치로 추천. **안 주면** 인기순이고 학습·필터·거리 없음 |
| `limit` | 10 | 1~50 |
| `reviews` | 1 | 카드마다 담을 리뷰 미리보기 수(0~20) |

| 필드 | 뜻 |
|---|---|
| `card_id` | `POST /preferences`·`GET /cards/{id}` 에 그대로 보낸다 |

| `distance_m` | 저장된 위치에서의 거리(m, 정수). 위치를 모르면 `null` |

`store`:

| 필드 | 뜻 |
|---|---|
| `lat` `lon` | **가게 좌표.** 지도 딥링크와 '도착했나' 판정에 쓴다. ⚠️ **주소를 지오코딩하지 말 것** — 주소에는 `지하 1층`·`302호` 같은 접미사가 붙어 지오코더가 자주 실패한다. 2,795곳 전부에 있다 |
| `category` | 카카오 세부 분류(153종: `육류,고기`·`일식집`·`돈까스,우동`…). 없으면 업종으로 대체 |
| `category_group` | 필터의 업종 9개 중 하나. 필터 칩과 같은 글자로 표시할 때 이걸 쓴다 |
| `score` | 평균 별점(소수). 리뷰가 없으면 `null`. **수집 원본의 평균 그대로**다 — 아래 `review_count` 와 모집단이 다르다 |
| `review_count` | **여기서 볼 수 있는 리뷰 수** = `GET /cards/{card_id}/reviews` 가 돌려주는 개수(수집 리뷰 + 우리 사용자 후기). **카카오에 달린 전체 리뷰 수가 아니다** — 아래 "`review_count` 는 무엇을 세나" 절 |
| `tags` | 그 가게를 나타내는 태그 최대 5개 — **필터 어휘(`GET /filters` 의 태그 이름)로만** 나간다. 원본 이름은 칸 이름으로 바뀐다(`친절한`→`친절` · `감성적`→`분위기` · `소개팅`·`데이트코스`→`데이트` · `회식장소`→`단체모임`). 필터로 걸린 태그는 반드시 여기 있다 |
| `reviews` | 미리보기 `reviews` 건. **표현력이 높은 리뷰가 앞에 온다** — 무엇이 어떤지 구체적으로 쓴 것부터(`server/recsys/expressiveness.py`). 같은 등급 안에서는 본문 있고, 평균에 가깝고, 사진 많은 순 |
| `summary` | 카카오 AI 한 줄 요약. 없으면 `null` |
| `subway` / `parking` | 한 줄 문자열. 없으면 `null` |
| `open_hours` | **요일별 영업시간.** 있으면 **월~일 7개가 항상 순서대로** 온다. 없으면 빈 배열 `[]` — 2,795곳 중 2,443곳에 있다 |

> **`open_status` 는 없어졌다** (2026-09-16). 수집 순간 카카오 화면에 찍혀 있던
> 문자열이라 2,795곳 중 **1,932곳이 `영업 중`** 으로 굳어 있었다(수집을 낮에 돌렸다).
> 새벽에 받아도 그 값이므로 배지에 쓰면 닫힌 가게가 영업 중으로 보인다. 지금 상태는
> 아래 `open_now` 가 요청 시점에 계산한다. **파싱하던 쪽은 지우면 된다** — 키가
>없어져 `null` 이 될 뿐이라 따로 고치지 않아도 터지지는 않는다.

### `open_now` — 지금 영업 중인가 (카드 최상위)

**서버가 요청한 순간에 계산한다.** `store` 안이 아니라 카드 최상위에 있다
(`distance_m`·`bookmarked` 와 같은 자리 — 요청마다 달라지는 값이다).

```json
{"card_id": 1944, "store": {…},
 "open_now": {"state": "open",
              "until":       "2026-09-16T15:00:00+09:00",
              "opens_at":    null,
              "closes_at":   "2026-09-16T22:00:00+09:00",
              "break_start": "2026-09-16T15:00:00+09:00",
              "break_end":   "2026-09-16T17:00:00+09:00",
              "day": "수"}}
```

| `state` | 뜻 | 배지 문구 예 |
|---|---|---|
| `open` | 영업 중 | "영업 중 · 22:00 종료" |
| `break` | 브레이크타임 | "브레이크타임 · 17:00 재개" |
| `closed` | 영업 종료 | "영업 종료 · 11:00 오픈" |
| `unknown` | 시간표 정보 없음 | **배지를 감춘다** |

⚠️ **`unknown` 을 "영업 종료" 로 뭉개지 말 것.** 352곳(13%)이 여기 해당하고,
**정보가 없는 것은 닫힌 것과 다르다.** 상태를 둘(`영업중`/`영업중 아님`)로 접으면
시간표가 없는 가게가 모두 닫힌 것으로 보인다.

시각 필드 — **해당 없으면 `null`** 이다:

| 필드 | 뜻 | `open` | `break` | `closed` | `unknown` |
|---|---|---|---|---|---|
| `until` | **이 상태가 끝나는 시각.** 배지 한 줄에 쓰는 값 | `closes_at` 또는 `break_start` 중 먼저 | `break_end` | `opens_at` | `null` |
| `opens_at` | 다음에 **문 여는** 시각 | `null`(이미 열림) | 브레이크 끝 | 다음 영업 시작 | `null` |
| `closes_at` | 영업이 **실제로 끝나는** 시각 | 값 | 값 | *다음* 영업의 종료 | `null` |
| `break_start` | 아직 남아 있는 브레이크 시작 | 값 또는 `null` | 지금 그 브레이크 | 다음 영업의 브레이크 | `null` |
| `break_end` | 그 브레이크가 끝나는 시각 | `break_start` 와 함께 | 값 | 값 | `null` |
| `day` | 이 답을 **어느 요일 시간표로** 냈나 | `월`~`일` | 같음 | 다음 영업일 | `null` |

**왜 `until` 하나로 부족한가.** `until` 은 상태에 따라 가리키는 대상이 바뀐다. 위 예에서
`until` 은 15:00(브레이크 시작)이므로, 그것만 쓰면 **"오늘 22:00 까지" 라는 사실이 응답에서
사라진다.** 그래서 넷을 따로 싣는다. 넷은 모두 **같은 영업 구간 하나**를 설명한다 —
지금 열려 있으면 그 구간, 닫혀 있으면 다음 구간이다. 덕분에 `closed` 일 때도
"열면 몇 시까지 하고 브레이크는 언제인지" 를 한 번에 알 수 있다.

**`day` 는 새벽에 어제 요일이 나온다.** 토요일 01:00 에 `11:00 ~ 02:00` 가게를 보면
답은 금요일 시간표에서 나오므로 `day` 는 `"금"` 이다. `open_hours` 에서 강조할 줄을
고를 때 오늘 요일이 아니라 **이 값**을 봐야 한다.

**앱에서 직접 계산하지 말 것.** 경계가 셋이고 하나라도 틀리면 화면에 바로 보인다:
자정을 넘기는 영업이 **16.3%**(`11:00 ~ 02:00`), 새벽에는 **전날 영업분**을 봐야 하고,
브레이크타임도 걸러야 한다. 서버가 한 번만 제대로 계산해서 준다.

**`open_hours` 는 주간 시간표를 그리는 용도**로 쓰라 ("월~금 11:00~22:00" 같은 안내).

```json
{"day": "월", "open": "11:00", "close": "22:00", "overnight": false,
 "breaks": [{"start": "15:00", "end": "17:00", "label": "브레이크타임"}]}
{"day": "금", "open": "11:00", "close": "02:00", "overnight": true,  "breaks": []}
{"day": "일", "open": null,    "close": null,    "overnight": false, "breaks": []}
```

- **월~일 7개가 항상 순서대로 온다.** 원본에 빠진 요일이 있어도(2,443곳 중 86곳)
  서버가 `null` 줄로 채운다 — "일요일에 여나" 를 물을 때 요일을 뒤지지 않게 한다.
  시간표가 **아예** 없는 가게(352곳)만 빈 배열 `[]` 이다
- `day` 는 `월`~`일`. **날짜는 떼어 냈다** — 원본은 수집 그 주의 날짜가 박혀 있어서
  (`"수(9/2)"`) 그대로 쓰면 다음 주에 거짓말이 된다
- `open`·`close` 는 `HH:MM`. **둘 다 `null` 이면 그날 영업하지 않는다** — 대부분
  정기휴무이지만 '정보 없음' 과 구분되지는 않는다. 주말은 **일요일 휴무 812곳 ·
  토요일 휴무 311곳**이다
- `overnight` 이 `true` 면 **닫는 시각이 다음 날**이다(`11:00 ~ 02:00`). 전체
  15,738건 중 2,567건(16.3%). 화면에는 `익일 02:00` 으로 적어야 한다
- `breaks` 는 **시각으로 쪼개서** 준다(`start`·`end`·`label`). 문자열을 앱이 쪼개면
  앱 두 개가 각자 다르게 틀린다. `label` 은 가게가 적은 자유 문구라 없으면 `null`
- ⚠️ **공휴일·임시휴무는 반영되지 않는다.** 주간 시간표일 뿐이다

동작:

- 저장된 필터가 **항상** 적용된다(`cat` OR · `tag` OR · 둘 사이와 `within_m` 은 AND). 필터가 촘촘하면 `limit` 보다 적게, 0장까지
  올 수 있다 — 필터를 무시하고 채우지 않는다. 걸러진 카드는 "보여준 것" 으로 세지 않아 필터를 풀면 다시 나온다.
- **한 번 내보낸 카드는 그 사용자에게 다시 나오지 않는다**(응답을 받았으면 보여줬다고 본다). 앱이 버리면 그 카드는
  사라진다 — 미리 받아 두는 양을 크게 잡지 말 것.
- 같은 업종이 3장 연속 나오지 않는다. 처음엔 평점 좋은 가게 위주, 스와이프가 쌓일수록 취향 쪽으로 옮겨 간다.
- 저장된 `within_m` 이 있는데 위치가 없으면 **400**.

#### 정렬 규칙 — 무엇이 먼저 오나

필터는 **통과/탈락**만 정한다. 그 안의 순서는 이렇게 정해진다.

```
1순위  고른 태그와 겹치는 수 (태그를 2개 이상 골랐을 때만)
2순위  추천 점수 + 거리 보너스
```

- **겹치는 태그 수가 많은 카드가 먼저 온다.** `tag=["단체모임","분위기"]` 면 둘 다 가진 가게가
  하나만 가진 가게보다 **항상** 앞이다(점수가 낮아도). 태그가 OR 라서 '하나만 맞는 곳' 도 후보에
  들어오는데, 칩을 두 개 누른 뜻은 '둘 다면 더 좋다' 이기 때문이다.
  태그를 **하나만** 골랐으면 후보가 전부 그 태그를 가졌으므로 이 계층은 생기지 않는다.
- **거리는 점수에 섞인다**(벽이 아니다). 후보 안에서 가까울수록 점수가 올라가고, 그 크기는
  '한 표준편차 더 가까우면 점수 +0.4' 정도다. 그래서 **먼 곳도 취향에 아주 잘 맞으면 나온다** —
  '500m 밖은 아예 안 보고 싶다' 면 그건 `within_m` 의 일이다(그건 벽이다).
- 저장된 위치가 없으면 거리 보정은 **없다**(`distance_m` 도 `null`). 좌표를 모르는 가게는
  후보 평균으로 취급해 벌하지도 봐주지도 않는다.
- 500m 안쪽 카드는 `recommendation_reason` 이 거리 문장으로 온다
  (`"역삼역 근처, 걸어서 갈 만한 344m 거리예요."`). 단, 태그 계층이 있는 요청에서는 순서를 정한
  까닭이 태그이므로 정책의 이유 문장을 그대로 둔다 — 화면의 한 줄은 **가장 큰 까닭**을 말한다.
- 같은 업종 3연속 금지·같은 브랜드 연속 금지 같은 다양성 규칙은 이 순서 **위에서** 그대로 돈다.

### `GET /cards/{card_id}?reviews=5&user_id=…` — 카드 상세

목록의 카드에 **`menus` 가 붙고** 리뷰가 더 온다(기본 5건, 최대 50).

```json
→ {"card_id": 65, "store": {…, "reviews": [ 5건 ]}, "image": "…", "images": […],
   "menus": [{"id": 0, "store_id": "1050527540", "name": "메뉴판 (런치)", "price": 99000, "price_text": null,
              "image": "http://t1.kakaocdn.net/mystore/302B…", "description": "고우가만의 특별한 런치 코스메뉴 입니다.",
              "is_recommend": true}, …],
   "distance_m": 64}
```

| `menus[]` 필드 | 뜻 |
|---|---|
| `price` | 원 단위 정수. **표기 없는 메뉴는 `null`** (전체의 44%). `-1`·`0` 은 절대 오지 않는다 |
| `price_text` | 가격이 글자일 때(`"변동가격"`). `price` 가 `null` 이고 이게 있으면 이걸 보여준다 |
| `image` | 메뉴 사진. 가게가 등록한 메뉴에만(12%). 없으면 `null` — 카드의 `images` 로 대신 |
| `description` | 구성 설명. 없으면 `null` |
| `is_recommend` | 가게가 추천으로 표시한 메뉴 |

- 메뉴 순서: **원본 `menu_index` 오름차순**. 인기 순위·추천 표시·음식 여부로 재정렬하지 않는다.
  같은 인덱스는 원본 파일 순서, 인덱스가 없거나 잘못된 줄은 맨 뒤에서 파일 순서를 유지한다.
  `menus[].id`는 기존대로 응답 배열의 순번(0부터)이며 원본 `menu_index`나 영구 메뉴 식별자가 아니다.
- 메뉴가 없는 가게는 `menus: []`.
- 상세는 **필터와 무관**하다 — 필터에 걸리지 않는 가게도 id 로는 조회된다(좋아요 목록에서 열 때).
- `user_id` 를 주면 저장된 위치로 `distance_m` 을 채우고, 안 주면 `null`.
- 없는 `card_id` 는 404.

### `GET /cards/{card_id}/reviews?limit=0` — 리뷰 전체

`limit` 0(기본)이면 전부. 페이징 없음. 리뷰가 없으면 `[]`.

```json
→ [{"id": 13590288, "store_id": "1050527540",
    "content": "역삼역에서 바로 찾아가기 좋은 가성비 한우 오마카세 맛집이었어요.\n프라이빗 룸으로만 …",
    "score": 5, "images": ["http://t1.daumcdn.net/local/kakaomapPhoto/review/caee…?original", …],
    "reviewer_id": "770328703", "date": "2025-08-29 15:30:58",
    "tags": ["맛", "친절", "분위기", "주차"], "like_count": 0}]
```

- `content` 에 **줄바꿈(`\n`)이 들어 있다.** 그대로 뿌리면 한 줄로 뭉친다.
- `score` 는 1~5 정수, 별점 없는 리뷰는 `null`. `images` 없으면 `[]`.

## 5. 선호(스와이프)

### `POST /preferences` — 카드를 넘겼다

```json
POST /preferences   {"user_id": "u_7373bd0fa56e", "card_id": 65, "prefer": "like"}
→ {"ok": true, "count": 1772, "learned": { … }}
```

- `prefer` 는 `"like"`(오른쪽) · `"dislike"`(왼쪽). 다른 값은 **400**. 없는 `card_id` 는 404.
- **다음 `GET /cards` 에 즉시 반영**된다. 카드를 넘길 때마다 보내라(모아서 보내면 그 사이 추천이 못 배운다).
- 같은 카드를 다시 보내면 마지막 값이 남는다.
- `count` 는 서버 전체 기록 수(그 사용자 것이 아니다). `learned` 는 디버깅용 — 의존하지 말 것.
  무거운 `prototypes`·`hist` 는 담지 않는다(관리자 화면 `/admin` 에서만 받는다). 담았을 때
  이 엔드포인트 비용의 76~88% 였다.
- ⚠️ `include_decision_metrics=true` 를 켜면 응답이 **60배 가까이 커진다**(30스와이프에서 약 190KB).
  위 감량과 별개의 페이로드다. 기본은 꺼져 있고, 켜는 쪽이 그 크기를 감당해야 한다.

### `GET /preferences/{user_id}?prefer=like` — 선호한 카드 목록

`prefer` = `like`(기본) · `dislike` · `all`. 표현한 순서대로, 같은 카드를 두 번 표현하면 두 번 온다.
기록이 없으면 404 가 아니라 `[]`.

```json
→ [{"card_id": 65, "store": {… "reviews": []}, "image": "…", "images": […]}]
```
(`recommendation_reason`·`policy`·`distance_m` 은 없다 — 추천이 아니라 목록이다.)

## 5.5 찜 — '나중에 볼' 목록

**좋아요와 다른 기능이다.** 좋아요는 취향 모델의 입력이고 답한 카드는 다시 안 나온다.
찜은 사용자가 담아 두는 목록일 뿐이라 **추천을 하나도 바꾸지 않는다** — 담은 가게가 추천에
다시 나올 수 있고, 모델·노출 로그도 그대로다. 화면의 하트/북마크 버튼에 그대로 붙이면 된다.

### `PUT /users/{user_id}/bookmarks/{card_id}` — 담기 (멱등)

```json
→ {"card_id": 2018, "bookmarked": true, "at": "2026-09-10T16:52:07+09:00", "count": 1}
```

- 여러 번 눌러도 결과가 같다. 이미 담긴 카드면 **처음 담은 시각**이 그대로 온다
- `count` 는 그 사용자의 전체 찜 수 — 화면의 배지에 그대로 쓰면 된다
- 없는 `card_id` 는 **404**, 잘못된 `user_id` 는 422. 등록하지 않은 `user_id` 도 된다
- 한 사람당 **500개**까지. 넘으면 가장 오래 담아 둔 것부터 빠진다

### `DELETE /users/{user_id}/bookmarks/{card_id}` — 빼기

```json
→ {"card_id": 2018, "bookmarked": false, "at": null, "count": 1}
```
담겨 있지 않아도 **200** 이다(이미 원하는 상태다). 낙관적 UI 를 그대로 써도 된다.

### `GET /users/{user_id}/bookmarks?limit=50&offset=0` — 담아 둔 목록

**최근에 담은 순**이다. 카드 모양은 `GET /cards` 의 카드와 같고 `bookmarked_at`·`distance_m`
이 더 붙는다(`reviews` 로 리뷰 수를 조절할 수 있다, 기본 1건).

```json
→ [{"card_id": 65,   "store": {"name": "고우가 역삼역점", "category_group": "한식", …},
    "image": "…", "images": […], "bookmarked": true,
    "bookmarked_at": "2026-09-10T16:52:07+09:00", "distance_m": 64},
   {"card_id": 2018, "store": {"name": "퍼그피자하우스 강남점", "category_group": "양식", …},
    "bookmarked_at": "2026-09-10T16:52:07+09:00", "distance_m": 852}]
```

- 하나도 없으면 404 가 아니라 `[]`
- `distance_m` 은 **저장된 위치**에서의 거리(없으면 `null`)
- 뺐다 다시 담으면 맨 위로 온다
- 페이징: `limit`(기본 50, 최대 100) · `offset`

카드 응답(`GET /cards`, `GET /cards/{id}`, `GET /preferences/{id}`)에는 `bookmarked`(bool) 가
붙어 있다 — 목록을 따로 받지 않고도 버튼의 상태를 그릴 수 있다. `user_id` 없이 부르면 `false`
이고, `GET /users/{id}` 의 `bookmarks` 가 전체 개수다.

## 5.7 길찾기와 설문 — 추천이 맞았는지 되묻기

스와이프 like 는 **카드를 보고 넘긴 것**일 뿐이다. 실제로 가서 어땠는지는 물어봐야 안다.
그래서 **길찾기를 누른 순간을 방문 의사로 기록**하고 **3시간 뒤에 되묻는다**.

GPS 로 방문을 판정하지 않는다 — 백그라운드 위치 추적이 필요하고, 역삼동처럼 건물이 밀집한
곳에서는 반경 100m 안에 수십 곳이 들어와 어느 가게인지 특정할 수 없다. 길찾기는 사용자가
그 가게를 **직접 지목한 순간**이라 정확하고 배터리도 쓰지 않는다.

**앱이 할 일은 셋이다.**

```
① 지도 앱으로 넘어가기 직전   POST /users/{id}/directions
② 앱이 열릴 때 한 번          GET  /users/{id}/surveys/pending   → 있으면 배너
③ 배너에서 사용자가 고르면    POST /users/{id}/surveys

마이페이지의 '내 기록' 은 넷째다.

④ 마이페이지                  GET  /users/{id}/surveys           → 답한 것 전부
```

### `POST /users/{user_id}/directions` — 길찾기를 눌렀다

**지도 앱으로 넘어가기 직전에** 부른다. 응답을 기다릴 필요 없다 — 실패해도 사용자 흐름을
막지 말고 그냥 넘어가면 된다.

```json
{"card_id": 2018, "map_app": "kakao", "mode": "transit"}
```

- `map_app` : `naver` · `kakao` · `google` — 다른 값은 **422**
- `mode` : `walk` · `transit` · `car` — 다른 값은 **422**
- 없는 `card_id` 는 **404**

```json
{"card_id":2018,"at":"2026-09-11T13:55:47+09:00",
 "survey_at":"2026-09-11T16:55:47+09:00","count":1}
```

- `survey_at` : 이 시각 이후에 `pending` 에 뜬다(= `at` + 3시간).
  **로컬 알림 예약에 쓸 수 있다** (서버 푸시는 아직 없다)
- `count` : 그 사용자가 길을 찾아 본 가게 수
- **멱등이 아니다.** 같은 카드를 다시 누르면 시각이 갱신되고 설문도 **최신 길찾기** 기준으로
  다시 묻는다 — 어제 갔고 오늘 또 갔으면 물어야 하는 것은 오늘 방문이다

### `GET /users/{user_id}/surveys/pending?after_hours=0` — 물어볼 목록

**앱이 열릴 때 한 번** 부른다. 서버에 타이머가 없다 — 부른 그 순간 계산해서 답한다.

**시점 판단은 클라이언트가 한다.** 서버는 기본적으로 시간으로 거르지 않는다. 각 항목의
`hours_ago` 를 보고 배너를 띄울지 앱이 정하라 — 권장은 3시간 이후다. 서버에서 걸러
받고 싶으면 `?after_hours=3` 을 준다(0~168).

```json
[{"card_id":2018,"store_id":"382622582","name":"퍼그피자하우스 강남점",
  "category":"피자","image":null,"at":"2026-09-11T09:55:47+09:00","hours_ago":4,
  "photo_ids":[],
]
```

- 하나도 없으면 404 가 아니라 **빈 배열 `[]`**
- **방금 누른 길찾기도 나온다**(`hours_ago: 0`) — 기본값이 `after_hours=0` 이다
- **일주일** 지난 길찾기는 나오지 않는다(기억이 남아 있지 않다)
- 최대 **10개**. 더 있으면 최근 것부터 준다
- `photo_ids` : 이 카드에 **이미 올려 둔** 사진 id. 배너를 다시 열었을 때 올린 것을
  보여주고 몇 장 더 올릴 수 있는지 알려주는 데 쓴다. 주소는 `/media/{앞 2자}/{id}.jpg`
- `hours_ago` : 배너 문구에 쓴다 — "4시간 전에 퍼그피자하우스 강남점 가셨나요?"
- `image` 는 `null` 일 수 있다(사진이 없는 가게)
- `store_id` : 데이터가 갱신되면 `card_id` 는 바뀌지만 이 값은 그대로다. 로컬에 오래
  보관할 것이 있으면 이걸 키로 쓰라

### `GET /users/{user_id}/surveys?limit=50&offset=0` — 내가 답한 설문 목록 (마이페이지)

`pending`(아직 답할 것)의 **반대쪽**이다. 이미 답한 것을 **최근에 답한 순**으로 준다.
카드 모양은 `GET /cards` 와 같고 `survey` 가 더 붙는다.

```json
→ [{"card_id": 2018, "store": {"name": "퍼그피자하우스 강남점", "category_group": "양식", …},
    "image": "…", "images": […], "bookmarked": false, "open_now": {…},
    "survey": {"visited": true, "satisfaction": "good",
               "review": {"taste": "고등어초회가 신선했어요",
                          "price": "2인 4만원, 적당했어요",
                          "mood": "조용하고 좌석 간격이 넓어요"},
               "not_visited_reason": null,
               "images": ["/media/9f/9f2c….jpg"],
               "at": "2026-09-16T18:20:11+09:00"}},
   {"card_id": 65, "store": {…},
    "survey": {"visited": false, "satisfaction": null, "review": null,
               "not_visited_reason": "no_time", "images": [],
               "at": "2026-09-15T12:03:40+09:00"}}]
```

- ⚠️ **가게 화면의 `user_reviews` 와 다른 것이다.** 저쪽은 **남에게 보이는 글**이라
  방문·세 줄·빈칸을 모두 거르지만, 이쪽은 **내 기록**이라 답한 대로 다 나온다
- **안 갔다고 답한 것도 나온다.** '내가 답한 설문' 의 목록이지 '내가 쓴 후기' 의
  목록이 아니다. 후기만 보려면 `?visited=true` 로 부른다
- ⚠️ **답은 `survey` 안에 있다. 카드와 평평하게 섞이지 않는다.** 이름이 겹치기
  때문이다 — 바깥 `images` 는 **가게 사진**이고 `survey.images` 는 **내가 올린 사진**
  이다. 펴서 합치면 한쪽이 다른 쪽을 덮어써서 화면이 조용히 틀린다
- **방문 근거(`arrived`·`closest_m`·`dwell_min`)는 나오지 않는다.** 앱이 위치로 계산해
  보낸 값이라 이탈 분석에만 쓰고 사용자에게 되돌려 주지 않는다
- 카드당 한 건이고 **마지막에 답한 것**이 남는다(`POST` 의 중복 규칙과 같다)
- 하나도 없으면 404 가 아니라 `[]`
- 페이징: `limit`(기본 50, 최대 100) · `offset`. `visited` 로 거른 **뒤에** 자른다
- `reviews` 로 카드에 담을 **카카오** 리뷰 수를 정한다. **기본이 0 이다**(찜 목록은 1) —
  내 기록에 남의 수집 리뷰를 같이 실을 이유가 없다

`GET /user/{user_id}/surveys` 도 같다 — 찜·길찾기와 마찬가지로 설문은 **사람**에 붙으므로
세션이 여럿이어도 한 목록으로 모인다.

### 방문 근거 — **앱이 계산하고 서버는 받아 적는다**

길찾기는 방문 **의사**다. 눌러 놓고 안 가는 경우를 가리려면 도착을 확인해야 한다.
그 판정을 **서버에서 하지 않는다** — 앱이 이미 자기 위치를 들고 있고 가게 좌표도
응답으로 받으므로(`store.lat`·`store.lon`), 기기에서 계산해 결과만 설문에 실어 보낸다.

```
① 지도 열 때        POST /users/{id}/directions        어느 가게인지 알려준다
② 앱이 켜져 있으면   (앱 안에서 위치를 모은다)            서버로 안 보낸다
③ 물어볼 목록        GET  /users/{id}/surveys/pending    답 안 한 길찾기 전부
④ 앱이 판정          위치 기록 × store.lat/lon           100m 안이면 도착
⑤ 설문              POST /users/{id}/surveys            근거를 숫자로 함께
```

**왜 앱에서 하나.** 위치가 기기를 떠나지 않는다 — 서버가 궤적을 들고 있을 이유가 없고,
보관·삭제 책임도 생기지 않는다. 앱이 판정에 필요한 것을 이미 다 갖고 있다.

**가게는 길찾기로 이미 특정돼 있다.** 위치만으로 '어느 가게냐' 를 맞히는 것은 역삼동에서
불가능하다(가장 가까운 이웃까지 중앙값 8.2m, 100m 안에 평균 49.5곳). 그러나 사용자가
길찾기로 가게를 알려 줬으므로 남은 질문은 "그 좌표에 갔나" 하나이고, 그건 목표점 한
곳과의 거리 비교다. 그래서 **지오펜스도 백그라운드 권한도 반드시 필요하지 않다** —
식당에서 앱을 한 번이라도 열면 그 순간의 좌표로 판정된다.

여기서 나오는 근거는 **"그 자리에 도착했다"** 이고 "그 가게에서 먹었다" 는 아니다.
A 를 찍고 옆 B 에서 먹으면 구분하지 못한다.

**설문에 실어 보내는 값** (셋 다 선택)

| 필드 | 뜻 |
|---|---|
| `arrived` | 앱이 판정한 도착 여부. **모르면 생략**(`null`) |
| `closest_m` | 그 가게에 가장 가까웠던 거리(m) |
| `dwell_min` | 그 반경 안에 머문 시간(분). 위치를 한 번만 잡았으면 `0` |

⚠️ **모르는 것을 `arrived: false` 로 보내지 말 것.** 위치를 못 본 것과 안 간 것은 다르다.
`false` 로 뭉개면 위치 권한을 거부한 사용자가 전부 "안 갔다" 로 기록된다. 모르면 필드를
아예 빼라 — 서버는 그 셋을 구분해서 저장한다(값 있음 / `false` / 없음).

⚠️ **`closest_m` 을 꼭 같이 보낼 것.** `arrived` 만 보내면 '도착 반경 얼마가 맞나' 가
앱에 굳어 버리고 나중에 데이터로 다시 볼 수 없다. 거리는 **스칼라라서 좌표가 새지 않는다**
— 위치는 기기에 남고 서버는 "얼마나 가까웠나" 만 안다.

**서버는 이 값으로 설문을 막지 않는다.** 근거가 없어도, `arrived=false` 여도 받는다.
콜드스타트에 문을 잠그면 유일한 피드백 경로가 막히고 규칙을 검증할 표본도 못 모은다.
거를지는 앱이 정한다 — 권장은 **`arrived != false` 만 배너에 띄우기**(모르는 건 물어보고,
앱이 보기에 멀었던 것만 빼기)다.

**앱이 판정에 쓸 값**

- `store.lat` · `store.lon` — 카드 응답(목록·상세 둘 다)에 있다. **주소를 지오코딩하지
  말 것** — `지하 1층`·`302호` 같은 접미사에서 지오코더가 자주 실패한다
- 반경은 **100m** 를 권한다. 역삼동은 빌딩 골짜기라 GPS 정확도가 10~30m 이고 실내에서
  더 나빠진다. 가게 좌표도 POI 중심점이라 건물 크기만큼 틀어진다. 좁히면 '갔는데 못
  잡는' 쪽이 늘고 그 방문은 표본에서 영구히 사라진다 — 넓혀서 '지나갔을 뿐인데 잡은'
  것은 설문에서 '안 갔다' 로 걸러진다
- 길찾기(`pending` 의 `at`)로부터 **6시간** 안의 위치만 볼 것. 그 이전 것도 보지 말 것 —
  어제 그 앞을 지난 것은 그 방문의 근거가 아니다
- OS 가 주는 정확도가 **200m** 보다 나쁜 값은 쓰지 말 것(셀 타워만 잡힌 값이다)


**배너 흐름 (합의된 UX)**

```
"가게를 방문했나요?"   +  이 목록을 리스트로 보여준다
        ↓ 사용자가 하나를 고른다
1단계  방문하셨나요?            예 / 아니오
        ├ 아니오 → 왜?  멀다 / 시간없음 / 마음바뀜 / 다른곳
        └ 예    → 2단계
2단계  추천이 취향에 맞았나요?   😞 😐 😊          ← 핵심 지표
3단계  후기 세 줄 (필수)
         맛은?      [                    ]
         가격은?    [                    ]
         분위기는?  [                    ]        ← 그대로 가게 리뷰가 된다
```

**방문했다면 2·3단계가 모두 필수다.** 선택으로 두면 대부분 비워서 오고, 그러면 추천이
맞았는지도 모르고 가게 리뷰도 안 쌓인다 — 이 설문이 있는 이유가 그 둘이다. 대신 문항을
**셋으로 줄였다**(위생·대기 삭제) — 한 번 방문으로 판단하기 어렵고, 문항이 많으면
응답률이 떨어진다.

### `POST /users/{user_id}/surveys` — 설문 답하기

배너에서 고른 가게 **하나**에 답한다. 여러 곳이면 각각 따로 부른다.

```json
{"card_id":2018,"visited":true,"satisfaction":"good",
 "review":{"taste":"고등어초회가 신선했어요",
           "price":"2인 4만원, 적당했어요",
           "mood":"조용하고 좌석 간격이 넓어요"},
 "arrived":true,"closest_m":34,"dwell_min":41}
```

```json
{"card_id":741,"visited":false,"not_visited_reason":"changed_mind"}
```

| 필드 | 값 | 언제 |
|---|---|---|
| `card_id` | 정수 | 항상 |
| `visited` | `true` / `false` | 항상 |
| `not_visited_reason` | `far` · `no_time` · `changed_mind` · `went_elsewhere` | `visited=false` |
| `satisfaction` | `bad` · `soso` · `good` | **`visited=true` 면 필수** — 핵심 지표 |
| `review` | `{taste, price, mood}` 각 1~200자 | **`visited=true` 면 필수** |
| `arrived` | `true` / `false` | 선택 — 앱이 판정한 도착 여부. **모르면 생략** |
| `closest_m` | 0 이상 정수 | 선택 — 가장 가까웠던 거리(m). `arrived` 와 함께 보낼 것 |
| `dwell_min` | 0 이상 정수 | 선택 — 그 반경 안에 머문 분 |

**`visited=true` 면 둘 다 필수다**(없으면 422). 선택으로 두면 대부분 비워서 오고, 그러면
추천이 맞았는지도 모르고 가게 리뷰도 안 쌓인다 — 이 설문이 있는 이유가 그 둘이다.

> ⚠️ **`soso` 는 만족으로 세지 않는다.** 집계의 `satisfied_rate` 는 `good` 만 분자에 넣고
> 분모는 `good + soso + bad` 다. 화면에 😐 로 보이니 사용자는 "중간"으로 인식하지만,
> 지표에서는 만족이 아니다 — 넣으면 지표가 무뎌져 정책 비교를 못 한다.
> 나중에 "만족도 60%" 를 해석할 때 이 정의를 기억할 것.

**`review` 는 세 줄이다.** 한 칸짜리 자유 후기가 아니라 축을 나눈 이유: 빈칸을 막는
'필수' 가 의미를 가지려면 무엇을 쓸지가 정해져 있어야 한다. "좋았어요" 한 줄은 다음
사람에게 아무것도 알려 주지 않지만, 맛·가격·분위기가 각각 있으면 읽을 만한 리뷰가 된다.

| 필드 | 뜻 |
|---|---|
| `review.taste` | 맛에 대해 한 줄 |
| `review.price` | 가격에 대해 한 줄 |
| `review.mood` | 분위기에 대해 한 줄 |

- 앞뒤 공백은 서버가 자른다. **자르고 나서 비면 422** — 공백만 받아 주면 '필수' 가
  이름뿐이 되고 빈 줄이 가게 화면에 그대로 나간다
- 한 줄이라도 빠지거나 200자를 넘으면 **422**
- 위생·대기는 문항에서 뺐다. 한 번 방문으로 판단하기 어렵고, 문항이 늘면 응답률이 떨어진다
- **이 세 줄은 가게 리뷰가 된다** — 세 줄이 다 차 있으면 `GET /cards/{card_id}` 의
  `user_reviews` 로 다른 사용자에게 보인다(아래 절). **"맛있어요" 도 실린다.** 구체적인
  글일수록 앞에 설 뿐이다(표현력 순, 같으면 최근 순). 실렸는지는 응답의 `published`,
  세 줄이 각각 얼마나 구체적인지는 `review_levels`(축별 0~3)로 돌려준다 — 레벨이
  낮다고 거절되지 않으니 "조금 더 구체적으로 써 주세요" 안내에만 쓰면 된다
- `visited=false` 인데 후기를 보내면 **가게에 실리지 않는다.** 안 가 본 가게의 후기이기
  때문이다(저장은 된다 — 이탈 분석에 쓸 수 있다)

### `user_reviews` — 설문이 가게 리뷰가 된다

`GET /cards/{card_id}`(상세)에만 붙는다. 목록에는 없다 — 카드 수만큼 곱해지는 자리라
한 장당 후기 몇 건이 붙으면 응답이 금세 커진다(사진 주소까지 들어간다).

```json
"user_reviews": [
  {"name": "민수", "satisfaction": "good",
   "taste": "고등어초회가 신선했어요",
   "price": "2인 4만원, 적당했어요",
   "mood": "조용하고 좌석 간격이 넓어요",
   "images": ["/media/9f/9f2c….jpg"],
   "at": "2026-09-16T18:20:11+09:00"}
]
```

- ⚠️ **같은 후기가 `store.reviews` 에도 섞여 나간다.** 아래 "`store.reviews` 에도 실린다"
  절을 볼 것. **두 자리를 다 그리면 같은 글이 두 번 보인다** — 한쪽만 쓸 것
- ⚠️ **`store.score` 는 움직이지 않는다.** 그 값은 추천 점수의 평판 성분이 읽는 값이라,
  후기 한두 건이 평균에 들어가면 콜드스타트에 순위가 흔들리고 "왜 이 가게가 올라왔나" 를
  설명할 수 없게 된다. 표시와 점수는 다른 문제다 — 점수에 넣을지는 후기가 쌓인 뒤에 따로 정한다
- `store.review_count` 에는 이 후기도 **세어 들어간다.** 리스트에 6건이 보이는데 머리말이
  5건이라고 적혀 있으면 그건 그냥 틀린 숫자이기 때문이다
- `name` 은 작성자 이름. 이름 없이 발급받은 사용자는 `null` 이다.
  **`user_id` 는 주지 않는다** — 이 서버에서 그 값은 그 사람의 열쇠다(쥐고 있으면 그
  사람의 찜·취향·설문을 다 읽고 쓸 수 있다)
- `images` 는 설문에 올린 사진이다. 지우면 여기서도 사라진다(사진의 주인은 설문이다)
- **사람당 가게당 하나**다. 다시 길찾기하고 또 방문해 답하면 마지막 것만 남는다
- **표현력 순, 같으면 최근 순**이다 — `store.reviews` 와 같은 잣대
  (`server/recsys/expressiveness.py`). 키는 세 축 레벨 합 → 최고 레벨이다
- **세 줄이 다 차 있으면 실린다.** 표현력은 **자격이 아니라 순서**다 —
  "맛있어요 / 괜찮아요 / 좋아요" 도 실리고 구체적인 글 뒤에 선다. 2026-09-21 까지는
  줄마다 L2(속성 명시) 이상을 요구했는데, 그 문턱으로 운영 카드 2,795장 중 후기가 실린
  카드가 **1장**이었다(카카오 28,633건으로 재도 세 축 동시 L2 는 1.0~1.4%). 지금은
  걸러 내지 않는다 — 약한 글은 지우는 것이 아니라 뒤로 보낸다

```json
{"ok":true,"card_id":2018,"recorded":true,"remaining":0,
 "published":true,"review_levels":{"taste":2,"price":2,"mood":2}}
```

- `recorded` : 이번에 **새로 기록됐나**. 같은 길찾기에 두 번 답하면 `false` 이고
  **덮어쓰지 않는다**(표본이 부풀면 집계를 믿을 수 없다). 앱은 `false` 를 실패로 보지 말고
  조용히 배너를 닫으면 된다
- `remaining` : 아직 답하지 않은 후보 수. `0` 이면 배너를 닫는다
- `published` : 이 후기가 **가게 화면에 실렸나**(`user_reviews`). `visited=false` 거나
  세 줄 중 빈 줄이 있거나 `recorded=false`(중복 응답)면 `false` 다
- `review_levels` : 세 줄 각각의 표현력 레벨(`taste`·`price`·`mood`, 0~3).
  0 언급 없음 · 1 평가만("맛있어요") · 2 속성 명시("라떼가 부드러워요") · 3 구체 묘사.
  **순서에만 쓰이고 실리는 자격과는 무관하다** — "조금 더 구체적으로 써 주세요" 안내에
  쓰면 된다. `review` 를 보내지 않았으면 `null`
- **길찾기 기록은 필요 없다.** 앱이 방문 판단을 스스로 하고 설문만 보내는 것이 기본
  경로다. 없는 `card_id` 만 **404** `no such card`
- 같은 카드에 두 번 답하면 `recorded=false` 다. 단 `POST /directions` 를 부른 경우에는
  **새 길찾기가 문을 다시 연다** — 다시 가 봤으면 다시 물어야 한다
- 응답에 `source` 가 남는다 — `direction`(배너를 거쳤다) · `app`(앱이 직접 판단해
  보냈다). 두 경로의 만족도가 크게 다르면 한쪽 표본을 의심해야 한다
- 3시간이 안 지났어도 답은 받는다(경계에서 답한 정당한 응답을 잃지 않기 위해).
  서버가 경과 시간을 함께 기록해 집계에서 구분한다

`review` 는 앞뒤 공백을 서버가 자른다. **공백만 보내면 없는 것으로 저장된다** — 빈
문자열을 남기면 집계에서 '후기 있음' 으로 세어져 응답률이 부푼다.

### `store.reviews` 에도 실린다 — 카카오 리뷰와 같은 모양으로

2026-09-21 부터 같은 후기가 **`store.reviews` 안에도** 카카오 리뷰와 똑같은 모양
(`Review`)으로 들어간다. 앱이 `user_reviews` 를 파싱하지 않고 가게 상세의 리뷰 섹션이
`store.reviews` 만 그려서, 사용자가 쓴 글이 서버에는 쌓이는데 화면에는 한 건도 안 떴다.
**앱이 이미 그리는 자리에 서버가 넣는 쪽**으로 뒤집었다.

```json
{"source_platform": "matchuri",
 "id": 1000000000042,
 "store_id": "16421356",
 "content": "맛 · 고등어초회가 신선했어요\n가격 · 2인 4만원, 적당\n분위기 · 조용하고 좌석 간격이 넓어요",
 "score": 5,
 "images": ["/media/9f/9f2c….jpg"],
 "reviewer_id": null,
 "date": "2026-09-21 16:16:34",
 "tags": [],
 "like_count": 0}
```

- 붙는 곳은 **상세 `GET /cards/{card_id}`**(세션 경로
  `GET /user/{user_id}/session/{session_id}/cards/{card_id}` 포함)와
  **`GET /cards/{card_id}/reviews`**(리뷰 더보기) 둘이다.
  **목록 `GET /cards` 에는 섞이지 않는다** — 카드 수만큼 곱해지는 자리다.
  단 **`store.review_count` 에는 목록에서도 세어 들어간다** — 개수는 리스트 길이 하나라
  공짜고, 목록과 상세가 다른 숫자를 주면 같은 가게가 화면마다 달라진다
- **항상 배열 맨 앞이다.** 상세 미리보기가 5건뿐이라(`reviews` 기본값) 표현력 순에 섞으면
  리뷰 수백 건짜리 가게에서 사용자 글이 그대로 묻힌다. 순서가 아니라 자리로 보장한다.
  그래서 상세 응답의 `store.reviews` 길이가 `reviews` 파라미터보다 **클 수 있다**
- 우리 글끼리의 순서는 `user_reviews` 와 같다 — **표현력 순, 같으면 최근 순**
- **우리 글을 골라내는 법**: `source_platform == "matchuri"` **또는** `id >= 1000000000000`
  (`10**12`). 카카오는 양수, 네이버는 음수라 이 대역과 겹치지 않는다
- `content` 는 세 줄을 축 이름과 함께 접은 것이다 — `맛 · …\n가격 · …\n분위기 · …`.
  카카오 리뷰 본문에도 줄바꿈이 있으니 그리는 쪽은 그대로면 된다
- `score` 는 만족도를 별점으로 옮긴 것이다 — `good`=**5** · `soso`=**3** · `bad`=**1**.
  만족도를 안 준 설문은 `null`(별점 없는 카카오 리뷰와 같다)
- `reviewer_id` 는 **항상 `null`** 이다. 여기 넣을 수 있는 값은 `user_id` 뿐인데 그건
  그 사람의 열쇠라서 가게 화면에 실을 수 없다
- `date` 는 카카오와 같은 `"YYYY-MM-DD HH:MM:SS"` 다(`user_reviews[].at` 은 ISO 8601 이다)
- `tags` 는 `[]`, `like_count` 는 `0` — 카카오가 자기 화면에서 모으는 값이라 우리에겐 없다
- `images` 는 설문에 올린 사진이고 이미 최종 URL 이다. `original_images=true` 로 불러도
  **같은 URL** 이다(수집 원본이라는 다른 주소가 없다)

### `review_count` 는 무엇을 세나 — 2026-09-22 부터 뜻이 바뀌었다

`store.review_count` 는 **이 서비스에서 실제로 볼 수 있는 리뷰 수**다.

```
review_count == len(GET /cards/{card_id}/reviews)   # 항상 성립한다
              = 우리가 들고 있는 수집 리뷰 + 그 가게에 달린 우리 사용자 후기
```

전에는 **카카오가 자기 화면에 적어 둔 총 리뷰 수**를 그대로 내보냈다. 그 숫자는 우리가
가진 것과 다르다 — 리뷰 수집에는 가게당 상한이 있다(`BE/crawler/config.py`:
`REVIEWS_PER_STORE`). 2026-09-22 산출물 기준:

| | |
|---|---|
| 가게 | 2,795곳 |
| 적힌 총합 vs 실제 보유 | 65,763건 vs **33,300건**(50.6%) |
| 숫자가 목록보다 컸던 가게 | **717곳**(25.7%) — 최대 928 대 37 |
| 숫자와 목록이 맞던 가게 | 2,078곳(리뷰가 상한 아래인 곳) |

그래서 헤더에 "리뷰 928" 이라고 적혀 있는데 더보기를 눌러도 37건뿐인 화면이 나왔다.
**인기 가게일수록 이 숫자는 상한 근처에서 평평해진다** — 리뷰 900건짜리와 30건짜리가
비슷한 숫자로 보인다. 인기도가 필요하면 `score`(평균 별점)를 쓰거나 서버에 따로 요청할 것.

`store.score` 는 **바꾸지 않았다.** 그 값은 추천 점수의 평판 성분이 읽는다. 그래서
`score` 는 여전히 카카오가 전체 리뷰로 낸 평균이고, 옆의 개수만 우리가 가진 수다 —
"리뷰 20 · 별점 4.5" 의 4.5 는 20건의 평균이 아니다.

### `POST /users/{user_id}/surveys/{card_id}/photos` — 사진 붙이기

`multipart/form-data`, 필드 이름은 **`file`**, 한 번에 **한 장**이다.

```
POST /users/u_3f2a.../surveys/2018/photos
Content-Type: multipart/form-data; boundary=...
  file: <사진 바이트>
```

```json
{"photo_id":"9f2c1ab74e0d4c1fb3a8d5e6072c8a11",
 "url":"/media/9f/9f2c1ab74e0d4c1fb3a8d5e6072c8a11.jpg",
 "width":1600,"height":1200,"bytes":284915}
```

**설문과 순서는 상관없다.** 사진은 `(사람, 카드)` 에 붙으므로 설문 전에 올려도 되고 답한
뒤에 더해도 된다. 올려 둔 사진은 `pending` 의 `photo_ids` 로 다시 받을 수 있다.

- 없는 `card_id` 는 **404**. 길찾기 기록은 필요 없다(설문과 같다)
- **사람당 30장**이 상한이다. 넘으면 **409** — 길찾기 관문이 사실상의 상한이었는데
  그게 없어졌고, 그대로 두면 카드 2,795장 × 3장까지 한 사람이 밀어 넣을 수 있다
- 한 카드에 **최대 3장**. 넘으면 **409** — 먼저 지워야 한다
- `image/jpeg` · `image/png` · `image/webp`, **최대 10MB**. 그 밖은 **415**
- 아이폰 **HEIC 는 받지 않는다.** 앱에서 JPEG 로 변환해서 보낼 것
- 응답의 `url` 을 **그대로 쓴다.** 경로 규칙은 바뀔 수 있다. 서버 기준 경로이므로
  앞에 API 호스트를 붙이면 된다
- 사진 볼륨이 붙지 않은 환경에서는 **503**. `GET /readyz` 의 `media_writable` 로 미리 안다

> ⚠️ **올린 파일과 받는 파일이 다르다.** 서버가 긴 변 1,600px JPEG 로 다시 굽고
> **EXIF 를 없앤다.** 휴대폰 사진에는 **촬영 좌표가 들어 있어서** 그대로 공개 URL 로
> 내보내면 사용자가 어디 있었는지가 새어 나간다. 회전 정보는 없애기 전에 적용하므로
> 세로로 찍은 사진이 눕지 않는다. 그래서 응답의 `width`/`height`/`bytes` 는 올린 값과
> 다르며, **그 값을 화면 배치에 쓸 것**이다.

사진 주소는 앱을 거치지 않고 nginx 가 바로 내보낸다. 내용이 바뀌지 않으므로(파일 이름이
uuid 다) 캐시를 1년으로 준다 — 앱에서 따로 캐시 무효화를 할 필요가 없다.

### `DELETE /users/{user_id}/surveys/{card_id}/photos/{photo_id}` — 사진 지우기

성공하면 본문 없이 **204**. 본인이 그 카드에 올린 사진만 지울 수 있고, 아니면 **404** 다.
이미 지운 사진도 **404** 다.

**추천을 바꾸지 않는다.** 좋아요(`POST /preferences`)와 달리 길찾기·설문·사진은 취향 모델과
'이미 본 카드' 목록을 건드리지 않는다 — 길찾기한 가게가 추천에 다시 나올 수 있다.

## 6. 취향 — 화면 한 장

취향은 **하나의 그림**으로 준다: 취향 지형도 위에서 내 취향의 중심이 어디에 있고 어디로 움직였나.
성분 가중치나 업종 막대는 관리자 화면(`/admin`)에만 있다.

관리자 전용 `GET /admin/api/map/layout`은 기존 고정 좌표·`ids`·`cats`·`cat`에
`cat2`·`cat3` 문자열 배열을 추가한다. 두 배열은 `ids`와 같은 순서이고 분류가 없으면 `null`이다.
`cat2 → cat3 → 가게` 확대에 사용하며, 같은 세부 분류명도 `(cat2, cat3)`로 구분한다.
읽기 전용이며 레이아웃·가게 원본 파일이 바뀔 때 캐시를 갱신한다. 추천 점수나 모델은 변경하지 않는다.

### `GET /taste/map` — 지형(고정)

```json
→ {"version": 1,
   "regions": [{"name": "한식", "x": 0.838, "y": 0.4531, "r": 0.1161, "count": 710},
               {"name": "카페", "x": 0.1077, "y": 0.6565, "r": 0.0607, "count": 460}, … 20개]}
```

- 모든 사용자가 같은 땅을 본다. 앱이 **한 번만 받아 캐시**하고 `version` 이 바뀌면 버린다.
- `x`,`y` ∈ [0,1]², 두 축의 배율이 같다(정사각형에 그리면 된다). `r` 은 "대충 이 근처" 를 그리는 반지름이지
  경계가 아니다(구성원의 절반은 밖에 있고, 큰 업종끼리 겹친다).
- **그리는 권장:** 가게 40곳 이상인 업종만 아주 옅은 면(알파 6~10%)으로, 반지름은 0.14 로 자르고, 이름은 원의
  위쪽 가장자리에. 후보 2,216곳의 점은 그리지 않는다 — 궤적이 그림이고 땅은 배경이다.
- 좌표는 UMAP 이라 **먼 두 지역 사이의 거리는 뜻이 없다.** 믿을 수 있는 것은 "무엇이 무엇 옆에 있나" 뿐.

### `GET /taste/map/children` — 확대할 때 필요한 항목만 조회

사용자 궤적 없이 공통 배경만 가볍게 조회할 때 쓴다. 세션 `/taste`의 `map.regions`와 같은 항목을
반환한다. `parent`에는 앞 응답에서 선택한 항목의 `key`를 그대로 URL 인코딩해 넣는다.

```text
GET /taste/map/children                          → level: "cat2"
GET /taste/map/children?parent=<선택한 cat2 key>   → level: "cat3"
GET /taste/map/children?parent=<선택한 cat3 key>   → level: "store"
```

응답은 **`{level, nodes}`**뿐이며, 각 항목은 `{key, name, x, y, r, count, card_id}`다.
분류의 좌표·반지름은 기존 지도와 같은 중앙값 요약이고 `card_id=null`이다. 가게는 이름·기존 좌표와
`r=0`, `count=1`, 실제 `card_id`를 반환하므로 `GET /cards/{card_id}`로 상세를 열 수 있다.
같은 세부 분류명도 상위 분류별 키가 다르다. 분류가 없는 가게는 `분류 없음` → `세부분류 없음`으로
접근할 수 있으며, 상위 분류만 있는 가게는 그 아래 `세부분류 없음`에 포함된다.

없는 키·가게 키를 `parent`로 보내면404, 지도나 카드 매핑이 준비되지 않으면503이다.
사용자와 무관한 읽기 전용 배경이며 취향 점수를 의미하지 않는다. 서버는 원본 변경 시 캐시를
갱신하고 `Cache-Control: no-cache`를 반환하므로, 화면을 다시 열 때 재조회한다.

### `GET /user/{user_id}/session/{session_id}/taste` — 내 궤적과 확대 지도

`S = /user/{user_id}/session/{session_id}`. 기존 `/users/{session_id}/taste`도 같은 확대 쿼리를
지원하지만, 새 클라이언트는 사용자 소유권을 확인하는 `S/taste`를 사용한다.

```text
GET S/taste             → map.level: 1 (전체 cat2, 기본)
GET S/taste?detail=1    → map.level: 1 (전체 cat2)
GET S/taste?detail=2    → map.level: 2 (전체 cat3)
GET S/taste?detail=3    → map.level: 3 (전체 가게)
```

**확대할 때 `map`만 달라진다.** `trail`·`now`·`drift`·`headline`·스와이프 수는 같은 세션의
전체 기록을 기준으로 유지한다. 좌표도 전역 [0,1]² 그대로이므로 클라이언트가 화면의 표시 범위만
확대해야 한다. 분류 밖 궤적을 삭제하거나 좌표를 다시 정규화하면 취향의 이동이 달라 보인다.

`map`은 **`{version: 3, level, regions}`**다. 기존 `regions[]`의 `name,x,y,r,count`에
`key,card_id`를 추가했다. `detail`은 정수 1·2·3이며 응답의 `map.level`도 같은 숫자다.
특정 분류의 자식만 반환하는 방식이 아니라, **선택한 상세 단계 전체**를 한 번에 반환한다.
`parent`는 사용자 취향 API에서 사용하지 않는다. `key`는 항목을 구분하는 안정적인 식별자다.
분류는 `card_id=null`, 가게는 `r=0,count=1`이며 `GET /cards/{card_id}`로 상세를 연다.
`detail`을 생략하거나 1로 보내면 전체 cat2로 돌아간다. 같은 cat3 이름이 서로 다른 cat2에
있어도 합치지 않으며 각기 다른 key로 구분한다.
version3는 숫자 level을 사용한다. 기존 문자열 level의 version2 캐시는 갱신한다.
공통 확대 API의 항목 순서를 사용하므로 배열 순번 대신 `key`로 항목·색상을 연결한다.
기존 지도의 결측 분류명 `미분류`는 확대 배경에서 `분류 없음`으로 표시된다. 궤적의 기존 `region`
문자열과 좌표는 유지한다.

예시(키는 자리표시자):

```json
→ {"user_id": "usr_example", "session_id": "s_example", "name": "도리", "swipes": 326, "likes": 178,
   "map": {"version": 3, "level": 1,
           "regions": [{"key": "<cat2 key>", "name": "일식", "x": 0.4, "y": 0.6,
                        "r": 0.1, "count": 157, "card_id": null}, …]},
   "trail": [{"n": 1,  "x": 0.8378, "y": 0.6024, "region": "한식", "store": "고우가 역삼역점", "card_id": 65},
             …
             {"n": 326, "x": 0.5667, "y": 0.5969, "region": "양식", "store": "비놀릭", "card_id": 131}],
   "now": {"x": 0.5667, "y": 0.5969, "region": "양식",
           "near": [{"name": "카페413프로젝트 역삼점", "card_id": 1385}, {"name": "마초쉐프 강남본점", "card_id": 1924},
                    {"name": "비놀릭", "card_id": 131}]},
   "drift": {"from_region": "한식", "to_region": "양식", "distance": 0.328, "window": 10},
   "headline": "좋아요한 가게를 바탕으로 취향을 알아가고 있어요"}
```

| 필드 | 뜻 | 화면 |
|---|---|---|
| `map` | 선택한 단계 전체의 고정 지형. `version=3`, `level=1/2/3`, `regions[]`에 식별 key와 카드 ID 포함 | 확대 가능한 배경 |
| `trail[]` | **like 마다 한 점**(최근 60개, 오래된 것부터). 위치는 like 한 가게 좌표의 지수이동평균(α=0.35)이라 한 장으로 튀지 않고 흐른다. `n` 은 몇 번째 스와이프였나, `store`/`card_id` 는 그 like 가게 | 오래된 쪽이 가늘고 옅은 곡선 하나 |
| `now` | 마지막 점 + `near`: 그 점에 가장 가까운 **내가 좋아요한 가게 3곳** | 강조된 현재 점 + 아래에 가게 이름 칩 3개 |
| `drift` | 10 like 전 점 → 지금 점의 **지도상 이동**. `distance`는 [0,1]² 좌표 거리이며 고차원 취향 변화량이 아님. like 11개 미만이면 `null` | "10번 전" 빈 고리 |
| `headline` | 현재 세션의 유효 좋아요를 최근 반응에 더 무게를 두어 요약한 관측 설명. 지도 위치와 독립적 | 맨 위 제목 |
| `region` | 지도상 위치의 주변 업종(이웃 15곳 다수결). 실제로 좋아한 음식·선호 업종을 뜻하지 않음 | 라벨 |

`headline`은 2D 좌표·이웃 업종·이동 거리를 취향으로 해석하지 않는다.
현재 좋아요 상태인 서로 다른 가게가 3곳 미만이면 기존 수집 안내를 보낸다. 그 이상이면
각 가게의 마지막 반응 시점에 추천 모델과 같은 최근 감쇠(10스와이프마다 절반)를 적용한다.
가중치 합의 과반인 cat3(같은 cat2 안에서 집계)가 있으면 그 이름, 없으면 과반 cat2를
"최근 좋아요에서는 {분류} 쪽이 두드러져요"로 설명한다. 이는 단순 가게 수의 과반이나
추천 확률이 아니다. 근거가 섞이거나 분류가 부족하면 "좋아요한 가게를 바탕으로 취향을
알아가고 있어요"로 안내한다. 분류가 없는 가게도 분모에 포함한다.

반복 좋아요는 한 가게로 세고, 싫어요로 바꾼 가게는 현재 설명에서 제외한다. 오래된 유효
좋아요를 임의의 창으로 자르지 않는다. 이전 세션 기억은 추천 모델에서 기존대로 쓰지만
이 문구는 **현재 세션의 관측**만 설명한다. 고차원 취향을 업종으로 대체하거나 취향이
확정됐다고 판단하지 않는다. 지도·궤적·region·drift·near와 응답 구조는 유지한다.

- **`near` 를 항상 같이 보여줄 것.** 취향이 두 갈래(한식+카페)면 평균 점이 둘 사이 빈 땅에 앉는다. 좌표는 거짓말할 수
  있지만 좋아요한 가게 이름은 거짓말하지 않는다.
- 읽기 전용이다 — 아무리 불러도 추천·학습에 영향이 없다.
- 다른 사용자 소유 세션·없는 세션은404, detail이 1·2·3 이외이거나 정수가 아니면422,
  지형이나 카드 매핑 미준비는503.
- 기존 `GET /taste/map`은 version1 응답을 유지한다. 사용자 지도 version3를 대신하는 캐시로 쓰지 않는다.
  확대 응답을 캐시한다면 detail 값을 구분한다. 분류가 없는 가게도 `분류 없음`/`세부분류 없음`으로 포함한다.
  공통 `/taste/map/children`의 parent 방식은 그대로 유지한다.
- 예시 화면: `GET /taste/example?user_id=…&session_id=…`. 1·2·3 단계 버튼으로 상세도를 선택한다.
  분류를 누르면 해당 좌표 주변으로 확대하며, 가게를 누르면 카드 상세를 본다.
  이전 세션 ID만 있는 `?user_id=…`도 지원한다. `?demo=1`은 기존 고정 그림을 보여주는 오프라인 예시이며
  실제 사용자·현재 지도와 연결되지 않는다.

## 8. 자주 묻는 것

- **필터를 걸었는데 카드가 적게/안 온다.** 정상이다. `GET /filters` 의 `count` 로 조합이 얼마나 좁은지 미리 보여주고,
  0장이면 "조건을 넓혀 보세요" 를 띄워라. 업종·태그는 **각각 OR** 이라 더 고르면 넓어지지만, 업종·태그·거리를
  **함께** 걸면 좁아진다.
- **거리가 `null` 이다.** 위치를 저장하지 않았다(`PUT /users/{id}/location`).
- **`400 저장된 필터의 within_m 을 쓸 위치가 없습니다`.** 반경은 저장했는데 위치가 없다. 위치를 저장하거나 반경을 `null` 로.
- **같은 카드를 또 받고 싶다.** 안 된다 — 한 번 준 카드는 그 사용자에게 다시 안 나온다. 좋아요 목록(`GET /preferences/{id}`)이나
  찜 목록(`GET /users/{id}/bookmarks`)에서 다시 열어라.
- **찜과 좋아요를 같은 버튼에 묶어도 되나.** 안 된다. 좋아요는 추천을 바꾸고(그리고 그 카드는 다시 안 나온다) 찜은 목록에만 담긴다.
  둘을 함께 누르고 싶으면 두 요청을 다 보내라.
- **카테고리 글자가 필터와 다르다.** `store.category` 는 카카오 세부 분류(153종), 필터와 같은 9개 라벨은 `store.category_group`.
- **`policy`·`learned` 는 뭔가.** 추천 실험·디버깅용이다. 화면에 쓰지 말고 타입에서 빼도 된다.

## 스와이프 중 선택 제안 (실험적, 클라이언트 선택 연동)

**가벼운 판단 수치 조회**: `GET /users/{user_id}/decision/metrics/summary?card_ids=12&card_ids=34`.
최상위 `decision_readiness_score`는 클라이언트 표시용 취향 파악 점수이며 실제 범위는0~80입니다(기존 앱이 화면0~100%로 환산). **적중 누적**입니다 — 답을 보기 전 계산한 개인화 순위와 실제 응답이 같은 방향이면 오르고 반대면 내려가며, 연속으로 맞히면 한 장의 증가폭이 커집니다. 빗나간 한 장은 **이제까지 쌓은 값의 절반까지만** 깎으며, 한 번이라도 순적중한 뒤에는 화면이 다시 0%가 되지 않습니다(0%는 "아직 아무것도 맞히지 못했다" 전용). **80은 `personalization.ready`가 true일 때만** 나오므로 화면100%와 서버 판정이 일치합니다. 그 전에는 최대79(화면98.8%)이고, `ready`가 다시 false가 되면 79 이하로 돌아갑니다. 학습으로 받아들인 스와이프에서만 움직이며 반복 조회·필터·위치·n·card_ids 변경으로는 변하지 않습니다. 재시작·재생에도 같은 값이 나오고, **새 결정 세션은 항상0에서 시작합니다** — 이전 세션에서 물려받는 것은 점수가 아니라 적중했을 때의 증가 속도(최대2배)이므로, 같은 답을 해도 재방문 사용자가 더 빨리 올라갑니다. `personalization.readiness_score`(완화 전 기준까지의 진행률)와는 다른 값이므로 서로 비교하지 마십시오. 정확도·만족 확률이나 학습 완료율이 아니며, 스와이프 횟수만으로 상승하지 않습니다. 분석 불가만 null입니다. 클라이언트는 점수로 추천 버튼을 막지 않습니다. `n`은 자동 제안 분석 장수로 기본4, 1~20입니다.
개인화 준비 여부·예측 구분력/안정성 점수·적합 가게 수와 지정 카드 중 가장 비슷한 쌍의 점수·ID·다양성 통과 여부를 받습니다. 기존 수치와 함께 `personalization.readiness_score`(0~100 취향 찾기 준비도)도 제공합니다. **준비도에는 순위 안정성이 들어가지 않습니다** — 그 값은 학습이 진행되는 동안 내려가므로 진행 척도로 쓰지 않습니다. `ready` 조건에서는 그대로 요구하고 값은 `stability_score`와 상세 metrics의 gates로 계속 제공하므로, **준비도가100이어도 `ready`는 false일 수 있습니다.** 의미와 null 규칙은 OpenAPI에 있습니다. [연동 방법](../BE/server/DECISION-CLIENT.md).
제안 장수는 `GET /users/{user_id}/decision?n=6`처럼 지정하며 기본4, 범위1~20입니다.

**판단 수치 export**: `GET /users/{user_id}/decision/metrics`로 개인화 근거·후보별 점수 분해·
성분별 가게 쌍 유사도·결측·통과/보류 근거를 내보냅니다. 준비 전에도 측정합니다.
`POST /preferences?include_decision_metrics=true`는 해당 피드백 직후 `decision_metrics`도 반환합니다.
JSON 다운로드·전체 후보 페이징·CSV 도구와 해석은 [판단 수치 내보내기](../BE/server/DECISION-METRICS.md)를 참고하세요.

`POST /preferences?include_decision=true`를 사용하면 기존 선호 저장과 학습을 마친 뒤
`decision` 필드에 선택 제안을 함께 받습니다. 기존 호출은 `decision: null`이며 기존
필드는 유지됩니다. 화면 재진입 또는 필터/위치 변경 후에는
`GET /users/{user_id}/decision?mode=auto`로 자동 권유를 다시 평가합니다.
사용자가 직접 선택하기를 누르면 기본 `GET …/decision`(mode=manual)을 호출합니다.
manual은 스와이프 전이나 낮은 점수에서도 현재 정보로 n곳을 반환합니다. 응답 타입은 `DecisionOut`입니다.

- `ready=true`: `cards`에 정확히 n장(기본4)이 있으며 `message`를 선택 권유 문구로 사용합니다.
  카드는 기존 카드 공통 필드에 `liked`, `distance_m`, `recommendation_reason`이 붙습니다.
  `recommendation_reason`은 자기 참조를 제외한 메뉴·소개·리뷰·음식사진의 관측된 취향 근거를
  한 줄로 제공합니다. 근거가 부족하면 auto는 종합 적합 설명을, manual은 현재 정보나 기본 추천으로 골랐다는 설명을 반환합니다.

- **`POST /users/{user_id}/decision/feedback`**: 제안 결과를 기록합니다.
  `{"proposal_id":"받은 ID","action":"select","card_id":12}` 또는
  `{"proposal_id":"받은 ID","action":"continue"}` → `{"ok":true}`.
  계속 둘러보면 기존 스와이프를 이어갈 수 있고 다음 decision은 같은 조합을 제외해 다시 고릅니다.
  일부 가게는 다시 포함될 수 있으며 개별 like/dislike는 바꾸지 않습니다. 선택 결과도 별도 보관합니다.
  동일 결과 재전송200, 다른 결과409, 잘못된 선택422, 없는/타 사용자/최근100개 밖 제안404,
  저장 실패503. 재시작 후에도 유지됩니다. 같은 필터에서 적용되고 GPS 갱신으로 해제되지 않으며,
  대안이 없으면 `ready=false`이며 개인화 점수는 이 이유로 바뀌지 않습니다. 자세한 연결은 `DECISION-CLIENT.md` 참고.
- `ready=false`: `cards=[]`, `message=null`, `proposal_id=null`. 스와이프를 이어갑니다.
- `status`: `learning`(auto의 개인화 근거 부족), `insufficient_candidates`(조건을 통과한 조합 부족),
  `unavailable`(취향 산출물 없음), `location_required`(반경 설정에 필요한 위치 없음), `ready`.
- 제안 응답은 `ready`, `status`, `proposal_id`, `message`, `cards`만 반환합니다.
  개인화 점수·적합 가게 수·유사도는 별도 summary, 상세 진단은 metrics로 조회합니다.

최종 후보는 **현재 카드 자격을 갖춘 전체 가게**입니다. 과거 좋아요·싫어요·서빙 여부로
후보를 제한하거나 좋아요한 4곳을 따로 제안하지 않습니다. 선호 반응은 모델 학습에
사용하고, 최종 4곳은 현재 취향 적합도와 다양성으로 판단합니다.
auto는 같은 브랜드와 극단적인 원시 유사도, 관측 성분 부족을 제외합니다. 업종 이름이 같다는
이유만으로 후보를 제외하지 않으며 같은 중식·일식 안에서도 실제 메뉴와 콘텐츠 차이를 비교합니다.
manual도 적합하고 다양한 조합을
우선하지만 조건을 통과한 조합이 없으면 현재 후보 안에서 차선의 n곳을 제공합니다.
manual의 ready는 개인화 검증 성공을 뜻하지 않습니다. 모든 경우 업종·태그·반경과 카드 자격을 지키며,
조회 자체로 학습·스와이프 노출·정책별 실험 로그를 변경하지 않습니다. 선택 후보 카드는
별도 비교 UI에서 사용하고 스와이프 큐에 삽입하지 않습니다. 제안 이후 기존 스와이프
서빙과 겹칠 수 있으므로 클라이언트는 선택 UI를 닫은 후 다음 큐를 표시합니다.

조합을 찾은 뒤 같은 적합도 탐색 범위(기존 상위60곳) 안에서 가장 큰 쌍 중복부터 줄이는
제한된 교체 탐색을 수행합니다. 가장 높은 순위의 가능한 선택 하나와 태그 등급 구성은 유지하며,
관측 성분이 더 부족한 조합을 ‘더 다르다’고 우대하지 않습니다. 성분별 전체 관측 가게 쌍의
백분위로 눈금을 맞추고 최댓값을 사용하므로 사진의 높은 유사도가 다른 성분의 낮은 점수에
상쇄되지 않습니다. 이 비교는 관련 후보 안의 상대적인 구성 개선이며, 전역 최적 조합이나
사용자 만족이 검증됐다는 뜻은 아닙니다. 기존 최소 다양성 통과 여부와도 구분합니다.

상세 metrics의 `pairs[].relative_similarities`는 성분별 백분위 [0,1],
`pairs[].redundancy_percentile`은 그중 최댓값(2성분 미만은 null)입니다.
`slate.max_pair_redundancy_percentile`은 해당 조합에서 가장 큰 값입니다. 원시 유사도와 평균,
클라이언트 summary의 기존 점수·응답 필드는 유지합니다. `same_fine_category`는 진단 정보이며
차단 조건이 아닙니다. 백분위는 중복 확률이 아니며 데이터 풀이나 임베딩이 바뀌면 달라집니다.

클라이언트 순서:

1. 스와이프 결과를 `include_decision=true`로 순서대로 저장합니다.
2. 이 자동 권유 응답의 `ready`이면 n곳 비교 화면을 제안합니다. 동일한 `proposal_id`를 다시 띄우지 않습니다.
3. `계속 둘러보기`를 선택하면 feedback에 `continue`를 보내고 기존 스와이프를 이어갑니다.
   이후 새로운 스와이프 결과의 decision 또는 별도 decision 조회로 다른 조합을 받습니다.
   유효한 대안이 이미 있으면 `ready`는 true를 유지할 수 있습니다. 자동 권유 재조회는 `mode=auto`를 사용합니다.
4. 사용자가 가게를 고르면 feedback에 `select`와 card_id를 보내고 기존 카드 상세·길찾기를 사용합니다.

비교 화면과 사용자 행동의 feedback POST 연결은 클라이언트에서 해야 합니다. 이번 변경은
백엔드만 포함합니다. 서버 세션은 누적 취향 기준이며 방문마다 초기화하지 않습니다.
auto는 기존 정책대로 고유 평가30~60곳에서 예측 검증을 완화하지만 적합도·다양성 조건은 유지합니다.
manual은 처음부터 요청 가능하며 점수로 차단하지 않습니다. 기존 추천·스와이프는 계속됩니다.
제안 발급 기록은 화면을 실제로 봤다는 노출 증거가 아닙니다. 결과 POST는 실제 행동 때만 보냅니다.

현재 앱은 초기 10장과 추가 50장을 선조회합니다. 피드백으로 모델이 갱신되어도 이미
받은 큐의 순서는 바뀌지 않습니다. 검증은 이 경로를 기본으로 재현했으며, 더 작은
배치로 바꾸는 실험은 비교용입니다. 이번 변경에서 기존 추천 흐름은 바꾸지 않았습니다.

판단 기준과 실제 검증 결과는 [선택 제안 검증](../BE/server/DECISION.md)을 참고하세요.


## 데이터 출처 플랫폼

가게(`store`), 리뷰(`store.reviews[]` 및 `/cards/{card_id}/reviews`), 메뉴(`menus[]`)는
`source_platform`을 반환합니다. `kakao`는 카카오맵, `naver`는 네이버지도에서 수집한 레코드이며,
출처를 알 수 없으면 `null`입니다. 사진 CDN 도메인이나 콘텐츠 작성자의 소속을 뜻하지 않습니다.
기존 카드 목록·상세·선호·찜·선택 제안에서도 같은 데이터 모델을 사용합니다.
사진 배열은 기존 URL 배열 형태를 유지하고, 사진 출처는 런타임 사진 레코드에 기록합니다.
