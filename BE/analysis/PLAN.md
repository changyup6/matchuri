# 추천 재설계 — 다중 벡터 취향 모델 (작업 계획서)

작성: 2026-09-09. 이 문서는 구현자가 따르는 **계약**이다. 바꾸려면 근거를 적고 바꾼다.

## 0. 왜 다시 하나

현재 서버(`server/recsys/swipe.py`)의 개인화는 `cat2` 업종 10개 + 메뉴 중앙가 4분위 위의
로지스틱 재가중이다. 업종 카테고리는 취향을 담지 못한다(곱창전골↔모츠나베, 냉면↔메밀소바는
업종이 다르지만 취향은 같다). 2026-09-08 시도(메뉴 기반 8개 수작업 축)도 결국 또 다른 정형
분류였고 품질순 대비 +0.5%p, CI 는 0 을 포함했다.

이번 설계 원칙:

1. 음식점을 **하나의 벡터로 평균내지 않는다.** 메뉴 벡터 3~8개, 리뷰 벡터 여러 개, 음식 사진 /
   공간 사진 벡터를 **집합**으로 유지한다 (late interaction, MaxSim).
2. 사용자 취향도 하나의 벡터가 아니다. 긍정 프로토타입 3~5개, 부정 프로토타입 2개.
   후보 점수는 `max_k sim(u_k, store)` — 여러 취향 중 가장 가까운 것과 비교한다.
3. 온라인 학습은 1,024차원 벡터 위에서 하지 않는다. 사용자별로 학습하는 것은
   **구성요소 점수의 가중치 몇 개**뿐이다 (메뉴유사·리뷰유사·사진유사·기피거리·품질·탐색).
   스와이프 수십 건으로 배울 수 있는 크기여야 한다.
4. 스와이프는 쌍대(pairwise) 비교로 학습한다. dislike 직후 like 는 "B > A" 제약이다.
5. 카테고리는 화면 표시·콜드스타트 보조로만 남긴다. 점수에서 뺀다.
6. **한 step 씩, 백테스트 근거 없이는 서버에 넣지 않는다.** 현재 모델은 품질 베이스라인으로 남긴다.

## 1. 백테스트 계약 (Step 0) — 모든 실험의 공통 잣대

### 데이터
- `data/kakao/reviews.jsonl` 33,300건. 전부 `author_id`, `rating`(1~5), `date`, `content` 있음.
  저자 21,803명. 리뷰 10개 이상 232명, 20개 이상 62명 (전체 가게 기준; 후보 풀 기준은 harness 가 재계산).
- `data/kakao/stores.jsonl` 2,795곳, `menus.jsonl` 49,057행(2,249곳, 고유 메뉴명 23,171),
  `photos.jsonl` 32,130장 (tag: FOOD 20,276 / INDOOR 6,443 / MYSTORE 3,036 / OUTDOOR 1,356 / MENU 1,012).
- 이 EC2에는 2026-09-08 PC 에서 추가 수집한 사용자 100명·리뷰 2,517건이 **없다.** 있는 것으로 한다.

### 후보 풀
- 서버의 카드 자격과 동일: 카카오 리뷰 1+ 이고 사진 1+ 인 가게 (`swipe._build_pool` 과 같은 규칙).
  harness 가 실제 수를 계산해 기록한다 (README 는 2,216, swipe.py 주석은 2,045).

### 평가 사용자와 시간 분할
- 사용자별로 후보 풀 안의 가게에 남긴 리뷰를 `date` 오름차순 정렬. 총 T 건.
- **평가 사용자 = T ≥ 10.**
- 미래(정답) 구간 F = `max(3, ceil(0.3·T))` 개 (가장 최근). 미래는 N 과 무관하게 고정.
- 이력 N ∈ {3, 5, 10, 20}: 미래 **직전** 의 최근 N 건 (중첩). N 보다 적으면 있는 만큼 쓰고, N 을 다 채운
  사용자 수를 N 별로 보고한다. (가장 오래된 N 개를 쓰는 것은 제품 동작과 다르다 — 이전 실수.)
- 같은 가게를 여러 번 리뷰한 경우: 이력에서는 그대로, 미래에서는 가게 단위로 유일화. 미래 가게가
  이력에 이미 있으면 미래에서 제외(제품은 한 번 준 카드를 다시 주지 않는다). 제외 건수 보고.

### 이력의 해석 (제품과 동일한 입력만 쓴다)
- 추천 시점에 아는 것은 **(가게, like/dislike)** 뿐이다. 사용자의 리뷰 원문은 입력으로 쓰지 않는다.
- rating ≥ 4 → like, rating ≤ 2 → dislike, 3 → 중립(입력하지 않음). 이 매핑은 상수로 두고 바꾸면 기록.
- **[2026-09-09 수정 — 5절 'Step 1 → Step 1.5' 결정 1번]** 과제 P 의 기본 해석은 이제 `visit`
  (방문한 가게 전부가 가중 1 의 관심 신호, dislike 없음)이다. 위의 like/dislike 매핑은
  `--history like_dislike` 로 남아 있고 Step 0·1 결과는 그것으로 **그대로 재현된다**
  (검증함: step0-baselines 의 모든 칸이 소수 12자리까지 일치).

### 과제와 지표 (둘 다 보고, 주 지표는 P)
- **P. 다음 방문 예측 (주 지표)** — 스와이프 like 는 "가보고 싶다"는 선택 신호이므로 이것이 제품과 맞는다.
  양성 = 미래 방문 가게(풀 안, 이력 제외), 음성 = 풀의 나머지 전부(샘플링 없이 전수 랭킹).
  지표: AUC, Hit@10, Recall@50, NDCG@20.
- **R. 방문 가게 중 만족 예측 (보조)** — 이전 세션이 잰 것. 미래 방문 가게 중 rating ≥ 4 vs ≤ 3.
  양쪽 클래스가 다 있는 사용자만. 지표: AUC. (별점은 취향보다 그 집의 실행 품질을 반영하므로 보조.)
- 집계: 사용자 평균. **품질 베이스라인 대비 사용자 단위 paired bootstrap 95% CI (2,000회, seed 고정).**
  CI 가 0 을 포함하면 "우위 미확정" 이라고 쓴다. 작은 양수를 근거로 삼지 않는다.

### 누수 규칙
- 가게 표현을 리뷰 텍스트로 만들 때(Step 2) 평가 사용자의 리뷰는 **전부** 제외한다.
- 품질 통계: 서버가 쓰는 카카오 집계(`review_avg`, `review_count`)를 1차로 쓴다. 평가 사용자 리뷰가
  집계에 섞여 있으나 가게당 최대 1건이라 미미함을 명시. 보조로 크롤링 리뷰만으로(평가 사용자 제외)
  다시 계산한 품질도 보고한다.
- 하이퍼파라미터(λ 등)는 **사용자 5-fold 교차검증**으로 고른다. 테스트 사용자에게서 고르지 않는다.

### 베이스라인 (반드시 포함)
1. `random`
2. `popularity` — log1p(review_count)
3. `quality` — 베이지안 평균 (BAYES_C=10, swipe.py 와 동일)
4. `current` — 현재 서버 모델(카테고리·가격 로지스틱)을 오프라인으로 재현. 이력을 like/dislike 로 순서대로
   먹여 동일한 온라인 갱신을 돌리고, 사후 평균으로 점수(Thompson 난수 없음). **서버 함수와 갱신 수식이
   같음을 테스트로 증명한다.**

### 산출물
- `analysis/backtest/` 패키지: 데이터 로드, 분할, 후보 풀, scorer 레지스트리, 지표, bootstrap, CLI.
- `analysis/backtest/results/<run>.json` + `<run>.md` (표: 모델 × N × 지표, CI, 사용자 수).
- `analysis/backtest/tests/` — 분할 규칙, 누수 차단, 지표, current 재현을 검증하는 단위 테스트.
- 실행: `~/venvs/recsys/bin/python -m analysis.backtest.run --models random,popularity,quality,current`

## 2. 가게 표현 (Step 1~3)

### 텍스트 임베딩 (Step 1 준비)
- 모델: `BAAI/bge-m3` dense, L2 정규화, 1,024차원. CPU(4코어, GPU 없음). `torch.set_num_threads(3)`.
- 임베딩 대상:
  - 메뉴: 고유 메뉴명 23,171개 (max_length 32).
  - 리뷰: `content` 길이 ≥ 20자, 동일 텍스트 중복 제거 (max_length 256).
  - 가게 텍스트: `ai_title + ai_summary + tags + review_tags` 를 이어 붙인 문장 1개/가게 (max_length 256).
- 출력: `data/vectors/{menus,reviews,store_text}.npy` (float32) + 같은 이름 `.index.jsonl`
  (행 → id/텍스트) + `manifest.json` (모델, 건수, 소요시간, sha256). git 에는 넣지 않는다(.gitignore).
- 로더: `analysis/vectors.py` — `load("menus") -> (ids, matrix)`.

### 메뉴 다중 벡터 (Step 1)
- 가게별 대표 메뉴 K ≤ 8: `menu_index` 순(카카오 노출 순서 = 대개 대표 메뉴 먼저)에서 **범용 메뉴 제외.**
  범용 메뉴 = 가게 수 기준 출현 빈도 상위(아메리카노·콜라·공기밥·소주 류) — 데이터에서 임계값을 정해
  목록을 기록한다. 카페는 음료가 곧 메뉴이므로 예외 규칙을 둘지 실험으로 정한다.
- 가게-가게 유사도 `MaxSim(A→B) = mean_{a∈A} max_{b∈B} a·b`, 대칭화는 양방향 평균.
  풀 전체 2.2k×2.2k 행렬을 modality 별로 미리 계산해 실험을 싸게 만든다.
- 사용자 점수: 이력의 like 가게 h 에 대해 `agg_h w_h · sim(h, i)`.
  **agg ∈ {mean, max, logsumexp(τ)}** 를 모두 비교한다 — "평균이 다봉형 취향을 뭉갠다"는 가설의 직접 검증.
  대조군: 가게=메뉴 평균 벡터 1개, 사용자=like 가게 평균 벡터 1개, 코사인 (이전 방식).
- dislike 가게: 가중치 0 vs 음수 를 비교. (낮은 별점은 음식 거부가 아니라 실행 실패일 수 있음 — 이전 진단.)
- 하이브리드: 사용자 내 후보 z-정규화 후 `quality_z + λ·content_z`, λ ∈ {0.25, 0.5, 1, 2, 4} 를 5-fold 로 선택.

### 리뷰 다중 벡터 (Step 2)
- 가게별 표현력 있는 리뷰 ≤ 12개(길이·구체성 휴리스틱; Hub 의 expressiveness 루브릭 참고, 사람 라벨은 아직 0건).
  평가 사용자 리뷰 제외. 이후 속성 추출(맛·식감·조리·재료·분위기·이용상황)은 근거가 생기면 추가.

### 사진 (Step 3)
- tag 가 이미 FOOD/INDOOR/OUTDOOR 로 나뉘어 있다. 음식 벡터(FOOD, 가게당 ≤ 6장)와 공간 벡터
  (INDOOR+OUTDOOR, ≤ 4장)를 분리. CLIP 계열 CPU 임베딩. 텍스트 결과가 나온 뒤 진행.

## 3. 사용자 모델과 온라인 학습 (Step 4)
- 긍정 프로토타입 ≤ 5개: like 가게들을 modality 별 유사도로 묶어(agglomerative) 대표. 부정 ≤ 2개.
- 구성요소 점수 벡터 `s = [menu, review, food_photo, space_photo, −negative, quality, price_fit, explore]`.
- 사용자별 가중치 w 를 pairwise(BPR) 온라인 갱신 + Thompson 샘플링. 파라미터 수 ≤ 10.
- 재시작 시 `state/preferences.jsonl` 재생으로 정확히 복원돼야 한다 (난수는 선택에만).

## 4. 서버 반영 (Step 5) 과 MR

- 백테스트에서 CI 가 0 을 넘긴 구성만 실제 추천에 켠다.
- 이 EC2 의 git 은 로컬(`feat/be-recsys-multivector`). GitLab 은 인증이 없어 push 불가 — 인증이 오면

## 5. 진행 기록

### Step 0 결과 (2026-09-09, `analysis/backtest/results/step0-baselines.md`)
- 풀 2,216곳, 평가 사용자 227명. N=10 을 다 채운 사용자 108명, N=20 은 31명 — **N ≤ 5 가 제품의 주 구간**이다.
- 과제 P(다음 방문): `popularity` AUC .676 이 압도, `quality` 는 .502 로 무작위. `current` 는 .505→.520 (학습은 되나 미약).
- 과제 R(만족): `quality` .704, `popularity` .482 (무작위 이하). **두 과제는 반대 방향**이다.
- `popularity` 의 P 우위에는 구조적 이점이 섞여 있다: 정답을 카카오 리뷰에서 뽑았으므로 리뷰 많은 가게가 정답이 될 확률 자체가 높다.

### Step 0 → Step 1 로 넘기는 결정
1. 과제 P 의 **참조 모델을 `popularity` 로** 둔다 (quality 는 P 에서 무의미). R 은 `quality` 참조 유지.
2. 표본틀 편향을 걷어내기 위해 **인기 매칭 AUC(`auc_pm`)** 를 추가한다: 양성마다 같은 리뷰수 십분위의
   음성만 상대로 순위 비교. 취향 신호가 인기와 독립적으로 존재하는지를 재는 지표다.
3. 콘텐츠 모델은 (a) 단독, (b) `popularity_z + λ·content_z` 하이브리드로 평가한다. λ 는 5-fold 로 고른다.
4. 메뉴 벡터의 범용 메뉴 문제는 stoplist 대신 **IDF 가중**(가게 문서빈도 기반)을 1차로 쓴다.
   아메리카노(369곳)는 저가중, 희귀 메뉴는 고가중. 변형은 실험으로 비교한다.
5. 근거 산출물에 **사례 설명**을 포함한다: 사용자의 like 가게 → 추천 상위 가게와, 어떤 메뉴 쌍이 매칭됐는지.

### Step 1 결과 (2026-09-09, `analysis/backtest/results/step1-menu.md`)
- 메뉴명 MaxSim 단독: P AUC .528 (popularity .676 에 크게 못 미침). 인기 매칭 `auc_pm` 에서는 .535 vs .525 로
  콘텐츠가 앞서나 CI 는 0 포함. Hit@10 은 콘텐츠 .07~.09 > popularity .044 — **상위는 정확하고 꼬리는 무작위**인 모양.
- 집계 max > mean (가설 방향 일치) 이나 +0.003~0.005 로 미미 — 사용자당 like 가 평균 4개뿐이라 뭉갤 봉우리가 적다.
- dislike 가중은 β 가 클수록 해롭다 (0 > −0.5 > −1). IDF 는 중립. K=8 > K=20.
- bge-m3 는 짧은 메뉴명에서 문자열 유사도로 동작한다 (곱창전골↔모츠나베 0.222, 초밥↔지라시스시 0.251,
  메밀소바↔멜론소다 0.688). 최근접 5곳 중 업종이 다른 비율 26% (무작위 82%) — 업종을 넘지 못하고 업종 안을 쪼갠다.
- 체인 문제: 같은 브랜드 지점끼리 유사도 1.0 으로 상위를 점거.

### Step 1 → Step 1.5 로 넘기는 결정 (계약 수정 — 근거 포함)
1. **과제 P 의 이력 해석을 바꾼다: 방문 = 관심.** 제품의 like 는 "가보고 싶다"(방문 전 관심)이고, 백테스트의 방문도
   방문 전 관심의 결과다. 별점은 방문 후 만족이라 관심과 직교한다. Step 1 에서 dislike 가중이 해로웠던 것이 이를 뒷받침한다.
   따라서 P 의 이력 신호 = **방문한 가게 전부**(rating 무관, 가중 1). 기존 like/dislike 해석은 `history=like_dislike` 열로 병기.
   이력 신호가 N=3/5/10/20 에서 2.3/4.0/7.0/8.8 → 3/5/10/20 으로 늘어난다. dislike("관심 없음")는 오프라인에서 검증할 수 없고
   shadow 로깅으로 온라인에서 검증한다고 명시한다.
2. **협업 필터 베이스라인(item-item 공방문)** 을 추가한다. 리뷰 21,803명 × 33,300건은 사용자-가게 행렬이다. 평가 사용자
   227명의 리뷰를 **전부 제외**하고 만든 가게-가게 공방문 코사인으로 `score(i) = agg_h sim(h,i)`. 콘텐츠가 이겨야 할 진짜
   상대이자 "다음 방문이 얼마나 예측 가능한가"의 상한 참고치다. 이건 크롤링 없이 지금 데이터로 된다.
3. λ 선택 기준을 AUC 외에 **NDCG@20** 으로도 돌린다. 스와이프 제품은 상위 10~20장이 전부다.
4. 같은 브랜드 지점은 근접 중복이다. 브랜드 정규화(지점명 제거) 후 이력과 같은 브랜드인 후보는 유사도 계산에서
   자기 자신처럼 취급하지 않도록 **브랜드 중복 억제** 옵션을 넣고 효과를 잰다.
5. 추가 크롤링의 근거: 평가 사용자의 이력은 가게별 크롤링 표본(가게당 ~12건)에 잘린 부분 관측이다. **이미 관측된
   사용자의 역삼 리뷰 목록을 사용자 단위로 보완**하면 범위(역삼)를 벗어나지 않고 N=10/20 표본(108/31명)이 커진다.
   크롤러는 상류 저장소(`crawler/`)에만 있어 GitLab 접근 뒤에 진행한다.

### Step 1.5 결과 (2026-09-09, `analysis/backtest/results/step1_5-visit-cf.md`)

위 결정 **1~4번**을 구현했다(5번 추가 크롤링은 GitLab 접근 대기라 손대지 않았다).

- **1번 계약 수정.** 이력 해석 `visit` 을 넣고 `like_dislike` 를 남겼다(`--history`). 신호 수는
  N 을 다 채운 사용자 기준 **3/5/10/20** 으로 예고대로 늘었다(전체 평균은 3.00/5.00/8.81/11.23 —
  N=10·20 을 채우는 사용자가 108·31명뿐이라 그렇다). 효과는 모델마다 다르다: `current` 는 과제 P
  AUC 가 N 전부에서 CI 로 올랐고(N=20 .5201 → .5540, +.0339 [+.0267, +.0412]) 과제 R 은 N=5·10·20
  에서 CI 로 **내렸다**(N=20 .7055 → .6623). `menu_top8_max` 는 P 에서 N=3·20 만 CI 를 넘겼다.
  방향은 '관심과 만족은 직교한다' 와 맞지만 **직교성을 따로 잰 것은 아니다.**
  `current` 는 like/dislike 를 나눠 받으므로 `visit` 에서 **모든 방문을 like 로 먹인다**(문서화).
- **2번 협업 필터.** `cf_item_{sum,mean,max}` 추가. 평가 사용자 227명의 리뷰 4,213건을 전면 제외.
  남은 저자 21,326명 중 풀 가게 2곳 이상은 **3,661명**뿐이고, 비영 가게 쌍은 **15,321 / 2,454,220
  (0.62%)**, 그 중 **98% 가 공방문자 1명**짜리다. 단독 성능은 N=5 AUC .5432 · auc_pm .5324 ·
  Hit@10 .0925 (`popularity` .6756 / .5250 / .0441) — **AUC 는 지고 Hit@10 은 이긴다.**
  `sum` 과 `mean` 은 사용자 안에서 순위가 같다(정의).
- **`hybrid_pop_cf_item_sum` 이 이 프로젝트에서 처음으로 `popularity` 를 일관되게 넘겼다.**
  AUC +.0060 (N=3) → +.0150 (N=20), CI 전부 0 을 넘김. 지표 4 × N 4 = 16칸 중 14칸이 유의.
  **다중비교 보정을 하지 않았고 폭은 AUC 0.01 수준**이다 — 서버 반영은 아직 아니다.
- **3번 λ 선택 기준.** `--select-metric auc|ndcg@20`. 메뉴 하이브리드에서 두 잣대가 **갈린다**:
  `auc` 는 λ=0.25 고정(AUC +.0047~+.0080, CI 통과), `ndcg@20` 은 λ 0.5~2 를 골라 Hit@10 은
  +.0220 오르지만 AUC 가 -.0157 (N=5) 로 **CI 를 나쁜 쪽으로 넘긴다.** CF 하이브리드에서는
  AUC 가 거의 안 움직이고(-.0002) Hit@10 만 +.0308 올라 상충이 없다.
- **4번 브랜드 중복 억제.** 이름 2,795개 중 공백 있는 1,583개의 89%가 마지막 토큰이 `점` 으로
  끝난다는 관찰에서 규칙을 만들었다(`analysis/content/brands.py`). 후보 풀 2,216곳 → 브랜드
  1,931개, 2곳 이상인 브랜드 129개에 414곳(18.7%). 억제하면 상위 10 안의 '이력과 같은 브랜드'
  가게가 사용자당 **1.53곳 → 0.02곳**으로 걷히지만 **지표는 하나도 안 오른다**(전 지표·전 N 에서
  CI 가 0 을 포함, 방향은 미세하게 음). 체인 억제는 지표가 아니라 **노출 규칙**의 문제다.

다음(Step 2)으로 넘길 것: CF 와 콘텐츠는 이기는 지표가 다르다(CF 는 Hit@10, 콘텐츠는 auc_pm) —
**섞으면 더 나아지는지**가 첫 질문이다. CF 의 증거가 얇다는 것(공방문자 1명이 98%)은 5번 크롤링의
근거를 하나 더 보탠다.

### Step 1.5 결과 요약 (2026-09-09, `step1_5-visit-cf.md`)
- 방문=관심 계약은 P 에서 전 N 유의하게 도움 (`current` +.005→+.034), R 에서는 반대 (예상대로 — R 은 별점 과제).
- `hybrid_pop_cf_item_sum` 이 **전 N 에서 popularity 를 AUC 로 유의하게 넘김** (+.006→+.015). Hit@10 .106 (popularity 의 2.4배).
  CF 는 극도로 희소(비영 쌍 0.62%, 98% 가 공방문자 1명)인데도 신호가 있다. 메뉴 콘텐츠는 auc_pm 에서, CF 는 AUC·Hit@10 에서 우세.
- 브랜드 억제는 지표를 바꾸지 않는다. 노출 규칙(같은 브랜드 연속 금지)으로만 쓴다.
- λ 선택: CF 하이브리드는 NDCG@20 기준이 공짜로 낫다. 메뉴 하이브리드는 AUC 와 NDCG 가 상충한다.

## 6. Step 4·5 설계 (오프라인 근거 위에서 제품이 실제로 도는 방식)

### 구성요소 점수 → 사용자별 가중치 (파라미터 ≤ 8)
후보 i 에 대해 사용자 u 의 현재 like 집합 L, dislike 집합 D 로 계산하는 성분 (전부 후보 풀 안 z-정규화):
```
z_pop   log1p(review_count)                       관심 백본 (Step 0)
z_q     베이지안 평균 평점                          만족 가드 (Step 0: R 에서 유일하게 작동)
z_cf    Σ_{h∈L} cooc_cos(h, i)                     공방문 (Step 1.5)
z_menu  max_{h∈L} MaxSim_menu(h, i)                메뉴 집합 (Step 1)
z_text  max_{h∈L} cos_text(h, i)                   카카오 요약문 (Step 2)
z_rev   max_{h∈L} MaxSim_review(h, i)              리뷰 집합 (Step 2)
z_neg   max_{h∈D} sim(h, i)   (modality 평균)      기피 — 오프라인 근거 없음, 온라인에서만 검증
```
`score = w·z + Thompson 노이즈`. w 의 사전값은 오프라인 블렌드(Step 2)의 CV 가중치. 사용자별 w 는
**쌍대 로지스틱**(새 like 카드 vs 최근 dislike 카드 ≤ 5쌍, σ(w·(z_A − z_B)))을 라플라스 근사 대각 가우시안으로
온라인 갱신 — 현재 서버의 갱신 골격(로지스틱 + 라플라스 + Thompson)을 그대로 쓰되 특성만 바꾼다. 반대 라벨이 아직
없으면 점별(pointwise) 갱신. 난수는 선택에만 쓰고 학습에는 안 쓴다 → `preferences.jsonl` 재생으로 정확 복원.

### 다중 취향 프로토타입은 "계산" 이 아니라 "설명" 용이다
max_{h∈L} 은 like 가게 수 L 에 선형이고 유사도 행렬이 미리 있어 2,216 후보 × L ≤ 300 은 밀리초다. 프로토타입 ≤ 5개는
like 가게를 유사도로 묶은 군집 대표로, 관리자 화면·추천 이유("매운 국물 / 조용한 카페 / 가성비 고기")에 쓴다.

### 콜드스타트·탐색·다양성
- 0 스와이프: `z_pop + 0.5·z_q` (관심 + 만족). 스와이프가 쌓일수록 w 가 이동.
- 10장 중 1장은 Thompson 표본이 큰 카드(탐색). 같은 브랜드 연속 금지, 같은 cat2 연속 3장 금지(기존), 배치 안
  메뉴 MaxSim > 0.9 인 근접 중복 금지.

### 서빙 산출물 (서버는 numpy 만 쓴다)
- `data/kakao/sim_{menu,text,review}.npy` float16 풀 2,216² (각 ~10MB) + `pool_ids.json` + `cooc.npz`(희소).
  오프라인 스크립트 `analysis/build_serving.py` 가 벡터에서 만든다. torch 는 이미지에 안 들어간다.

### 온라인 검증: shadow 가 아니라 **팀-드래프트 인터리빙**
사용자 수가 적어 A/B 는 검정력이 없다. 10장 배치를 신·구 정책이 번갈아 뽑아 섞고, 각 카드에 정책 태그를 로그에 남긴다.
정책별 like 율 비교가 곧 온라인 검정이다 (`MATCHURI_POLICY=interleave|new|legacy`). 관리자 화면에 정책별 like 율 노출.

### 추천 이유
최대 성분에서 만든다: "좋아요한 ○○의 리뷰와 닮았어요: '…'" (최적 리뷰 쌍), "메뉴 '마라탕' 이 좋아요한 ○○와 비슷해요",
"○○에 간 사람들이 많이 간 곳이에요"(공방문), 콜드스타트는 "리뷰 n개·평점 x 의 인기 가게예요".

### 임베딩 모델 프로브 결과 (2026-09-09, `probe-menu-embeddings.md`)
- bge-m3, KURE-v1, multilingual-e5-large-instruct, Qwen3-Embedding-0.6B, arctic-embed-l-v2 + 지시문/접두어 변형 10종 **전부**
  "취향 유사 쌍 vs 글자만 닮은 미끼 쌍" AUC < 0.5. 모츠나베를 곱창전골 근처에 두는 모델은 없다 (최선 20,449/23,198위).
- 글자가 안 겹치는 56방향의 중앙값 순위는 bge-m3 7,350 이 Qwen3 11,467 보다 낫다 → **모델 교체는 답이 아니다. bge-m3 유지.**
- 음식 계열 신호는 있으나(무작위 대비 0.5~0.94) 표기 유사도가 그 위를 덮는다. 4~10글자 고유명사에는 재료·조리법·맛이 없다.
- 결론: 메뉴 의미는 **설명 레이어**(메뉴명 → 재료·조리법·맛·매운맛·국물 문장, LLM 생성)에서 와야 한다. 붙인 뒤 같은 벤치마크
  (`analysis/probe_menu_embeddings.py` 상단 데이터)로 AUC > 0.5 를 확인하고, 못 넘으면 버린다.
- 함정: Qwen3/e5 는 config dtype 이 bf16/fp16 이라 CPU 에서 3~7배 느리고 코사인이 1.003 까지 나온다. `dtype=float32` 고정.
- 순서 결정: 리뷰·요약문(Step 2)이 이미 자연어 설명 레이어다. Step 2 결과를 본 뒤 메뉴 설명 레이어의 필요와 규모를 정한다.

## 7. Step 2 (2026-09-09, `analysis/backtest/results/step2-text-reviews.md`)

2절 '리뷰 다중 벡터' 와 3절 '구성요소 점수' 를 구현했다. Step 1.5 가 남긴 질문 — "CF 와 콘텐츠는
이기는 지표가 다르다, 섞으면 나아지는가" — 이 이 Step 의 주제다. 기준은 둘: `popularity` 와 Step 1.5 의
막대 `hybrid_pop_cf_item_sum`(λ 를 NDCG@20 으로 고른 것). **막대는 다시 계산해 step1_5 와 소수 4자리까지
같음을 확인했다**(AUC .6820/.6850/.6890/.6908).

### 결과
- **가게 요약문(`store_text`)** — `ai_title+ai_summary+tags` 를 문장 하나로. 후보 풀 2,216곳 중
  **2,203곳(99.4%)**, 없는 13곳은 메뉴와 같은 NaN 규칙. N=5 단독으로 AUC .5742 · **auc_pm .5596** ·
  Hit@10 .0661 — `popularity`(.6756/.5250/.0441) 에 AUC 는 CI 로 지고 **인기 매칭 AUC 는 메뉴(.5434)보다
  높다.** 집계는 `lse01` > `mean` > `max` 로 메뉴(max 우세)와 방향이 반대다.
- **리뷰 다중 벡터** — 가게당 ≤ 12개, 평가 사용자 227명의 리뷰 2,674건 전면 제외(테스트로 고정).
  쓸 수 있는 리뷰가 **0건 102곳 / 1~11건 1,394곳 / 12건 이상 720곳(32%)**, 쓴 벡터 15,643개.
  선택 변종(`longest12`/`random12`/`recent12`)과 집계(max/mean/lse01)의 NDCG@20 폭은 0.002~0.003 —
  **어느 쪽도 중요하지 않다.**
- **PLAN 원칙 1번이 리뷰에서는 뒤집혔다.** 단일 벡터 대조군(리뷰 12개의 평균 1개)이 MaxSim 을 전 지표에서
  이긴다: NDCG@20 .0168 vs .0110, AUC .6475 vs .6153, auc_pm .5457 vs .5420. 한 가게의 리뷰 12개는
  대체로 같은 말을 다르게 한 것이라 집합으로 둘 이득이 없고, 평균 벡터는 **개수 편향이 없다.**
- **난수 벡터 대조군이 이 Step 의 가장 중요한 발견이다.** 개수 구조만 남기고 벡터를 난수로 바꾸면 AUC
  **.6171 로 진짜 벡터(.6153)보다 높다.** MaxSim 의 `max_{b∈B}` 가 |B| 에 단조증가하는데 리뷰 수가 곧
  인기이기 때문이다(쓴 벡터 수 ↔ log1p(리뷰 수) 상관 **0.88**). 인기를 통제하면 뒤집힌다: 대조군 auc_pm
  .482(무작위 이하) vs 진짜 .542. **집합형 표현의 AUC 는 내용의 증거가 아니다.**
- **구성요소 블렌드가 막대를 넘었다.** `z_pop + Σ λ_m z_m`(성분 5개)의 λ 를 바깥 5-fold 로 학습했다.
  쌍대 로지스틱(BPR)이 지표 4 × N 4 = 16칸 중 **9칸에서 막대를 CI 로 넘겼고 진 칸은 없다** —
  AUC +.0100(N=5)/+.0101(N=10)/+.0115(N=20), auc_pm 전 N +.030~+.036, NDCG@20 N=5·20.
  `popularity` 대비로는 16/16칸 전부 CI 통과. 격자 탐욕 선택은 같은 성분으로 3/16칸에 그친다 —
  **λ 를 무엇으로 고르느냐가 어떤 성분을 쓰느냐만큼 중요하다.**
- **ablation(쌍대, 전 N·전 지표).** 기여가 CI 로 확인된 것은 `popularity`(5칸)·`cf_item_sum`(8칸)·
  `menu_top8_max`(5칸, 전부 auc_pm)·`text`(1칸). **`review` 는 한 칸도 못 넘겼다** — 학습된 λ 는 가장 큰
  0.47~0.68 인데도 빼도 지표가 안 나빠진다. 인기·CF·요약문과 겹치는 신호라는 뜻이다.
- **업종 교차.** 최근접 5곳 중 cat2 가 다른 비율: **리뷰 46.1%** > 요약문 27.1% ≈ 메뉴 26.3%
  (무작위 82.7%). 리뷰는 업종 경계를 확실히 더 넘지만 무작위와는 여전히 멀다. '카테고리를 넘는 취향' 의
  첫 관측이되, 절반은 여전히 같은 업종이다.

### Step 2 → Step 3 으로 넘기는 결정
1. **집합형 modality 에는 난수 벡터 대조군을 의무로 붙인다.** 사진(Step 3)도 같은 함정에 있다 — 사진 수는
   인기와 상관되고 MaxSim 은 집합이 클수록 점수가 커진다. 대조군 없이 나온 AUC 는 보고하지 않는다.
2. **리뷰는 점수에서 단일 벡터로 쓴다.** MaxSim 은 **설명 전용**으로 남긴다 — 6절의 추천 이유("좋아요한
   ○○의 리뷰와 닮았어요: '…'")는 리뷰 쌍이 필요하고, 사례 표가 그 쌍이 실제로 읽힌다는 것을 보여 준다.
3. **λ 는 쌍대 로지스틱으로 학습한다.** 격자 탐욕 선택은 버린다. 6절이 요구한 w 의 사전값은
   `cf .48~.50 / menu .23~.30 / text .39~.47 / review .47~.68`(N 별 폴드 평균, w_pop = 1).
4. **`blend_pairwise` 는 온라인 검증 후보다.** 4절의 기준("CI 가 0 을 넘긴 구성만")을 충족한 첫 모델이지만
   다중비교 보정을 하지 않았고 폭은 AUC 0.01 수준이다 — 6절의 팀-드래프트 인터리빙으로 확인한다.
5. **성분 간 중복을 잰다.** `review` 가 큰 λ 를 받고도 ablation 에서 죽는 것은 성분들이 서로 상관돼 있다는
   신호다. Step 3 에서 성분 상관 행렬을 보고 중복 성분을 정리한 뒤에 사진을 얹는다.
6. **`z_q`(품질)를 블렌드에 넣을지 다시 본다.** 이번에는 뺐다(과제 P 에서 AUC .50). 과제 R 의 가드로만
   쓸지, 성분으로 넣고 λ 가 0 이 되는지를 볼지 정해야 한다.

**6절과 달라진 것 (근거).**

1. **`z_rev` 는 MaxSim 이 아니라 리뷰 평균벡터 코사인의 `mean` 집계다.** Step 2 결정 2번이
   점수에서 단일 벡터를 쓰라고 했고, 그 모델(`review_longest12_single`)의 점수는
   `v_i·Σ_h v_h/‖Σ_h v_h‖` 라 후보 무관 상수를 빼면 **`mean_h cos(v_i, v_h)` 와 순위·z 가 동일**
   하다. lse 로 두면 오프라인에서 잰 적 없는 모델이 된다. MaxSim 은 설명 레이어에만 남았다.
2. **`z_text` 는 `max` 가 아니라 logsumexp τ=0.1.** Step 2·3a 의 결선 모델이 `text_lse01` 이다.
3. **설명용 리뷰 벡터는 가게당 12개가 아니라 6개.** 12개를 다 실으면 35MB 라 예산을 위협한다.
   6개면 21MB 이고 쌍 후보가 36개다 — 인용문 한 줄에는 충분하다. 점수용 평균 벡터는 12개 전부다.
4. **`cooc` 는 희소(`.npz`)가 아니라 조밀 float16.** 비영 쌍이 2.64%뿐이라 희소가 작지만(≈1MB),
   점수는 매번 like 행 |L|개를 뽑아 더하는 일이라 조밀 행렬이 단순하고 빠르다. 9.8MB 는 예산 안이다.
5. **행렬은 디스크에 float16, 메모리에 float32.** 호출마다 float16→float32 변환에 modality 당
   3.5ms(|L|=300)가 든다. 켤 때 한 번 펴면 0.6ms 다. 상주 메모리 +79MB.
6. **콜드스타트에 기피 항을 더한다.** 6절의 식은 `z_pop + 0.5·z_q` 이지만 dislike 는 like 없이도
   계산되므로 `w_neg·z_neg` 만 얹는다. 첫 10장에서 배운 것을 버릴 이유가 없다.
7. **경로는 `data/kakao/serving/`** (6절은 `data/kakao/sim_*.npy`). 크롤링 원본 테이블과 파생
   산출물을 한 디렉터리에 섞지 않기 위해서다.
8. **탐색 카드(10장에 1장)는 화면 기준이다.** 인터리빙에서 상대 정책이 뽑은 카드도 노출로 세므로
   '10장에 1장' 이 화면에서 참이 된다. 대신 그 슬롯이 legacy 차례에 걸리면 그 배치에는 탐색
   카드가 없다.

**남은 것·주의.** ① 쌍이 5개라 한 번의 피드백이 사후 분산을 legacy 보다 ~5배 빨리 좁힌다
(6절이 지정한 값이다. 탐색은 '10장에 1장' 규칙이 맡는다). ② 정책별 like 율은 **위치 편향**을

③ `/admin` 화면은 아직 legacy 패널만 그린다. 새 정책의 데이터는 `/admin/api/users/{id}` 의
`taste` 와 `/admin/api/policies` 에 이미 나온다. ④ 응답 계약은 **더하기만** 했다
(`/cards.policy`, `learned.policies`, `admin` 의 `taste`).

### Step 3d 온라인 폭주 수정 (2026-09-09, `server/recsys/`, `analysis/`)

지형도가 남긴 질문("`공방문` +13.96 뒤로 가중치가 한 자리도 안 움직인다")의 답이
나왔다. **포화는 증상이고 원인은 z 였다.** 실서버 기록에서 사용자
`u_475a743551e4` 가 `like 65 → dislike 65 → like 741` 세 장으로 `cf −63.63 · menu
−3.54 · text −1.17 · neg −2.42` 에 도달했고, 재생으로 소수점까지 재현했다.

- **원인 ① 쌍 안의 자기 유사도.** 성분 z 는 피드백을 넣기 전 집합으로 계산했지만
  **쌍의 상대쪽 가게는 이미 그 집합 안에** 있다. 유사도 행렬의 **대각선이 최댓값**
  (cooc(x,x)=1, sim(x,x)=1)이라 z(상대)가 자기 자신으로 부푼다. 실측: 741 과 짝지은
  65 의 `z_cf` 가 **+256.28**(menu +15.02 · text +7.61 · neg +10.17), Δz_cf =
  −256.35, 한 걸음에 `w_cf` 0.46 → **−63.63**. 게다가 `dislike 65` 는 쌍이
  (65, 65) 라 Δz = 0 이어서 **아무 일도 하지 않았고**, 65 는 like 와 dislike 집합에
  **동시에** 남았다.
- **원인 ② 자를 것 없는 z.** `cf` 는 공방문 코사인의 합이라 후보 대부분이 0 인
  희소·긴꼬리 점수다. 백테스트 후보(N=5)에서 `cf` 의 z 최대가 **+41.86**, |z| > 3 인
  후보가 **2.70%** 다(`menu` +14.65 / 1.23%, `text` +6.05 / 0.63%,
  `popularity` +3.74 / 0.43%). 되평가가 없어도 한 쌍이 가중치를 수 단위로 민다.
- **포화는 그 다음이다.** |w| 가 수십이 되면 σ(w·Δz) 가 0·1 에 붙어 기울기가 0 이
  되고, 그 뒤 어떤 피드백도 모델을 못 움직인다. 지형도가 본 '평평한 구간' 이 이것이다.

고친 것은 넷이고 전부 결정적이다(난수 없음 — 재생은 그대로 복원된다).

1. **leave-one-out.** 쌍을 채점할 때 **그 쌍의 두 가게를 L·D 에서 모두 뺀다**
   (`taste._loo_idx`). 쌍마다 이력이 다르므로 성분 계산도 쌍마다 한 번씩 돈다.
2. **마지막 라벨만 남긴다.** 같은 가게를 다시 평가하면 넣기 전에 **like·dislike
   양쪽에서 지운다** — 한 가게가 두 집합에 동시에 있으면 대각선 문제가 되살아난다.
3. **z 를 [−3, 3] 으로 자른다** (`content.Z_CLIP`). `component_scores` 한 곳에서
   자르므로 서빙·peek·지형도·재생이 같은 값을 본다.
4. **한 걸음을 |Δm_j| ≤ 0.5 로 묶는다** (`taste.MAX_STEP`). 라플라스 갱신은 그대로고
   이건 뚜껑이다 — 앞으로 어떤 성분이 또 긴 꼬리를 갖더라도 카드 한 장이 모델을
   뒤집지 못하게 한다.
