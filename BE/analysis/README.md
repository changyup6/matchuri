## 메뉴 벡터와 서빙 행렬 갱신

`embed.py --what menus`는 메뉴명과 원본 `description`을 함께 인코딩한다. 같은 이름이라도
설명이 다르면 별도 벡터이며, 설명이 없으면 이름만 쓴다. 업종·가격을 설명으로 만들어 넣지
않는다. 기본 토큰 상한은 256이며 원문이 상한을 넘으면 잘라 저장하지 않고 중단한다.

```bash
cd BE
python -m analysis.embed --what menus --data-dir /path/to/kakao \
  --output-dir /path/to/new-vectors --reuse-dir /path/to/old-vectors --local-only
```

기존 벡터는 같은 모델·차원·텍스트이고 과거 토큰 상한 안에 들어온 경우만 재사용한다.
새 `menus.npy`, `menus.index.jsonl`, `manifest.json`을 함께 반영한 뒤 `build_serving`으로
`sim_menu.npy`·`layout.json`·manifest를 다시 만든다. 메뉴 선택은 원본 `menu_index` 순서의
앞 8개를 유지한다. 기존 이름 전용 index도 읽지만 새 index의 입력 누락은 오류로 처리한다.
산출물은 Git에 넣지 않는다. 서버 재시작 시 이전 반응을 새 행렬로 재생하므로 개인별 학습
점수와 추천 순위도 달라질 수 있다. 입력 충실도 개선이 만족도 개선을 뜻하지는 않는다.

# ① 추천 실험

최근 상황을 따라가면서 누적 취향을 세부 선택에 남기는 실험은
[`temporal_taste`](temporal_taste/README.md)에 있다. 운영과 분리된 모델·고정 시나리오·
실측 결과이며, 기존 API 추천 모델을 교체한 것은 아니다.

## 과거 테스트베드 — 가상 페르소나

실유저가 없으므로 **가상 페르소나**로 replay 한다. 페르소나는 확률 모델이다.

```
P(선호) = sigmoid( b + 카테고리성향 + 가격대성향 + q·품질z [+ 매운맛보정] )
```

- 같은 (반복회차, 가게)는 어떤 정책이 보여주든 **같은 라벨**을 받는다 → 정책 간 공정 비교
- 후보 풀은 역삼동 전체 2,216곳. `server/recsys` 를 직접 임포트해 **실제 서빙 코드**를 잰다
- 모든 개선폭에 부트스트랩 95% CI 를 붙인다

| 파일 | 무엇을 |
|---|---|
| `swipe_test.py` | 서빙 정책 vs 품질정렬 vs 무작위 vs 오라클 |
| `method_compare.py` | 개인화 방법 5종 정면 비교 |
| `reco_proto.py` | 전국 실유저 리뷰(29만건) replay — 라벨이 합성이 아님 |
| `bge_bench.py`, `attr_axes*.py`, `menu_map.py` | 임베딩 기반 시도들 |

## 과거 결론 — 실제 사용자 검증 후 폐기

당시 채택했던 품질 백본 + 카테고리·가격 온라인 로지스틱 + Thompson 정책은
실제 사용자 검증에서 품질순보다 6~8%p 낮아 폐기했다. 아래 표는 왜 처음에는
그 정책을 채택했는지 남기는 과거 실험 기록이며 현재 성능 근거가 아니다.

후반(31~80장) 품질정렬 대비, 95% CI:

| 페르소나 | 개선 | 페르소나 | 개선 |
|---|---|---|---|
| 카페 선호 | **+18.7%p** | 미식가(평판=취향) | −2.0%p |
| 저가 선호 | **+13.3%p** | 취향 없음 | ±0 (무해) |
| 한식 선호 | **+5.3%p** | 텍스트에만 있는 취향 | 미해결 |

**기각한 방법과 이유** — 전부 품질 베이스라인에 졌다:

| 방법 | 결과 | 왜 졌나 |
|---|---|---|
| MF 전이 (전국 FunkSVD 가게벡터) | −11 ~ −47%p | 커버리지 절반 + 별점 회귀 벡터를 이진 스와이프에 fold-in 하면 노이즈 |
| 아이템 kNN (작성자 겹침) | −45%p (미식가) | 같은 사람이 간 두 가게 = 취향이 아니라 **생활권**(점심 반경) |
| Rocchio (LSA 텍스트) | −7%p | 비지도 축이 취향 축이 아님 |
| Rocchio (bge-m3 임베딩) | −1%p (무해까지 회복) | 임베딩은 좋아졌으나 80개 라벨의 평균차 벡터로는 방향을 못 뽑음 |
| 임베딩 PCA 24축을 피처로 | −21%p | 차원의 저주 + Thompson 노이즈 증폭 |
| 속성 축 8종(프로브) v1~v3 | −3 ~ −18%p | 축 판별력 부족(AUC 0.73) + 온라인 80장 예산으로는 피처 8개 추가 비용도 못 갚음 |

## 미해결 — 텍스트에만 있는 취향

"매운 걸 좋아함" 같은 취향은 카테고리·가격 축에 없다. 오라클 여유가 **+25.7%p** 열려 있는데
8가지 방법 전부 실패했다. 온라인 학습으로는 안 되고 **세션 밖**에서 풀어야 한다:

1. **온보딩 질문 1개** — "매운 거 좋아하세요?"는 스와이프 80장보다 정보량이 크다.
   축 데이터(`data/analysis/store_axes_menu.npz`)를 그대로 정렬에 쓰면 되고 탐색 비용이 0이다.
2. **실로그 오프라인 학습** — 스와이프가 수천 개 쌓이면 축 가중치를 세션 밖에서 학습해
   신규 세션의 사전분포로 주입한다.

## 주의 — 순환성

페르소나의 "취향"은 카테고리·가격 축으로 정의했고, 로지스틱의 피처도 같은 축이다.
따라서 이 실험이 증명하는 것은 **"이 축에 취향이 있다면 회복할 수 있다"**이지
"사람 취향이 그 축에 있다"가 아니다. 대조군으로 무지성 카테고리 매칭을 넣어 재보면,
취향=카테고리인 페르소나에서는 무지성 매칭이 오히려 더 낫다(0.876 vs 0.764).
로지스틱의 값어치는 **여러 축을 하나의 스무딩된 모델로 겸용**하는 데 있다.

실제 사람 취향이 어느 축에 얼마나 사는지는 **실스와이프 로그가 쌓여야** 답이 나온다.

# ② 리뷰 표현력(descriptive specificity) 분류

수집한 리뷰 1,200건이 **얼마나 구체적으로 묘사하고 있는지**를 규칙 기반으로 채점한다.
감정(좋다/나쁘다)이 아니라 서술의 구체성만 본다. 따라서 "맛없다"도 "맛있다"와 같은 레벨이다.

> **서비스 반영 (2026-09-18).** 채점기 본체는 `server/recsys/expressiveness.py` 로 옮겼다 —
> 배포되는 것이 `server/` 뿐이라서다. 여기 `rubric.py`·`scorer.py` 는 그 모듈을 다시 내보내는
> 껍데기라 아래 실행법은 그대로 통한다. 쓰는 곳 둘: 가게 상세의 카카오 리뷰 미리보기 순서
> (`recsys/store.py`, 표현력 → 옛 규칙) · 설문 세 줄의 순서
> (`app/user_reviews.py`, 정렬 키와 `review_levels` — 자격 게이트는 2026-09-21 에 없앴다).
> 옮기면서 고친 것(어근 중복 → multiattr 오판,
> 한 글자 지시대상 '면·파·김', '직원이·리뷰가·시간이' 함정어, 외국어 `lang` 표시, 사전 보강)은
> 그 모듈 docstring 에 있다. 카카오 3만 3천 건에서 미리보기 상위 5건의 L0·L1 비중이
> 42% → 14% 로 내려갔다.

## 표현력 레벨 (카테고리별 0~3)

| 레벨 | 이름 | 판정 | 예시 |
|---|---|---|---|
| **0** | 언급 없음 | 해당 축이 등장하지 않음 | — |
| **1** | 단순평가 | 가치판단만, 무엇이 어떤지 없음 | "맛있어요", "친절해요" |
| **2** | 속성언급 | 감각·속성 어휘로 서술 | "매콤달콤해요", "매장이 넓고 깨끗" |
| **3** | 구체묘사 | L2 + 구체화 신호 2종 이상 | "국물이 걸쭉해서 계란이 퍽퍽함" |

### 구체화 신호 5종 (L2 → L3 승급 조건)

| 신호 | 뜻 | 마커 |
|---|---|---|
| `degree` | 정도 조절·수량화 | 약간/살짝/적당/생각보다/~치고, 숫자+단위 |
| `compare` | 비교·유추 | ~같은/~보다/~에 비해/~라기보단/가장/중에 |
| `referent` | 구체 지시대상 | 메뉴명·재료명 (차슈, 국물, 계란, 떡볶이…) |
| `reason` | 근거·판단 유보 | 때문에/덕분에/~치고는/개인적으로/~인 편 |
| `multiattr` | 다중 속성 | 서로 다른 속성 어휘 2개 이상 |

> `너무·진짜·완전·엄청` 같은 **단순 강조부사는 신호로 치지 않는다.** 강조는 구체성을 더하지
> 않기 때문이다. 반대로 `약간·적당히·생각보다`는 화자가 정도를 **변별**했다는 신호이므로 인정한다.

### 보조 규칙
- 속성어 없이 화제어만 있어도 **구체화 신호가 2종 이상이면 L2** ("파스타는 다소 평범하고 조개에 모래가 많아")
- `wait`·`price`는 **숫자 자체가 속성 정보** → 화제어 + 수량표현이면 L2 (단 L3 은 불가)
- L3 도달은 **속성어가 반드시 있어야** 한다

## 리뷰 단위 지표

| 지표 | 정의 | 범위 |
|---|---|---|
| `grade` | 카테고리 레벨의 **최댓값** — 묘사 깊이 | 0~3 |
| `breadth` | 레벨 1 이상인 카테고리 수 — 묘사 폭 | 0~5 |
| `depth_sum` | 카테고리 레벨의 합 — 랭킹용 연속 점수 | 0~15 |

## 검증 방법과 한계

- 층화 무작위 표본 **2회 × 40~48건**을 직접 읽고 검수했다. 1차에서 오분류 6종(한국어 하-불규칙
  활용 미매칭, 오타, 서비스 속성어 오탐 등)을 찾아 사전과 규칙을 고쳤고, 2차 40건에서 남은
  명백한 오류는 1건("고양이"의 '양이'가 음식 '양'으로 매칭)이었다. 이것도 함정어 처리로 수정했다.
- **한계**: 규칙 기반이라 사전에 없는 표현은 놓친다. 특히 감각 형용사 없이 구체적인 사실만
  기술하는 리뷰("조개에 모래가 많아")는 보조 규칙으로 일부만 건진다.
- **L0/L1 경계가 가장 불안정하다.** 아스펙트 없는 칭찬("훌륭합니다", "전반적으로 괜춘")을
  0으로 볼지 1로 볼지는 정의 나름이다. 여기서는 **평가 대상이 특정되지 않으면 0**으로 뒀다.
- 검수는 작성자 본인이 수행했다. 독립 어노테이터 교차검증은 하지 않았다.

## LLM 채점 (EXAONE 3.5 7.8B, 로컬 Ollama)

규칙 기반과 별도로, 로컬 GPU(RTX 4050 6GB)에서 EXAONE 3.5 7.8B(Q4_K_M)로 동일한
루브릭을 채점시켜 교차검증했다. 전량 1,200건 완료.

### 실행 환경

```
모델    exaone3.5:7.8b (Q4_K_M, ~4.4GB)
서버    Ollama, OLLAMA_NUM_PARALLEL=3, FLASH_ATTENTION=1, KV_CACHE_TYPE=q8_0
컨텍스트 num_ctx=3072 (실측 프롬프트 ~2300토큰 + 출력 256 여유)
```

`OLLAMA_NUM_PARALLEL`(기본값 1)을 올리고 flash-attention·양자화 KV캐시를 켜서
np=1→3 구간에서 실측 약 2배 처리량 향상을 확인했다 (np=5는 오히려 np=3보다 나쁨 —
과분할로 스케줄링 오버헤드가 이득을 상회). Intel NPU(AI Boost)는 실측 벤치마크상
이 클래스 모델에는 GPU 대비 명확히 불리해 (Meteor Lake 기준 CPU보다도 느림) 검토 후 제외했다.
CPU 병행도 실측 118초/건(GPU 대비 30배)으로 기여分이 무의미해 제외했다.

### 결과 (규칙 기반 대비, 1,200건)

| 지표 | 값 |
|---|---|
| 등급 완전일치 | 55.1% |
| ±1 이내 일치 | 96.2% |
| weighted kappa | 0.439 (중간 수준) |
| 평균 등급 | 규칙 1.61 vs LLM 1.77 |

### 후처리 가드 3종 (LLM 출력 검증 레이어)

프롬프트에 명시적으로 금지 규칙을 넣어도 고쳐지지 않아, 결정론적 후처리로 교정했다.

1. **service↔wait 근거 재사용** — "웨이팅 없었음"류 문장을 service 근거로도 전용하는
   오류. 문자열 겹침 검사 + 의미 기반(대기 키워드만 있고 직원행동 키워드 없음) 검사 2종.
2. **service↔ambience 근거 재사용** — 청결/공간 묘사를 서비스 근거로 오용.
3. **빈 근거 스키마 위반** — `ev:"없음"`인데 `lv>=1`인 경우 0으로 정정.

3종 합쳐 **88회, 리뷰 85건(7.1%)** 에서 발동했다.
가장 흔한 오류는 "붐빈다 = 서비스가 바쁘다"로 추론하는 것이었다(54회).

### 알려진 한계

- **강조부사 반복이 L3로 잘못 승급되는 사례가 남아있다.** "너무너무 맛있음"처럼 실제
  속성어 없이 강조만 있는데도 L3를 받은 경우가 다수 확인됨 (L3인데 속성어 근거가
  전혀 없는 107건 중 표본 조사 결과 25~35%가 이 유형, 전체의 약 2.5~3% 추정).
  서비스/대기 혼동과 달리 키워드 기반 가드로 일반화하기 어려워(속성어 유무 자체가
  판단 대상) 미해결로 남겨둔다.
- **엉뚱한 축에 근거를 붙이는 경우**가 드물게 있다 (예: 메뉴 나열이 ambience 근거로,
  셰프 목격담이 ambience 근거로 인용됨). 발동 가능한 패턴이 다양해 가드화하지 않았다.
- 규칙 기반과 달리 **오타·신조어·영어 리뷰**를 잘 처리한다 (예: "마ㅅ있어요", "It's so
  delicious!"). 반대로 규칙 기반은 사전에 있는 표현만 정확히 잡는 대신 이런 유형에서
  전부 놓친다 — 즉 두 방식은 서로 다른 실패 모드를 가진다.
