# 트렌드 — 왜 이렇게 만들었나

`recsys/trend.py` 의 배경 문서다. 코드에는 "무엇을" 이 있고 여기에는 **"왜"** 와
**재본 숫자**가 있다. 명세가 아니라 판단의 기록이다.

측정은 전부 2026-09-14~16, `data/kakao/reviews.jsonl` 33,300건·추천 풀 1,629곳 기준.

---

## 1. 무엇이 문제였나

이 서비스에는 **시간 축이 없었다.**

| 정책 | 개인화 이전 점수 | 자리 |
|---|---|---|
| `legacy` | `w_q · qz` — 베이지안 평균 **평점** | `swipe.score` |
| `taste` | `z_pop + 0.5·z_q` — `pop` 은 `log1p(리뷰 총수)` | `taste._cold` |

둘 다 2013년부터의 **누적**이다. 10년 전에 500건 받고 식은 가게가 지난 세 달에
40건 받은 가게를 계속 이긴다. 그게 트렌드의 반대말이다.

그리고 트렌드를 관장하는 모듈이 따로 없었다 — `qz` 는 `swipe._build_pool`,
`pop` 은 `content.load` 에서 각각 만들어져 네 곳에 흩어져 있었다.

---

## 2. 데이터는 이미 있었다

`reviews.jsonl` 33,300건에 **전부 타임스탬프가 있다**(날짜 없는 리뷰 0건).

```
기간        2013-04-03 ~ 2026-09-02
리뷰 1건+   2,346곳

최근  90일:  3,658건 · 1,185곳 (3건+  370곳)
최근 180일:  6,599건 · 1,582곳 (3건+  718곳)
최근 365일: 11,630건 · 1,906곳 (3건+1,183곳)
```

**크롤 잘림은 문제가 아니었다.** 크롤이 가게당 30~40건에서 잘려 있고(총 65,763건 중
50.6%만 수집) 처음엔 이게 치명적일 줄 알았는데, 잘린 가게도 그 30~40건이 180일보다
과거까지 뻗어 있었다:

```
 90일 윈도우 — 온전 2,337곳 / 잘림  9곳 (0.4%)
180일 윈도우 — 온전 2,326곳 / 잘림 20곳 (0.9%)
```

**최근 윈도우는 99.1% 가 온전하다.** 외부 API 없이 트렌드를 만들 수 있다는 뜻이다.
180일을 고른 것은 커버리지다 — 90일이면 3건 이상인 가게가 370곳뿐이고 180일이면 718곳이다.

## 3. 신호 고르기

### 수준을 버리고 증가율만 남겼다

```
corr(log1p(최근 180일 리뷰 수), pop) = +0.576   ← 인기의 다른 이름
corr(증가율,                    pop) = +0.079   ← 거의 독립. 새 정보다
corr(최종 trend,                pop) = +0.100   (완성 후 실측)
```

`content.py` 가 `review` 성분을 버린 논리와 같다 — 그쪽은 `review`↔`popularity`
스피어만 +0.67 로 "인기의 다른 이름" 이라 가장 큰 λ 를 받고도 ablation 에서 죽었다.
같은 실수를 반복하지 않으려고 수준을 뺐다.

### 별점 변화는 약하다 — 26.6% 만 신호다

시간으로 반 가르는 대신 **무작위로** 반 갈라 같은 계산을 했다(플라시보 테스트):

```
실제(시간 분할)   398곳 · sd 0.957   분산 0.916
플라시보(무작위)          sd 0.820   분산 0.673   ← 순수 표본 잡음
                                  ─────────────
                    진짜 신호 분산 = 0.243 (전체의 26.6%)
```

**관측된 별점 변화의 73% 가 잡음이다.** 별점 분포가 J자(1점 17.8% · 5점 50.8%)라
리뷰 1건의 표준편차가 1.546 이고, 버킷당 3~4건 평균은 극도로 불안정하다.
그래서 `SHRINK_RATING = 0.27` 로 눌러 넣는다. 커버리지도 24%(398곳)뿐이라 부차 신호다.

### 윈도우는 반드시 같은 길이여야 한다

```
최근 180일 대 '그 이전 전체'  → 평균 변화 −0.317
최근 180일 대 '직전 180일'    → 평균 변화 −0.154
```

비대칭 윈도우가 없는 추세를 만들어낸다. 처음엔 전역 하락을 의심했지만 아니었다 —
연도별 전역 평균 별점은 2021년 이후 3.70~3.80 으로 평평하다. 전역 보정은 불필요하다.

### 하드 클립이 상위권을 뭉갠다

`np.clip(±3)` 을 쓰니 클립되는 건 2.27%(37곳)뿐인데 **상위 20곳이 전부 +3.00 동점**이
됐다. 트렌드가 띄우려는 바로 그 구간이 사라진 것이다. `3·tanh(z/3)` 은 ±3 경계를
지키면서 단조라 동점이 없고, `|z| < 1.5` 구간에서는 거의 선형이라 평범한 가게의
눈금은 그대로다.

## 4. 왜 성분이 아니라 보정층인가 — 이 문서의 핵심

`content.COMPONENTS` 에 9번째 성분으로 넣는 것이 자연스러워 보이지만 **안 된다.**

`taste.record` 는 성분 z 를 그대로 학습에 먹인다:

```python
z = art.component_scores(*_loo_idx(sess, art, {store_id, other}))
d = z[:, i] - z[:, art.pos[other]]
_logistic_step(sess, d, 1.0)          # z 가 m 에 박힌다
```

그리고 서버는 **재시작할 때마다** `preferences.jsonl` 을 처음부터 다시 먹여 `m` 을
복원한다(`app/state.py: restore`). 배포마다 그 일이 일어난다.

### 로그의 함수인가, 시계의 함수인가

```
m = f(preferences.jsonl, 산출물)
```

로그는 입력의 **절반**이고 나머지 절반이 산출물이다. 재생 보장은 **산출물을 고정했을
때만** 성립한다 — `manifest.json` 이 입력마다 sha256 을 남기는 이유가 이것이다.

* **산출물**(`sim_*`·`pop`·`quality`)은 버전이 있고 **사람이 의도해서** 다시 만든다
  → 느리고 추적 가능한 변경. 사실상 로그의 함수
* **트렌드**는 연속적으로 움직인다 → **시계의 함수**

같은 로그를 다음 주에 다시 먹이면 다른 `m` 이 나온다. `tests/test_replay.py` 가
지키는 계약이 깨진다.

**이 저장소는 이 문제를 이미 한 번 풀었다.** `app/ranking.py` 의 거리 보너스가
정확히 같은 이유로 `m`·`v` 에 한 톨도 안 들어간다. 트렌드는 거리와 같은 종류의
신호이므로 같은 자리에 둔다.

### 그래서 배선이 두 줄이다

```python
# app/ranking.py: build()
bonus = distance_bonus(...)
for sid, v in trend.bonus(ids).items():
    bonus[sid] = bonus.get(sid, 0.0) + v
```

거리가 이미 쓰던 채널에 합류하므로 `policy.pick_many` 까지의 배선을 새로 만들지
않았고, **두 정책에 같은 값이 내려간다** — 인터리빙 비교의 공정성이 유지된다.

### 나중에 성분으로 승격하려면

이론적 정답은 **시점 정합성(point-in-time correctness)** 이다. 그때 쓴 피처값을
그대로 학습에 쓰면 된다. `preferences.jsonl` 에 `at` 이 이미 있고(`app/state.py`),
트렌드는 `pop`·`quality` 처럼 **가게 하나당 숫자 하나**라 LOO 재계산이 필요 없다.
즉 결정 시점의 값을 로그에 적어두면(`ctx`) `m` 이 다시 로그만의 함수가 된다.

`explainer.md` 4절이 설문에서 이미 내린 판단과 같은 원칙이다 —
*"`hours_after` 와 `source` 를 기록한다 … **소급이 안 되는 정보다**"*.

단, 쌍대 갱신에서 상대 카드는 과거 것이라 시점이 섞인다. 이건 "그때 A 가 B 보다
더 뜨고 있었나" 를 배우는 것으로 해석하면 자연스럽다.

### 5.2 앵커 키워드 — 증가율에는 필요 없고, 수준에는 필요하다

이 문서의 옛 판은 `ratio` 가 요청 안에서 100 으로 정규화되니 고정 앵커로
재스케일해야 한다고 적었다. 추천이 쓰는 값은 `log(최근/직전)` 증가율이라
**정규화 상수가 로그 전에 약분된다.** 그래서 점수 수집은 **요청당 키워드 그룹을
하나만** 넣는다 — 여러 업종을 한 요청에 담으면 '한식' 이 100 을 먹고 '퓨전요리' 가
0.3 으로 눌려 해상도를 잃는다.

그런데 관측 화면의 **스테디셀러**("변동성과 무관하게 절대값이 월등한 것")는 **수준**을
견줘야 하고, 그건 이 캐시로는 불가능하다 — 실측하면 71개 파일이 **전부 최댓값 정확히
100.0** 이다. 그래서 `fetch_trend_category.py --level` 이 요청마다 같은 앵커
(`칼국수`)를 한 칸 더 넣어 두 그룹이 같은 상수를 공유하게 하고 `업종 중앙값 / 앵커
중앙값` 을 `data/analysis/trend_level.json` 에 적는다. 앵커 중앙값이 응답마다
2.49~27.23 으로 11배 흔들리는 게 바로 그 상수고, 비율에서 약분된다.

시계열은 새로 안 받는다. 수준 응답의 업종 시계열이 기존 캐시와 상수배로 **완전히**
비례해서(806일 전부, 이탈 0.0%) 기존 캐시를 자기 중앙값으로 나눈 뒤 수준을 곱한다
(`recsys/trend_search.py`). 이 값은 **추천에 들어가지 않는다** — 수준을 점수에 넣으면
큰 업종이 영구히 유리해지고 그건 트렌드가 아니다.

앵커는 **중간 크기**여야 한다. `맛집` 처럼 큰 것은 그것이 100 을 먹고 업종을 0 쪽으로
누른다. 응답이 소수 5자리라 100배 눌려도 유효숫자 3자리는 남으니 치명적인 쪽은 앵커가
너무 **작아** 분모가 되는 경우다. `--anchor` 로 바꿀 수 있다.

### 5.3 함정 셋 — 전부 실측으로 잡았다

**① 계절성.** 최근 180일 대 직전 180일은 곧 봄여름 대 가을겨울이다. 그대로 재면
냉면 +1.44, 호프 +3.67 이 '뜨는' 것으로, 오뎅바 −0.78 이 '식는' 것으로 나온다 —
트렌드가 아니라 **계절**이다. 비교 창을 **전년동기**로 바꿨다(`--basis yoy`, 기본값).
냉면 +1.44 → −0.21, 아이스크림 +0.15 → −0.30 으로 잡힌다. 받는 구간을 늘려
직전기간(`seq`)과 전년동기를 **한 번의 호출로** 둘 다 계산한다.

**② 이벤트 스파이크.** 검색량은 하루짜리 사건에 수백 배 튄다. 창의 대표값을
평균에서 **중앙값**으로 바꿨다 — 71개 기준 표준편차 0.606 → 0.494, 최대 절대값
4.25 → 3.09 이고 **둘의 상관이 +0.973** 이라 순위는 그대로고 꼬리만 눕는다.

**③ 키워드 오염.** 업종명이 곧 좋은 검색어는 아니다. `호프,요리주점` 이 +4.25 로
2위의 2.5배였다. 두 단어를 갈라 재보니 `호프` 는 맥줏집이 아니라 사람·작품 이름으로
검색돼 2025-06 평균 0.07 → 2026-07 최대 100.0 으로 튀는데 `요리주점` 은
32.45 → 22.74 로 멀쩡했다. `KEYWORD_OVERRIDE` 에 근거와 함께 적고 `요리주점` 만
쓴다 — 결과 −0.19. **같은 검사를 새 업종에도 해야 한다.**

### 5.4 65개가 음수인 것은 문제가 아니다

지금 분포는 중앙값 −0.194 · 표준편차 0.298 · 범위 −1.864~+0.377 이고 양수는 4개뿐이다.
네이버 검색 자체가 전년 대비 줄어드는 **공통 성분**이다. `trend.py` 의 z 가
`(vals - mean) / sd` 로 후보 집합 안 평균을 빼므로 공통 이동분은 **완전히 상쇄된다.**
`category` 항에서 뜻이 있는 것은 업종 사이의 **상대 순서**뿐이다.

### 5.5 서버는 여전히 네이버를 부르지 않는다

**서버는 외부 API 를 런타임에 부르지 않는다.** 외부 장애가 추천을 멈추면 안 되고,
"서버는 오프라인 산출물만 읽는다" 는 이 저장소의 약속이다. 이번 이관이 그 약속의
값을 증명했다 — 창구가 통째로 바뀌고 옛 키가 죽는 동안 서버 코드는 한 줄도 안 건드렸다.

관측은 `/admin/trends` 가 한다(`recsys/trend_history.national`). 파일이 없으면
`available: false` 이고 **오류가 아니다** — 역삼동 추이는 그대로 돈다.
그 화면은 역삼동 추이와 같은 25달 월 축에 나란히 그리므로 수집 구간도 거기 맞춰
806일을 받는다(점수에 필요한 545일보다 길다. 업종당 호출 수는 그대로 1이다).

⚠️ 이 값은 **전국**이다. 검색어 트렌드 API 에는 지역 파라미터가 아예 없다
(`device`·`gender`·`ages` 뿐). 역삼동은 오피스 상권이라 **대조용**으로 봐야 한다.

그리고 이 절의 어떤 것도 지금 추천 순서를 바꾸지 않는다 — 6절을 보라.

## 6. 기본이 꺼짐인 이유

`MATCHURI_TREND_WEIGHT` 의 기본값은 **0** 이다.

지금 legacy·taste 팀-드래프트 인터리빙이 돌고 있고, 그 비교는 '같은 조건에서 누가
더 잘 맞히나' 를 재는 실험이다. 트렌드가 순서를 건드리면 **기간 전후의 like 율을
합칠 수 없다.** 켜는 것은 그 실험이 끝난 뒤의 결정이다.

`tests/test_trend.py` 가 이것을 잠근다 — 꺼져 있으면 `ranking.build` 의 결과가
예전과 비트 단위로 같아야 하고, 켜도 `record` 가 만드는 `m`·`v` 는 한 톨도
달라지지 않아야 한다.

켤 때는 `0.4` 정도부터가 좋다(거리 보너스와 같은 눈금).

## 7. 켜기 전에 만들어야 할 것 — 노출 집중도

트렌드는 **전역 값**이라 모두를 같은 방향으로 민다. 거리는 사용자가 준 값이라 그
사람 맥락 안에서만 밀지만 트렌드는 그렇지 않다 → **인기 쏠림(rich-get-richer)**.

시간 감쇠는 이것을 **해결하지 못한다.** 감쇠는 점수의 *기억*을 줄이지 루프의 *이득*을
줄이지 않는다. 오히려 오래된 자연발생 증거를 빨리 잊게 해 루프가 만든 최신 증거의
비중을 높인다.

실제 해법은 셋이다.

1. **노출로 나눈다** — like 수가 아니라 `like/노출` 비율. 이게 본질이다
2. **탐색을 보장한다** — 이미 있다(Thompson σ×0.4, `EXPLORE_EVERY=10`)
3. **집중도를 감시한다** — `recsys/exposure.py` · `/admin/api/trend/concentration`
   · `/admin/trends` 화면 맨 아래. 노출 지니계수 · 상위 10/50/100곳 점유율

### 7.1 분모를 어디까지 잡나 — 이게 전부다

지니는 **풀 전체**에서 낸다. 노출 0 인 가게가 분모에 그대로 들어간다.

노출된 가게만 모아 재고 싶은 유혹이 있는데, 그러면 *'한 번도 안 나온 가게'* 가
분모에서 사라져 **집중도가 실제보다 좋아 보인다.** 같은 노출 분포라도 풀이 크면
지니는 커져야 맞다 — '1,600곳 중 3곳만 나갔다' 와 '3곳 중 3곳이 나갔다' 는 완전히
다른 상태다. 쏠림을 감시하라고 만든 지표가 쏠림을 숨기면 그건 지표가 아니다.
`tests/test_exposure.py` 의 `test_노출_0_인_가게가_분모에_들어간다` 가 이걸 잠근다.

`never_shown` 을 따로 싣는 것도 같은 이유다 — 지니 한 숫자로는 **"얇고 넓게"** 와
**"몇몇만 자주"** 가 안 갈린다(둘 다 낮은 지니가 될 수 있는 게 아니라, 100곳에 1번씩은
지니 0 이고 1곳에 100번은 0.99 다. 헷갈리는 쪽은 그 사이의 중간값들이다).

그리고 **정책별로 쪼갠다.** 합치면 인터리빙이 legacy 와 taste 를 섞어 버려 어느 쪽이
쏠리는지 안 보인다. 재노출은 **센다** — `policy.outcome_stats` 는 like 율을 재려고
(사용자·세션·카드)로 중복을 지우지만, 여기는 같은 가게를 **몇 번 밀었나**가 곧 쏠림이다.

### 7.2 읽는 법

완전 균등이면 지니 0 이고 상위 10/50/100 점유율이 풀 1,629곳 기준 각각
**0.6% · 3% · 6%** 다. 그보다 크면 그만큼 쏠린 것이다.

`trend_enabled` 를 응답에 같이 싣는다. 지금은 `false` 이므로 나오는 값이 곧
**끄고 잰 기준선**이다 — 켠 뒤 같은 수를 다시 재서 견주라는 뜻이고, 그 비교가
이 절의 목적 전부다. 기록이 없으면 `available: false` 이고 오류가 아니다
(노출은 카드가 실제로 나갈 때만 쌓이고 기동 복원에서는 안 쌓인다).

**트렌드나 내부 행동 점수를 켜기 전에 이 수를 먼저 적어 두라.** 켠 뒤에 기준선을
만들 수는 없다.

### 7.3 기준선 — 켜기 전의 숫자 (2026-09-18)

운영 `/admin/api/trend/concentration`(전 기간, 트렌드 무게 0 · 슬롯 0). 노출 28,037장 ·
사용자 333명 · 풀 1,499곳. `docker-compose.yml` 의 `MATCHURI_TREND_EVERY=10` 이 들어가기 **직전** 값이다.

| | 노출 | 안 나온 곳 | 지니 | 상위10 | 상위50 | 상위100 |
|---|---|---|---|---|---|---|
| 전체 | 28,037 | 0 | **0.449** | 5.6% | 18.0% | 28.1% |
| legacy | 13,859 | 38 | 0.576 | 8.9% | 25.9% | 37.6% |
| taste | 14,178 | 22 | 0.512 | 7.1% | 21.9% | 32.6% |

완전 균등이면 상위10·50·100 이 0.7%·3.3%·6.7% 다(풀 1,499). 지금도 상위 100곳이 노출의 28% 를
먹는다 — 트렌드 없이도 인기 쏠림은 있다. 켠 뒤 볼 것은 **`trend` 행의 지니와 상위N** 이고, 전체 행이
이 표보다 눈에 띄게 오르면(지니 +0.05 이상을 기준으로 잡는다) `MATCHURI_TREND_EVERY=0` 으로 되돌린다.

같은 날의 인터리빙 성적(`/admin/api/policies`): legacy like 율 0.655 [0.640, 0.671] · taste 0.676
[0.660, 0.691], 응답 3,497건씩. 구간이 겹쳐 아직 판정 전이다. 슬롯 `trend` 행은 여기 옆에 셋째로 붙는다.

## 8. 비교 API 를 트래픽 분할로 만들지 않은 이유

```
GET /admin/api/trend                  지금 무엇이 뜬다고 보는가 + 출처별 분해
GET /admin/api/trend/compare?user_id=&weight=1.0
    before/after 순위 · moved_in/moved_out · 카드별 점수 변화
```

레인을 셋으로 나누면 사용자 70여 명·선호 2,500건에서 **인터리빙이 먼저 죽는다.**
그래서 `peek` 방식으로 **같은 사용자의 같은 세션을 두 번 채점해** 차이만 본다 —
카드를 소비하지 않고, `shown` 에 넣지 않고, 노출 로그를 쓰지 않는다. 표본을 나누지
않으므로 실험 비용이 0 이다.

진짜 트래픽 분할이 필요해지면 슬롯(`EXPLORE_EVERY` 옆에 `TREND_EVERY`)으로 붙인다.
그때는 `exposures.jsonl` 에 라벨이 따로 붙어 like 율·방문율·만족도를 직접 비교할 수 있다.

### 8.1 그래서 슬롯으로 붙였다 (2026-09-18)

```
MATCHURI_TREND_EVERY = 0 (기본, 꺼짐) | N
```

"서버를 따로 올려 A/B 하면 안 되나" 가 질문이었다. 안 된다 — 셋 다 이 저장소가 이미
적어 둔 이유다. ① 사용자 70여 명을 둘로 나누면 검정력이 없다(`policy.py` 머리말).
② 인스턴스가 하나고 트래픽을 나눌 프록시가 없다. ③ 클라이언트를 분기시켜야 하는데
FE 는 못 고친다. 그리고 무게(`MATCHURI_TREND_WEIGHT`)로 켜는 것도 답이 아니다 —
`ranking.build` 가 두 정책에 **같은 값**을 내리므로 legacy·taste 가 같이 밀려 인터리빙으로는
트렌드의 효과를 잴 수 없다.

슬롯은 **세 번째 드래프터가 아니라 자리**다. N장에 한 장을 `trend.slot_pick` 이 고르고
그 자리에 넣는다. 나머지 자리는 인터리빙이 그대로 채운다(`policy.pick_many`).

| 결정 | 왜 |
|---|---|
| **N장은 누적으로 센다** (`sess["served"]`) | 배치 크기로 나누면 `limit=5` 클라이언트는 영원히 슬롯을 못 받고, 배치마다 한 장이면 `limit=3` 에서 셋에 하나가 트렌드가 된다 |
| **자리는 씨앗 고정 난수** (사용자·배치) | 늘 마지막 칸이면 위치 편향이 트렌드 성적에 얹힌다. `_first_drafter` 와 같은 원리 |
| **후보는 z > 0 뿐** | 슬롯은 '요즘 뜨는 가게' 자리다. 오르는 가게가 없으면 비우고 두 정책이 채운다 — 채워야 하는 자리가 아니다 |
| **상위 10곳 중 난수** (`SLOT_TOP_N`) | 1위만 뽑으면 모든 사용자가 같은 가게를 받아 7절의 집중도가 바로 튄다. 재려는 것은 "1위 가게" 가 아니라 "트렌드가 고른 카드" 의 like 율이다 |
| **태그 계층을 z 보다 앞에** | `ranking.tiers` 와 같다. 사용자가 고른 태그를 더 가진 가게가 먼저 — 슬롯도 필터 규칙 밖에 있지 않다 |
| **먼저 뽑고 양쪽에 알린다** | 두 정책이 드래프트하기 전에 자리를 잡아야 중복이 없고, '같은 업종 3연속 금지' 가 실제 화면을 본다 |
| **피드백은 두 정책이 똑같이 배운다** | `record` 는 누가 뽑았는지 묻지 않는다. 슬롯 카드의 like 도 `m`·`v` 에 들어가고, 재생 계약은 그대로다(트렌드 값 자체는 여전히 학습 밖) |
| **판정의 상대는 legacy+taste 합산** | 슬롯 카드가 밀어낸 자리는 어느 한 정책의 자리가 아니라 인터리빙의 자리다. `outcome_stats["slot"]` 에 따로 낸다 — 기존 `verdict`(legacy 대 taste)는 건드리지 않는다 |

라벨 `trend` 는 `outcome_stats`·`survey_stats`·`exposure.concentration` 에 셋째 행으로
나온다. 집중도는 슬롯이 쏠림을 만드는지가 곧 질문이므로 **따로** 잰다.

켜는 순서는 `ASSESSMENT-recsys.md` 4.5 절 그대로다 — 시점 정합 백테스트가 먼저고,
집중도 기준선을 적은 뒤 `MATCHURI_TREND_EVERY=10` 으로 시작한다(10장에 1장).

## 10. 다음 후보 (아직 결정 전)

이 작업을 하면서 같이 잰 것들이다. 트렌드보다 값어치가 큰 것도 있다.

### 취향 모델이 굳는다 — 망각 계수

`_logistic_step` 의 `v` 는 **단조 감소만 한다**. 실측:

```
스와이프    v      한 걸음    취향을 0.5 바꾸는 데 필요한 스와이프
     1   0.9145   0.4572                 1
   100   0.0531   0.0265                19
   300   0.0157   0.0078                64
   600   0.0073   0.0037               137
```

600번 스와이프한 사용자는 한 성분을 0.5 움직이는 데 **137번의 일관된 스와이프**가
필요하다. 사전값이 `m[menu]=0.24` 수준인 걸 감안하면 사실상 동결이다.

해법은 망각 계수다: `1/v ← λ·(1/v) + p(1−p)x²`. **재생을 깨지 않는다** — 단
감쇠를 **직전 이벤트와의 간격**(로그의 `at` 에서 읽는다)으로 해야 하고 '지금으로부터
경과' 로 하면 시계의 함수가 되어 깨진다. `ctx` 로깅도 필요 없다.

### 가장 큰 구멍은 트렌드가 아니라 가격이다

```
legacy  x = [절편, 품질, 리뷰수, 업종 11개, 가격대 5개]
taste   z = [인기, 평판, 공방문, 메뉴, 분위기, 리뷰, 사진, 기피]   ← 가격·업종 없음
```

신 정책은 가격을 `menu` 유사도를 통해 간접적으로만 본다. 가격 데이터는 1,813곳
(64.9%)에 있고 중앙가 4분위가 7,900 / 13,000 / 21,000원이다.

축은 **절대 가격이 아니라 "내 like 들의 가격대와 얼마나 가까운가"** 여야 한다 —
가격 선호는 단조가 아니라서(싼 것·비싼 것·중간대 선호가 다 있다) 절대값을 축으로
쓰면 `m[price]` 부호 하나로 표현할 수 없다.

### 그 외

| 후보 | 커버리지 | 성분/보정층 | 메모 |
|---|---|---|---|
| **지금 영업하나** | 87.4% | 보정층 (시계의 함수) | 구현 최소·체감 최대. 닫힌 집 추천은 죽은 카드다 |
| **리뷰 태그** | 78.4% | 성분 | `{가성비 1104, 친절 842, 분위기 652, 맛 639 …}`. 사장님이 쓴 소개글보다 깨끗하다. ⚠️ `친절`(842)/`친절한`(708) 분리 — 정규화 사전 선행 |
| 시간대·요일 | — | 보정층 | 개인화하면 축이 8×시간대로 불어난다. 당분간 전역 계수 |
| 지하철 거리 | 100% | 보정층 | 기존 거리와 중복 확인부터 |
| 내부 행동 점수 | — | 보정층 | 가게당 1.5회뿐. 설문 데이터 뒤 |

**새 성분은 넣기 전에 `corr(새 성분, 기존 성분)` 을 먼저 재야 한다.** 이 저장소는
`review`(인기와 +0.67)와 `food`(상위 20장 정확도 부족)를 ablation 에서 죽인 전력이
있고 둘 다 지금 사전값 0 으로 자리만 남아 있다. 가격은 `menu` 와, 리뷰 태그는
`text` 와 겹칠 위험이 있다.

## 11. 자주 나온 오해

**"가게 특성이 사람마다 바뀌는 것 아닌가?"** — 아니다. `sim_menu`(1629×1629)·
리뷰 임베딩(8282×1024)·`pop`·`quality` 는 전부 고정이고 `.npy` 로 저장돼 있다.
사람마다 다른 것은 `z` 인데, 그건 가게 특성이 아니라 **고정 행렬에서 그 사람의
like 줄만 뽑아 요약한 값**이다. 행렬은 그대로고 어느 줄을 읽느냐만 다르다.

**"그럼 1024차원 임베딩을 직접 쓰면 되지 않나?"** — 측정 문제가 아니라 산수 문제다.
가게 벡터가 1024차원이면 사용자 벡터도 1024차원이어야 하는데, 스와이프 20~30번으로
1024개 숫자를 정할 수 없다. `z` 는 **차원 축소 장치**다 — 1024차원을 "내 like 들과
얼마나 닮았나" 한 숫자로 접어서 사용자가 배울 숫자를 1024개 → 1개로 줄인다.
그래서 8성분이면 스와이프 20~30번으로도 의미 있게 움직인다.

**"그냥 like 한 가게들의 평균을 사용자 벡터로 쓰면?"** — 평균은 **실제로 존재하지
않는 취향**을 가리킨다. 김밥천국(5천원)과 오마카세(15만원)를 좋아한 사람의 평균은
7만5천원짜리 유령 가게다. 그래서 집계가 `max`·`lse`(부드러운 max)다 — "내가 좋아한
것 중 **하나라도** 닮았으면" 이라야 취향의 갈래가 살아남는다. 여섯 축 중 넷이
max 계열인 것은 의도적이다.

## 12. 주 신호를 리뷰에서 검색으로 옮겼다 — 메뉴 키워드와 계절 선행 (2026-09-18)

"네이버 트렌드 기반으로 하자, 거기에 계절과 음식 트렌드가 다 들어 있다" 가 출발이었다.
맞는 말이었고, 숫자가 그걸 확인해 줬다.

### 12.1 왜 리뷰가 주 신호가 못 되나

`inflow`(리뷰 증가율)는 근거가 강했지만(TREND-EVIDENCE 1절) **표본이 없다.** 원본을 다시 세니
추천 풀 1,629곳의 최근 90일 리뷰가 **중앙값 1건**, 0건인 곳이 46% 다(180일 창도 중앙값 1).
리뷰가 33,300건 전부 카카오이고 가게당 30~40건에서 잘린 탓이다. 같은 가게의 네이버 방문자
리뷰는 카카오의 **약 26배**(326곳 매칭, 중앙값)라 그걸 붙이면 풀리지만, 그건 크롤러 작업이고
TLS 흉내·IP 제한이 걸린 수동 수집이다. 검색 트렌드는 이미 있고, 하루 단위로 545일 이상이다.

### 12.2 업종 항은 계절을 지운 값이었다

`fetch_trend_category.py` 의 기본 비교 창이 `yoy`(전년동기)다. 냉면이 7월에 8.6배 오르는 건
작년 7월에도 올랐으니 yoy 에서는 0 근처다. 즉 **가장 근거가 강한 신호(계절, TREND-EVIDENCE 2절)를
스스로 없애고** 있었다. 그래서 넷을 따로 굽는다.

| 키 | 정의 | 잡는 것 |
|---|---|---|
| `yoy` → 서버의 `fad` | log(최근 180일 / 작년 같은 180일) | 유행 — 작년보다 더 뜨나 |
| `seq` | log(최근 180일 / 직전 180일) | 최근 방향 (계절 포함, 아직 안 쓴다) |
| `season` | log(작년 **다음 4주** / 작년 **지난 4주**) | 계절 선행 — 이제 오르는 철인가 |
| `in_season` | log(작년 다음 4주 / 작년 1년) | 지금이 그것의 철인가 (아직 안 쓴다) |

`season` 은 계절 나이브(seasonal naive)다 — 반복되는 계절에서는 작년 이 시점의 다음 4주가 올해의
예측값이고, 시계열 수십~수천 개 규모에서 이게 기준선이다. 딥러닝은 이걸 홀드아웃에서 이길 때만
들인다. 작년 정렬은 요일을 맞추려고 364일. 9월 중순 기준 떡·한과 +0.48, 감자탕 +0.28, 국밥
+0.25 가 오르고 냉면 −0.71, 아이스크림 −0.28, 샐러드 −0.24 가 내린다.

### 12.3 가게를 가르는 것은 메뉴다

데이터랩은 개별 상호를 못 잰다(5.3절). 업종 71개 값을 가게 1,629곳에 펴면 같은 국밥집 20곳이
동점이라 슬롯의 "상위 10곳" 을 뽑을 수 없다. 메뉴명은 풀 전부에 있고 상위 1,000개가 가게의 79%
에 걸린다 → `fetch_trend_menu.py` (997콜, 월 한도의 2%). 가게 점수는 서버(`recsys/trend.py`)가
그 가게 키워드들의 **상위 3개 평균**을 업종 값과 **부분 수축**으로 합친다:

    store = (n · 메뉴 상위3 평균 + 1 · 업종) / (n + 1)     n = 쓸 수 있는 키워드 수(≤3)

메뉴가 없는 가게(21%)는 업종 값을, 많은 가게는 자기 값을 받는다. `BAYES_C` 와 같은 원리다.

| 결정 | 왜 |
|---|---|
| **밀도 5 미만 키워드는 버린다** | 검색량이 거의 없는 키워드는 며칠 스파이크로 season ±2 가 나온다(본죽장조림버터비빔밥 +2.87). 5 로 거르면 \|season\|>1 인 것이 콩국수·중국냉면·열무냉면(내림)과 유자차·모듬전·생굴(오름)만 남는다 — 전부 진짜 철 |
| **상위 3 평균, 최댓값 아님** | 최댓값이면 메뉴 30개짜리 카페가 늘 이기고, 전체 평균이면 늘 0 이다 |
| **슬롯 후보는 브랜드마다 한 곳** | 같은 체인은 메뉴가 같아 점수도 같다 — 실측에서 본죽 4곳이 상위 10 중 4곳이었다. `brand_key.json` 으로 접는다 |
| **무게: season 1.0 · fad 0.5 · inflow 0.5 · rating 0.3** | 검색이 주, 리뷰는 같은 업종·메뉴 안에서 가게를 가르는 보조. **손으로 둔 첫 추정값**이고 시점 정합 백테스트와 슬롯 like 율이 고친다 |
| **검색 항은 리뷰 0건 가게에도** | 우주가 리뷰가 아니라 가게 전체다. 풀 1,629곳 전부 season·fad 값을 받는다(실측) |

실데이터(2026-09-18): 오르는 쪽 본죽(죽·추석), 잇테이블(유자차·홍차), 끝장(모듬전), 한우본
(설렁탕·국밥). 내리는 쪽 스테이크·포케·파스타. 풀 전체 점수 계산 2ms.

### 12.4 시점 정합 백테스트 — 리뷰 라벨로는 판정이 안 된다 (2026-09-18)

`analysis/trend_backtest.py`. 선호 로그는 운영 서버에만 있어 라벨을 **리뷰 유입**으로 잡았다.
시점 t(매달 1일, 2025-08~2026-08 13개)마다 t 까지의 자료로 `season`·`fad`·`inflow` 를 만들고
(서버와 같은 정의·같은 수축), (t, t+28일] 의 리뷰로 라벨을 세 가지 냈다.

| 라벨 | 정의 | season | fad | inflow |
|---|---|---|---|---|
| A | 다음 4주 − 지난 4주 부호 | AUC 0.507 | 0.500 | **0.364** |
| B | 다음 4주 > 자기 180일 속도 | 0.493 | 0.501 | 0.495 |
| C | 업종 계절 대 업종 리뷰 점유율 변화 ρ (업종 42개) | −0.003 | — | — |

전부 동전이다. `inflow` 의 A 0.364 는 신호가 아니라 **평균 회귀**다 — 지난 4주에 몰린 가게는
다음 4주가 줄기 마련이라 최근에 늘어난 가게가 자동으로 음수가 된다.

**그런데 라벨의 천장이 이렇다.** 신호 없이 리뷰 수만으로 낼 수 있는 가장 좋은 예측기:

```
지난 4주 수 → 다음 4주 수               ρ +0.28   (인기 지속)
지난 4주 변화 → 다음 4주 변화           ρ −0.46   (라벨 A 는 평균 회귀가 지배)
'직전 4주가 자기 속도 초과' → 라벨 B    AUC 0.56  ← 라벨 B 의 실질 천장
다음 4주 리뷰 0건인 가게 75% · 가게당 평균 0.4건
```

가게당 월 0.4건이면 라벨의 대부분이 포아송 잡음이다. 천장이 0.56 인 자리에서 0.49~0.51 은
"신호가 없다" 가 아니라 **"이 라벨로는 못 잰다"** 다. 12.1 에서 리뷰가 주 신호가 못 되는 이유와
같은 이유로 리뷰는 **검증 라벨도 못 된다.** 결론 셋:

1. 무게(season 1.0 · fad 0.5 · inflow 0.5)는 **여전히 가설**이다. 이 데이터로는 올릴 수도 내릴 수도 없다.
2. 검색 계절이 역삼동 행동과 같이 움직이는지의 최종 판단은 **슬롯의 like 율**이다(8.1절). 그게
   원래 슬롯을 만든 이유이기도 하다.
3. like 기반 as-of 백테스트는 가능하다 — 운영 `state/preferences.jsonl`(스와이프 2,800건)과
   `exposures.jsonl` 을 로컬로 받아오면 같은 스크립트에 라벨만 바꿔 끼운다. 카드 단위 라벨이라
   리뷰보다 두껍다. 서버에서 받아오는 것은 사람이 해야 한다(scp).

### 12.5 아직 안 한 것

- like 기반 as-of 백테스트 (위 3번) — 운영 state 사본이 필요하다
- 전국 검색량이 역삼동 직장인 점심 상권과 같이 움직이는지는 슬롯 like 율이 답한다
- `seq`·`in_season` 은 굽지만 안 쓴다. like 백테스트에서 값이 있으면 출처로 올린다
- 네이버 리뷰 수집 — 리뷰 신호(와 리뷰 라벨)를 두껍게 하는 가장 큰 한 수. 크롤러 일이라 따로

## 13. 반영 계획 — 측정 → 전역 반영 → 개인별 가중치 (2026-09-21)

트렌드는 지금 **점수에 0 으로** 들어가고(`MATCHURI_TREND_WEIGHT` 미설정 = 0.0) **슬롯으로
재고 있다**(`MATCHURI_TREND_EVERY=10`, 10장에 1장, `policy="trend"` 라벨). 순서를 이렇게
잡은 이유는 4절·9절과 같다 — 무게로 켜면 두 정책이 같이 밀려 인터리빙으로 효과를 못 잰다.
켜기 전에 슬롯으로 결론을 낸다.

### 무엇이 들어가나 — 네이버 + 우리 로그, 역할이 다르다

    점수(trend.py)   season · fad  ← 네이버 데이터랩(업종 71 + 메뉴 키워드 1,000, 12절)   주 신호
                     inflow · rating ← 우리 리뷰                                           보조
    측정             슬롯 라벨별 like 율 · 설문(방문 여부)  ← 우리 행동 로그                 판정 근거
    3단계 재료       사람별 트렌드 카드 like 율             ← 우리 행동 로그                 개인 가중치

행동 로그는 점수에 직접 들어가지 않는다. **어느 쪽 트렌드가 먹히는지를 재는 데** 쓰고,
③에서 사람마다 무게를 정하는 재료가 된다.

### ① 측정 (지금 — 사실상 2026-09-21 시작)

슬롯 켜기는 09-18 저녁에 머지됐지만 Jenkinsfile 이 컴파일되지 않아 **사흘 동안 배포가 없었다**
(`0f4d854`). 실제로 켜진 것은 09-21 10:20. 그날 12:07 성적:

    legacy       평가 3,825   like 65.0%  [63.5, 66.5]
    taste        평가 3,838   like 67.3%  [65.8, 68.8]
    trend(슬롯)  평가    48   like 60.4%  [46.3, 73.0]   ← 아직 모른다
    interleaved  평가 7,663   like 66.2%  [65.1, 67.2]

**판정 조건**: trend 의 95% 구간이 interleaved 와 갈릴 것(어느 쪽으로든). ±5pp 면 평가
350건, 지금 속도(2시간 48건)로 하루 이틀. 안전하게 **1,000건(약 일주일)** 을 본다 —
요일 효과(점심 상권)가 한 바퀴 돌아야 한다.

같은 기간에 **소스별로 갈라 잰다.** `df25db7` 이 카드마다 뽑힌 이유의 숫자(attribution:
개인화·평판·상황·트렌드)를 준다. 트렌드 슬롯 카드를 "계절이 뽑았나 / 유행이 뽑았나 /
리뷰 증가율이 뽑았나" 로 나눠 like 율을 내면 `w_season`·`w_fad`·`w_inflow` 의 상대 무게가
여기서 나온다. 12.4 의 리뷰 라벨 백테스트가 못 한 판정이다 — like 라벨은 할 수 있다.

같이 적어 둘 것: 켜기 **전**의 노출 집중도(지니·`never_shown`·상위N,
`/admin/api/trend/concentration`). 7절 — 켠 뒤에는 기준선을 만들 수 없다.

### ② 전역 반영 — 작게, 되돌릴 수 있게

trend ≥ interleaved 로 갈리면 둘 중 하나. **슬롯 빈도를 올린다**(10 → 5장에 1장) 또는
**보정층 무게를 켠다**(`MATCHURI_TREND_WEIGHT=0.3~0.5`). 슬롯 쪽이 먼저다 — 라벨이 남아
계속 잴 수 있다. 무게를 켜면 그 뒤로는 인터리빙으로 못 잰다.

켠 뒤 일주일 안에 ①의 기준선과 집중도를 견준다. 지니가 오르고 `never_shown` 이 늘면
쏠림이다 — 되돌린다(7.2절 읽는 법). **갈리지 않으면 켜지 않는다.** 표본이 더 필요하면
슬롯을 더 돌릴 뿐이다.

### ③ 개인별 트렌드 가중치

사람마다 트렌드 카드에 대한 like 율을 자기 전체 like 율과 견줘 **친화도**를 낸다.
표본이 적은 사람은 전역 값으로 수축한다 — 평점의 `BAYES_C` 와 같은 원리(작은 표본은
전역으로, 큰 표본은 자기 값으로).

    w_user = w_global × 친화도_user
    친화도_user = (like_trend_u + k · p_global) / (n_trend_u + k)  ÷  p_global   (k 는 수축 상수)

**`m` 에 넣지 않는다.** 트렌드 값은 시계의 함수라 `m` 에 들어가면 재생 결정성이
깨진다(4절, `tests/test_replay.py`). 친화도는 **로그의 함수**다 — 좋아요/싫어요는
`preferences.jsonl` 에, 어느 카드가 trend 라벨이었는지는 `exposures.jsonl` 에 있다. 재생하면
같은 값이 나오므로 보정층에 산다. `app/ranking.py` 의 거리 보너스와 같은 자리다.

사람별 표본이 몇십 건씩 있어야 뜻이 있다. ①·②가 몇 주 돈 뒤의 일이다.

### 하지 않는 것

- **지역(역삼동) 트렌드.** 우리 리뷰로 업종 계절을 재 보니 진폭이 표본 크기와 반대로
  움직였다(가게 200곳+ 1.42배 대 100곳- 2.68배, `TREND-EVIDENCE.md` 2.4). 잡음이다.
  전국 계절·유행 + 우리 리뷰 보조로 간다.
- **고정 전역 가산항.** 모두를 같은 방향으로 밀어 취향을 덮는다. 슬롯(자리) 또는
  개인별 무게(③)만 쓴다.
- **판정 전에 무게 켜기.** 켜는 순간 측정이 끝난다.
