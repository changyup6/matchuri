## 1. 무엇을 어떻게 바꿨나

한 문장으로: **업종·가격대 위의 로지스틱을 걷어내고, 가게를 여러 벡터로 표현한
성분 점수 8개와 그 위의 사용자별 가중치로 추천을 만든다.** 구 정책은 지우지 않고
같은 화면에서 나란히 돌린다.

### 1.1 가게 표현 — 다중 벡터

| modality | 표현 | 근거 |
|---|---|---|
| 메뉴 | 대표 메뉴 ≤ 8개를 **집합으로 유지**, MaxSim (late interaction) | Step 1 |
| 가게 요약문 | `ai_title + ai_summary + tags` 문장 1개의 코사인 | Step 2 |
| 리뷰 | 고른 리뷰 ≤ 12개의 **평균 벡터** 코사인 (집합 아님 — 이유는 2.4) | Step 2 |
| 음식 사진 | 음식 사진 ≤ 4장 CLIP 벡터의 **평균 벡터** 코사인 | Step 3b |
| 공방문 | item-item 공방문 코사인 (리뷰 21,553명, 제외 없음) | Step 1.5 |

임베딩은 `BAAI/bge-m3`(텍스트 1,024차원)와 `openai/clip-vit-base-patch32`(이미지
512차원). 어느 modality 도 없는 가게는 **NaN** 으로 둔다 — 0 으로 채우면 '아무와도
안 닮은 가게' 가 되어 구조적으로 밀려나는데 실제로는 '모른다' 이기 때문이다.

### 1.2 성분 점수 8개와 사용자별 가중치

후보 i, 사용자의 like 집합 L · dislike 집합 D 에 대해 (전부 그 사용자의 **후보 안**
z-정규화, NaN 은 z 정규화 뒤 0 = 후보 평균):

```
z_pop     log1p(리뷰 수)                          관심 백본       Step 0
z_q       베이지안 평균 평점                       만족 가드       Step 0
z_cf      Σ_{h∈L} 공방문코사인(h, i)               공방문          Step 1.5
z_menu    max_{h∈L} 메뉴 MaxSim(h, i)             메뉴 집합       Step 1
z_text    lse(τ=0.1)_{h∈L} 요약문 코사인           가게 요약문     Step 2
z_review  mean_{h∈L} 리뷰 평균벡터 코사인           리뷰            Step 2  (사전값 0)
z_food    lse(τ=0.1)_{h∈L} 음식사진 코사인         음식 사진       Step 3b (사전값 0)
z_neg     max_{h∈D} (메뉴·요약문·리뷰 유사도의 평균) 기피            오프라인 근거 없음

점수 = w·z + Thompson(σ×0.4)
콜드스타트(like 0개) = z_pop + 0.5·z_q (+ dislike 가 있으면 w_neg·z_neg)
```

**w 는 사용자마다 온라인으로 배운다.** 새 피드백이 오면 반대 라벨의 최근 5건과 짝지어
`σ(w·(z_like − z_dislike))` 위에서 로지스틱 한 걸음 + 라플라스 근사 대각 가우시안
갱신을 한다. 점별(pointwise) 갱신은 '좋아요를 많이 받는 성분' 을 배우는데 그건 인기의
다른 이름이고, 쌍대는 '이 사람이 A 보다 B 를 고른 이유' 를 배운다 — Step 2 에서 λ 를
격자 탐욕 대신 쌍대 로지스틱으로 학습하자 16칸 중 3칸 → **9칸**으로 뛰었다. 반대
라벨이 아직 없으면 점별로 대신한다. 학습 파라미터는 사람당 **8개**뿐이라 스와이프
수십 건으로 움직인다.

사전값은 백테스트가 폴드 밖에서 학습한 λ 다(`data/kakao/serving/prior.json`,
`source: step3d-clip`): `pop 1.0 · quality 0.05 · cf 0.46 · menu 0.25 · text 0.40 ·
neg −0.25`, 사전 sd 전부 0.5. **`review` 와 `food` 는 사전 평균 0** 으로 실린다
(4절과 2.6 참고).

### 1.3 팀-드래프트 인터리빙 — shadow 가 아니다

```
MATCHURI_POLICY = interleave (기본) | legacy | taste
```

사용자가 적어 A/B 는 검정력이 없다. shadow(구 정책으로 주고 신 정책 점수는 로그만)는
신 정책이 **실제로 보여줬을 카드**에 대한 반응을 영영 못 본다. 그래서 10장 배치를 두
정책이 **한 장씩 번갈아** 뽑아 섞고 카드마다 정책 태그를 남긴다. 먼저 뽑는 정책은
(사용자 id + 배치 번호) 씨앗 난수로 정해 위치 편향을 상쇄하고 재현 가능하게 했다.
어느 쪽이 뽑았든 **두 정책이 모든 피드백을 받는다** — 그래야 성적을 '같은 이력을 본
두 모델' 로 비교할 수 있다. 노출은 `state/exposures.jsonl` 에 남고
`GET /admin/api/policies` 가 정책별 like 율과 **Wilson 95% 구간**, 그리고 '구간이
겹치면 아직 모른다' 는 판정을 준다.

### 1.4 서빙 산출물 — 서버는 numpy 만 쓴다

서버 이미지에 torch 도 1,024차원 임베딩도 들어가지 않는다. 들어가는 것은 후보 풀
2,216곳짜리 행렬 몇 장이고, `analysis/build_serving.py` 가 오프라인에서 만든다.

| 파일 | 크기 | 내용 |
|---|---|---|
| `pool_ids.json` | 29KB | 후보 풀 id — 서버 `swipe._build_pool` 과 **같은 순서**(빌드가 확인한다) |
| `sim_menu.npy` / `sim_text.npy` / `sim_review.npy` / `sim_food.npy` / `cooc.npy` | 각 9.8MB | float16 2,216², modality 없는 가게는 NaN |
| `review_vecs.npy` · `review_pairs.json` | 22.9MB | 설명용 리뷰 벡터(가게당 ≤ 6)와 스니펫 |
| `brand_key.json` · `prior.json` · `manifest.json` | 74KB | 브랜드 키, 사전값, 입력·출력 sha256 |
| **합계** | **72.1MB** | 예산 80MB |

프로덕션 빌드는 **평가 사용자를 제외하지 않는다** — 누수 규칙은 '정답을 미리 보지
않았다' 를 증명하기 위한 것이고 프로덕션에는 정답이 없다. 그 결과 공방문 비영 쌍이
15,321(0.62%) → **64,752(2.64%)** 로 늘었다. 디스크에서는 float16 이지만 켤 때
float32 로 펴서 올린다(+98MB 상주) — 호출마다 변환하면 |L|=300 에서 modality 당
3.5ms 가 들고, 켤 때 한 번이면 0.6ms 다.

**산출물이 없으면 경고 한 줄을 남기고 legacy 로만 돈다. 죽지 않는다.**

### 1.5 관리자 화면

`app/static/admin.html` 한 장(빌드 없음, CDN·웹폰트 0개). 맨 위가 **정책 실험 패널**
— 정책별 노출·좋아요·별로·무응답과 선호율을 Wilson 95% 구간 막대로 그리고 판정을
한국어 한 줄로 적는다(`아직 판정 불가 — 구간이 겹침` / `taste 우세`). **like 율
숫자보다 구간 겹침을 먼저 읽게** 하는 것이 이 패널의 목적이다. 아래는 사용자별로 두
모델을 나란히 본 것 — 성분 가중치 `w ± 사후 sd` 수염 막대, 취향 프로토타입 ≤ 5개,
이력(막대 높이 = 쌍대 갱신에 쓴 쌍 수), 다음 카드의 성분 기여 `w·z` 분해.

**성분 이름·개수·순서는 전부 API 가 준다.** 화면이 성분을 세지도 이름 붙이지도 않고
`tests/test_admin_ui.py` 가 그 계약을 잠근다. 8번째 성분(`food`)을 얹을 때
`admin.html` 을 **한 줄도 고치지 않았다** — 그 계약의 첫 실증이다.

## 2. 왜 필요한가 — 근거 사슬 (Step 0 → Step 3c)

### 2.0 문제

현재 서버의 개인화는 `cat2` 업종 10개 + 메뉴 중앙가 4분위 위의 로지스틱 재가중이다.
**업종 카테고리는 취향을 담지 못한다** — 곱창전골↔모츠나베, 냉면↔메밀소바는 업종이
다르지만 취향은 같다. 2026-09-08 의 시도(메뉴 기반 수작업 8축)도 결국 또 다른 정형
분류였고 품질순 대비 **+0.5%p, CI 는 0 을 포함**했다.

### 2.1 Step 0 — 잣대부터 만들었다 (`step0-baselines.md`)

후보 풀 2,216곳, 평가 사용자 227명. 사용자별 시간 분할(미래 = 최근 30%), 이력
N ∈ {3,5,10,20}, 사용자 단위 **paired bootstrap 95% CI(2,000회, seed 고정)**.
CI 가 0 을 포함하면 '우위 미확정' 이라고 쓴다 — 작은 양수를 근거로 삼지 않는다.

- 과제 P(다음 방문): `popularity` AUC **.676** 이 압도. `quality` 는 .502(무작위),
  **현재 서버 모델 `current` 는 .505 → .520** — 학습은 되지만 미약하다.
- 과제 R(만족): `quality` **.704**, `popularity` .482(무작위 이하). **두 과제는 반대
  방향**이다.
- `popularity` 의 P 우위에는 구조적 이점이 섞여 있다(정답을 카카오 리뷰에서 뽑았으니
  리뷰 많은 가게가 정답이 될 확률이 높다). 그래서 **인기 매칭 AUC(`auc_pm`)** 를
  더했다 — 양성마다 같은 리뷰수 십분위의 음성만 상대로 순위를 재는 지표다. **취향
  신호가 인기와 독립적으로 존재하는지**를 재는 것이 이 프로젝트의 진짜 질문이다.
- N=10 을 다 채운 사용자 108명, N=20 은 **31명** — N ≤ 5 가 제품의 주 구간이다.

### 2.2 Step 1 — 메뉴 다중 벡터, 그리고 첫 음성 결과 (`step1-menu.md`)

메뉴 MaxSim 단독 P AUC .528(popularity .676 에 크게 못 미침), `auc_pm` .535 vs .525
(CI 0 포함), Hit@10 은 .07~.09 로 popularity .044 를 넘는다 — **상위는 맞히고 꼬리는
못 맞힌다**는 모양이 여기서 처음 나온다.

**bge-m3 는 짧은 메뉴명에서 의미가 아니라 글자를 본다.** 곱창전골↔모츠나베 0.222,
초밥↔지라시스시 0.251인데 **메밀소바↔멜론소다는 0.688** 이다. 최근접 5곳 중 업종이
다른 비율 26%(무작위 82%) — 업종을 넘지 못하고 업종 안을 쪼갠다.

### 2.3 Step 1.5 — 계약을 고치고 CF 를 붙였다 (`step1_5-visit-cf.md`)

- **방문 = 관심.** 제품의 like 는 '가보고 싶다'(방문 전 관심)이고 별점은 방문 후
  만족이라 직교한다. Step 1 에서 dislike 가중이 해로웠던 것이 그 방증이다. 이력 해석을
  `visit` 으로 바꾸자 `current` 의 P AUC 가 전 N 에서 CI 로 올랐고(N=20 .5201 →
  .5540) 과제 R 은 반대로 내렸다 — 예상한 방향이다.
- **협업 필터가 처음으로 `popularity` 를 일관되게 넘겼다.** `hybrid_pop_cf_item_sum`
  AUC +.0060(N=3) → +.0150(N=20), 16칸 중 14칸 CI 통과, Hit@10 .106(popularity 의
  2.4배). CF 는 극도로 희소한데도(비영 쌍 0.62%, 그 중 98%가 공방문자 1명) 신호가 있다.
- **브랜드 억제는 지표를 하나도 안 바꾼다.** 상위 10 안의 '이력과 같은 브랜드' 가게가
  사용자당 1.53곳 → 0.02곳으로 걷히는데도 전 지표·전 N 에서 CI 가 0 을 포함한다.
  그래서 점수가 아니라 **노출 규칙**(같은 브랜드 연속 금지)으로만 쓴다.

### 2.4 Step 2 — 요약문·리뷰, 그리고 **난수 대조군** (`step2-text-reviews.md`)

이 Step 의 가장 중요한 결과는 새 성분이 아니라 **음성 결과**다.

- **난수 벡터 대조군이 진짜 벡터를 이겼다.** 리뷰 MaxSim 에서 개수 구조만 남기고
  벡터를 난수로 바꾸면 AUC **.6171** 로 진짜(.6153)보다 **높다.** `max_{b∈B}` 가
  |B| 에 단조증가하는데 리뷰 수가 곧 인기이기 때문이다(쓴 벡터 수 ↔ log1p(리뷰 수)
  상관 **0.88**). 인기를 통제하면 뒤집힌다(대조군 auc_pm .482 vs 진짜 .542).
  → **집합형 표현의 AUC 는 내용의 증거가 아니다.** 이후 모든 집합형 modality 에
  난수 대조군을 의무로 붙였다.
- **PLAN 원칙 1번("집합으로 유지한다")이 리뷰에서 뒤집혔다.** 단일 평균 벡터가
  MaxSim 을 전 지표에서 이긴다(NDCG@20 .0168 vs .0110, AUC .6475 vs .6153). 한 가게의
  리뷰 12개는 대체로 같은 말을 다르게 한 것이고, 평균 벡터는 **개수 편향이 없다.**
  → 리뷰는 점수에서 단일 벡터로 쓰고 MaxSim 은 **설명 전용**으로 남겼다.
- **구성요소 블렌드가 막대를 넘었다.** `z_pop + Σ λ_m z_m` 의 λ 를 바깥 5-fold 쌍대
  로지스틱으로 학습하니 16칸 중 **9칸에서 CI 로 이기고 진 칸은 0** (AUC +.0100/+.0101/
  +.0115, auc_pm 전 N +.030~+.036). 격자 탐욕 선택은 같은 성분으로 3칸에 그친다 —
  **λ 를 무엇으로 고르느냐가 어떤 성분을 쓰느냐만큼 중요하다.**
- 가게 요약문은 커버리지 99.4%, N=5 단독 auc_pm **.5596** 으로 메뉴(.5434)보다 높다.

### 2.5 메뉴명 임베딩 모델 프로브 — 전부 실패 (`probe-menu-embeddings.md`)

'모델을 바꾸면 되지 않나' 를 먼저 닫았다. bge-m3 · KURE-v1 ·
multilingual-e5-large-instruct · Qwen3-Embedding-0.6B · arctic-embed-l-v2 + 지시문·
접두어 변형 **10종 전부**가 "취향 유사 쌍 vs 글자만 닮은 미끼 쌍" AUC **< 0.5** 였다.
모츠나베를 곱창전골 근처에 두는 모델은 없다(최선 20,449 / 23,198위). 글자가 안 겹치는
56방향의 중앙값 순위는 bge-m3 7,350 이 Qwen3 11,467 보다 낫다.
→ **모델 교체는 답이 아니다.** 4~10글자 고유명사에는 재료·조리법·맛이 없고, 의미는
리뷰·요약문 같은 **자연어 설명 레이어**에서 와야 한다.

### 2.6 Step 3a·3b·3c — 무엇을 켜고 무엇을 껐나

**Step 3a** (`step3a-final-spec.md`) — 메뉴는 난수 대조군을 넘는다(AUC .5350 vs
.4931, 16칸 중 10칸 CI 승, 진 칸 0). 리뷰에서 벌어진 역전이 메뉴에는 없는 이유는
**집합 크기 ↔ 인기 상관**이다(메뉴 0.196 vs 리뷰 0.88). 성분 상관을 재니
`review`↔`popularity` **+0.673** — **`review` 는 인기의 다른 이름**이고 그래서 가장 큰
λ 를 받고도 ablation 에서 죽었다. `quality` 는 λ 가 0 이 되지 않아(20폴드 전부 양수)
작은 값으로 남겼다. 서빙 사양이 여기서 나왔다.

**Step 3b** (`step3b-photos.md`) — 사진 9,533장을 CLIP 으로 임베딩하고 음식/공간을
분리해 각각 난수 대조군과 함께 쟀다.

- **음식 사진은 대조군을 넘는다.** `photo_food_max` N=5 AUC .5881 · auc_pm **.5657**,
  대조군 .4838/.4853, 4개 지표 전부 CI 승(ΔAUC +.104 [+.077, +.131]).
  **auc_pm .5657 은 이 프로젝트 콘텐츠 modality 중 최고**다(메뉴 .5434 · 요약문 .5596 ·
  리뷰 .5457). `popularity` 대비 auc_pm 을 전 N 에서 CI 로 넘겼다(+.027~+.041).
- **공간 사진에는 신호가 없다.** `photo_space_mean` AUC .4976 vs 대조군 .4994 —
  **4개 지표 어느 것도 대조군을 못 넘는다.** 최근접 5곳의 업종 교차 60.3%가 높은 것은
  취향이 업종을 넘어서가 아니라 **실내 사진이 업종과 무관하게 서로 닮았기** 때문이다
  (점수가 무작위인 것이 그 증거). → 점수에서 뺐다. 카드 이미지 선택에만 쓴다.

**Step 3c** (`step3d-clip-food-blend.md`) — 음식 사진을 블렌드에 얹었다. 채택 규칙은
**재기 전에** 정했다: (g)=(d)+food 가 (d) 를 CI 로 이긴 칸 ≥ 1 이고 **진 칸 0**.

- **이긴 칸 3(전부 auc_pm, +.0077~+.0100) · 진 칸 1(`ndcg@20` N=20 −.0040
  [−.0080, −.0003]) → 규칙대로 기각.**
- **오르는 지표와 내리는 지표가 다르다.** 오르는 것은 인기를 통제한 랭킹이고
  내리는 것은 **맨 위 20장**이다. 스와이프 제품이 보여 주는 것이 상위 10~20장이므로
  이 방향의 손해가 더 비싸다.
- **`food` 가 죽은 이유는 `review` 와 다르다.** `log1p(리뷰 수)` 와의 상관이
  **+0.140** 뿐이다(`review` 는 +0.673). λ 도 죽지 않았다(폴드 평균 .35~.39, 20폴드
  전부 양수). **중복이라 죽은 것이 아니라 상위를 세우는 정확도가 모자라 죽었다.**
- (d) 재현은 완전하다 — 막대와 (d) 를 포함한 **28개 값의 최대 편차 0.00e+00.**

### 2.7 그래서 `review` 와 `food` 를 **온라인 전용**으로 실었다

둘 다 오프라인 점수 성분에서 빠졌지만, 성분 **자리**는 남기고 사전 평균만 0 으로
싣는다. 처음에는 점수에 아무것도 더하지 않고, 그 사람의 쌍대 피드백만이 0 에서
밀어낼 수 있다. 이것이 '**오프라인이 답하지 못한 질문을 온라인에 넘기는**' 형식이다.

| 성분 | 왜 0 인가 | 인기와의 관계 | 온라인이 답할 질문 |
|---|---|---|---|
| `review` | Step 3a — 가장 큰 λ 를 받고도 ablation 에서 한 칸도 못 넘겼다 | 스피어만 **+0.673** | '인기와 겹친다' 가 **개인** 취향에서도 참인가 |
| `food` | Step 3c — auc_pm 은 세 N 에서 CI 로 이겼지만 `ndcg@20` N=20 에서 져 '진 칸 0' 규칙에 걸렸다 | 스피어만 **+0.140** | 227명 평균의 상위 20장을 못 바꾼 신호가 **한 사람의** 상위 카드는 바꾸는가 |

`food` 를 남긴 근거가 여기 있다. 오프라인이 말한 것은 '인기를 통제하면 이기지만 상위
20장을 바꿀 만큼 정확하지 않다' 이고, **인기와 독립적인 취향 정보를 나른다는 것도 같은
실험이 보여 준 사실**이다(auc_pm .5657 은 이 프로젝트 최고치). 판정이 칸 하나에
걸려 있었으므로 이 결과는 '사진은 아직 아니다' 이지 '사진은 안 된다' 가 아니다.
실제 스모크에서 `review` 는 40 스와이프 만에 0 → 0.205 로 움직였고 "좋아요한 ○○의
리뷰와 닮았어요: '…'" 가 나왔다.

## 4. 남은 제약 (읽는 사람이 반드시 알아야 하는 것)

1. **표본이 작다.** 평가 사용자 227명 중 N=10 을 다 채운 사람은 108명, **N=20 은
   31명**뿐이다. N=20 칸의 CI 는 그 31명 위에서 나온 것이다.
2. **다중비교 보정을 하지 않았다.** Step 3a 는 변종 5 × 지표 4 × N 4 + 제거 시험
   5×5, Step 3c 는 변종 4 × 지표 4 × N 4 + 제거 시험 2 칸을 봤다. 채택 규칙을 **재기
   전에** 정한 것이 유일한 방어이고 충분하지 않다. Step 3c 의 판정은 **칸 하나**에
   걸려 있어 bootstrap 표본을 다시 뽑거나 N 을 하나 빼면 뒤집힐 폭이다.
3. **변종 채택을 테스트 사용자 227명의 지표를 보고 했다.** λ 만 폴드 밖에서 학습했다.
   즉 '어떤 성분 집합을 쓸까' 는 테스트에서 골랐다 — 스윕 승자에 대한 편향이 남아 있다.
4. **효과의 폭이 AUC 0.01 수준이다.** 4절 기준("CI 가 0 을 넘긴 구성만 켠다")은
   충족하지만 **온라인 인터리빙 전에는 제품 효과의 근거가 아니다.** 이 MR 이 켜는 것은
   '더 나은 추천' 이 아니라 **'더 나은지 물을 수 있는 장치'** 다.
5. **`review`·`food` 는 오프라인 근거 없이 온라인 전용으로 실렸다**(사전 평균 0).

   성분을 늘린 만큼 사후 분산이 늦게 좁혀지는 비용도 있다.
6. **`z_food` 의 집계가 오프라인과 다르다.** 블렌드에 얹었던 것은 `photo_food_max`
   이고 서버는 `lse(τ=0.1)` 다(같은 τ 를 쓰는 `z_text` 와 눈금 만드는 방식을 맞췄다).
   사전 평균이 0 이라 오프라인 λ 를 물려받지 않지만, **이 조합을 오프라인에서 잰 적은
   없다**(Step 3c 주의 ⑤ — 집계를 블렌드 위에서 다시 스윕하지 않았다).
