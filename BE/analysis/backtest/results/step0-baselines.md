## 읽는 법과 주의

- **CI 가 0 을 포함하면 우위 미확정이다.** 작은 양수를 근거로 삼지 않는다 (PLAN 1절).
- 과제 P 는 음성이 2천여 곳인 전수 랭킹이라 Hit@10·NDCG@20 의 절댓값이 아주 작다(무작위 기준 Recall@50 = 50/2,216 = 2.3%). 절댓값을 제품 성능으로 읽지 말고 모델 간 **차이**만 본다.
- **`popularity` 에는 구조적 이점이 있다.** 정답(미래 방문)을 카카오 리뷰에서 뽑았으므로 '리뷰가 많은 가게' 는 정답으로 뽑힐 확률 자체가 높다 — 정답의 표본추출 틀과 특성이 같은 양이다. 리뷰 기반 백테스트라면 어디서나 생기는 편향이고 제거할 방법이 없다. 새 모델이 `popularity` 를 넘는지가 진짜 시험이며, `popularity` 를 넘었다는 사실만으로 제품에서 그만큼 좋다고 말하면 안 된다.
- 재방문(같은 사용자·같은 가게 리뷰 2건 이상)은 이 데이터에 **0건**이다. 과거에 간 가게가 미래에 다시 나온 경우도 **0건**이다. 따라서 '미래 유일화·과거 제외' 규칙은 실제로 아무 행도 지우지 않았다.
- '이력에 이미 있으면 미래에서 제외' 의 '이력' 을 **과거 전체**로 읽었다(최근 N 창이 아니라). 정답 집합이 N 에 따라 달라지면 N 간 비교가 성립하지 않기 때문이다. 위 재방문 0건이라 두 해석의 결과는 같다 — N 창으로 읽어도 제외 건수는 N ∈ {3, 5, 10, 20} 전부 0건이다.
- 과제 R 은 like 매핑과 경계가 다르다 — 여기서는 rating 3 이 **음성**이다 (PLAN 이 그렇게 정의했다). 이력 매핑에서 3 은 중립이다.
- 이력이 짧은 사용자는 N 을 다 채우지 못한다. N 을 키운 결과를 볼 때는 위의 '다 채운 사용자 수' 를 같이 본다 — N=20 은 대부분 실제로 20 이 아니다.

## 누수 규칙

- `quality` 는 서버가 쓰는 카카오 집계(`review_avg`·`review_count`)다. 평가 사용자 리뷰가 이 집계에 섞여 있다. **크기를 직접 쟀다**: 정답 가게 1,342쌍에 대해 그 사용자의 별점 1건을 빼면 베이지안 품질이 평균 0.0311 (95분위 0.1000) 움직인다. 풀 전체 품질의 표준편차 0.4607 의 6.8% 다(정답 가게의 리뷰 수 중앙값 26건). PLAN 의 '미미함' 은 이 수치로 뒷받침된다.
- 반면 `quality_crawled`(누수 제거)는 `quality_crawled_all`(미제거)보다 과제 R 에서 뚜렷이 낮다. 크롤링 코퍼스는 가게당 리뷰가 훨씬 적어(전체 2,216곳에 리뷰 3만여 건) 본인 리뷰 1건의 비중이 크기 때문이고, 표본이 12% 줄어든 효과도 섞여 있다. **두 수치의 차이를 카카오 집계의 누수 크기로 읽으면 안 된다** — 그건 위 문단의 수치다.
- `quality_crawled` 는 크롤링 리뷰만으로 다시 계산하되 평가 사용자 227명의 리뷰를 **전부** 뺐다. 그러고 나면 리뷰가 하나도 남지 않는 가게가 18곳이라 그 가게들은 전체 평균으로 수렴한다 — 누수는 없지만 해상도가 낮다.
- 사용자의 리뷰 **원문은 어떤 모델의 입력도 아니다.** 추천 시점에 제품이 아는 것은 (가게, like/dislike) 뿐이다.
- Step 2 에서 가게 표현을 리뷰 텍스트로 만들 때도 평가 사용자의 리뷰는 전부 제외한다(`pool.attach_crawled_quality` 와 같은 제외 집합을 쓴다).
- 하이퍼파라미터(λ 등)는 `cv.select_hyperparam` 의 사용자 5-fold 로 고른다. 테스트 사용자에게서 고르지 않는다.
