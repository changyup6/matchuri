# 관측 스택(Prometheus + Grafana) — 실서버 대상 검증 (2026-09-10)

`monitoring/` 을 붙이면서, **살아 있는 스택(`-p backmock`)을 건드리지 않고** 설정·규칙·
대시보드가 실제로 도는지 확인한 기록이다. 방법은 같은 설정 파일을 그대로 쓰는 일회용
사본을 다른 프로젝트 이름으로 띄우고, 살아 있는 도커 네트워크에 **읽기로만** 끼어드는 것이다.

```bash
cd ~/matchuri-be
docker compose -f monitoring/docker-compose.test.yml -p backmock-obs-test up -d
# 확인 후
docker compose -f monitoring/docker-compose.test.yml -p backmock-obs-test down -v
```

- 프로젝트·볼륨 이름이 다르다(`prom-data-test` · `grafana-data-test`) — 운영 볼륨과 안 겹친다.
- 네트워크는 `backmock_default` 에 `external` 로 붙기만 한다. 실서버의 `app:8000/metrics` 를
  긁는 것 말고는 아무것도 하지 않는다.
- Grafana 는 **`127.0.0.1:13000`** 에만 열었다(루프백이라 인터넷에서 못 닿는다).

## 1. 수집 대상 — 넷 다 UP

```
$ wget -qO- 'http://localhost:9090/api/v1/targets?state=active'
matchuri     http://app:8000/metrics             up
nginx        http://nginx-exporter:9113/metrics  up
node         http://node-exporter:9100/metrics   up
prometheus   http://localhost:9090/metrics       up
```

**`nginx` 잡이 UP 인 것은 exporter 프로세스가 살아 있다는 뜻일 뿐이다.** 정작 그 exporter 가
읽어야 할 `stub_status` 는 아직 실서버에 배포되지 않았으므로 `nginx_up = 0` 이고,
`nginx_connections_*` · `nginx_http_requests_total` 은 **계열이 없다**:

```
nginx_up                 0        ← /nginx_status 가 404. 배포 뒤 1 이 된다
nginx_connections_active (없음)
```

이것이 대시보드의 `nginx 연결` 패널과 `엣지가 받은 요청` 계열이 지금 비어 있는 이유다.
**배포 뒤에 이 둘이 채워지는 것으로 nginx 설정이 먹었는지 확인하면 된다.**

## 2. 규칙 — 8개 전부 평가된다

```
$ wget -qO- http://localhost:9090/api/v1/rules
group matchuri-recording   lastEval=0.0017s
   recording  matchuri:http_error_ratio:5m      health=ok
   recording  matchuri:http_p95_seconds:5m      health=ok
   recording  matchuri:like_rate_by_policy:1h   health=ok
group matchuri-alerts      lastEval=0.0007s
   alerting   AppDown         health=ok  state=inactive
   alerting   HighErrorRate   health=ok  state=inactive
   alerting   SlowP95         health=ok  state=inactive
   alerting   DiskLow         health=ok  state=inactive
   alerting   MemLow          health=ok  state=inactive
```

알림 다섯이 전부 `inactive` — 서버가 멀쩡하다는 뜻이다. **Alertmanager 는 없다**(의도한 것.
`monitoring/README.md` 의 '알림' 절). 규칙은 평가되고 `ALERTS` 시계열로 남으므로 Grafana 에서
울고 있는 것을 볼 수 있다.

`promtool` 정적 검사도 통과한다:

```
$ docker run --rm -v ~/matchuri-be/monitoring/prometheus:/etc/prometheus:ro \
    --entrypoint promtool prom/prometheus:v2.55.1 check config /etc/prometheus/prometheus.yml
  SUCCESS: 1 rule files found
 SUCCESS: /etc/prometheus/prometheus.yml is valid prometheus config file syntax
  SUCCESS: 8 rules found
```

### 기록 규칙이 실제로 낸 값

```
matchuri:http_p95_seconds:5m       0.1614          (161ms — /cards 를 부른 직후라 높다)
matchuri:http_error_ratio:5m       0               (5xx 없음)
matchuri:like_rate_by_policy:1h    (계열 없음)      ← 아래 4절 참고
```

`http_error_ratio` 는 처음에 **계열 자체가 없었다.** 5xx 가 한 건도 없으면
`sum(rate(…{status=~"5.."}))` 이 빈 벡터가 되고 나눗셈 결과도 빈 벡터가 되기 때문이다.
화면에서 그건 '0%' 가 아니라 '데이터 없음' 으로 보이고, 그 둘이 똑같이 보이면 사람이
지표가 고장 났나부터 의심하게 된다. 그래서 `or vector(0)` 으로 바닥을 깔았다.

## 3. Grafana — 로그인·프로비저닝

```
GET  /grafana/api/health                       {"database":"ok","version":"11.3.1"}
GET  /grafana/api/search        (익명)          401     ← 익명 열람 꺼짐
GET  /grafana/api/org  -u admin:<시크릿>        200     ← 시크릿 파일의 비밀번호로 로그인됨
GET  /grafana/api/org  -u admin:wrong          401
GET  /grafana/api/datasources                  prometheus  http://prometheus:9090  default=True readOnly=True
GET  /grafana/api/datasources/uid/prometheus/health
     {"status":"OK","message":"Successfully queried the Prometheus API."}
GET  /grafana/api/search?type=dash-db
     matchuri-ops       맛추리 운영        [맛추리 운영 recsys]
     matchuri-latency   맛추리 지연 상세    [맛추리 운영 지연]
```

`readOnly=True` 와 대시보드의 `allowUiUpdates:false` 가 의도한 대로다 — 화면에서 고친 것은
저장되지 않고 파일만이 원본이다.

### 컨테이너가 안 뜬 이유 하나 (기록해 둔다)

첫 기동에서 Grafana 가 바로 죽었다:

```
Getting secret GF_SECURITY_ADMIN_PASSWORD from /run/secrets/grafana_admin
/run.sh: line 59: /run/secrets/grafana_admin: Permission denied
```

컴포즈 시크릿은 호스트 파일의 **소유자와 모드를 그대로** 컨테이너에 넘기는데, Grafana 는
컨테이너 안에서 **uid 472** 로 돈다. `ubuntu(1000)` 소유 + 600 이면 못 읽는다 —
`nginx/.htpasswd` 가 `101:101` 이어야 했던 것과 똑같은 함정이다.

```bash
sudo chown 472:472 ~/matchuri-secrets/grafana-admin-password   # 모드는 600 그대로
```

## 4. 패널 — 49개 쿼리를 Grafana `/api/ds/query` 로 실제로 돌렸다

두 대시보드의 **모든 target 을** Grafana 의 데이터소스 쿼리 API 로 보냈다(패널이 실제로 그리는
경로 그대로다 — `$__rate_interval` 해석과 `format:heatmap` 까지 Grafana 가 처리한다).

```
총 49개 쿼리 · PromQL 오류 0개 · 데이터가 돌아온 쿼리 42개
```

데이터가 비어 있는 7개는 전부 **아직 그런 일이 일어나지 않아서**이고, 셋으로 갈린다.

| 패널 | 왜 비었나 | 언제 채워지나 |
|---|---|---|
| `nginx 연결` (4계열) · `엣지가 받은 요청` | `stub_status` 미배포 → `nginx_up=0` | 이번 nginx 설정을 배포하면 |
| `정책별 좋아요율` · `지금 좋아요율` · `prefer 별 선호/분` | 앱 재시작 뒤 아직 스와이프가 한 건도 없어 `matchuri_preferences_total` 계열이 아예 없다 | 사용자가 첫 좋아요/싫어요를 누르면 |
| `시간당 처리 못 한 예외` | 재시작 뒤 처리 못 한 예외가 없다(`matchuri_errors_total` 없음) | 사고가 나면 (안 나는 게 낫다) |

카운터에 **관측이 한 번도 없으면 앱이 그 줄을 아예 내보내지 않는다**(`observe.py` 는 관측된
라벨 조합만 렌더링한다). 그래서 '0' 이 아니라 '없음' 이 된다 — 이 셋은 지표도 쿼리도 정상이다.

### 어떻게 찍었나 (다음 사람을 위해)

`http://admin:<pw>@127.0.0.1:13000/…` 는 **통하지 않는다.** 크롬은 URL 에 넣은 자격증명을
401 챌린지를 받은 뒤에만 보내는데, Grafana 는 HTML 요청에 401 대신 `/login` 으로 302 를 준다.
결과는 로그인 화면 스크린샷이다(실제로 처음에 그렇게 찍혔다).

익명 접근을 켜는 것(= 검증 대상인 인증을 끄는 것)은 답이 아니라고 봤다. 그래서 스크린샷을
찍는 동안만 `Authorization` 헤더를 대신 붙여 주는 15줄짜리 프록시를 앞에 세웠다.

```bash
python3 authproxy.py ~/matchuri-secrets/grafana-admin-password &   # 13001 → 13000
chrome-headless-shell --headless --no-sandbox --enable-unsafe-swiftshader \
  --window-size=1440,3000 --virtual-time-budget=35000 \
  --screenshot=grafana-20260910.png \
  'http://127.0.0.1:13001/grafana/d/matchuri-ops?kiosk&from=now-1h&to=now'
```

`--enable-unsafe-swiftshader` 가 없으면 WebGL 폴백 경고와 함께 일부 패널이 비어 나온다.
`--virtual-time-budget` 은 패널 쿼리가 끝날 때까지 기다리는 시간이다(30초면 넉넉하다).

## 7. 확인하지 못한 것

- **`/nginx_status` 와 `nginx-exporter` 의 실제 수집.** 실서버 nginx 가 아직 옛 설정이라
  404 다. 문법 검사는 통과했다(`nginx -t`, 업스트림 이름까지 포함해서).
- **nginx 의 `/grafana/` 프록시와 `/metrics` 404.** 같은 이유 — 배포 뒤 확인해야 한다.
- **정책별 좋아요율.** 스와이프를 만들어 내려면 실서버 `state/preferences.jsonl` 에 가짜
  기록을 써야 해서 하지 않았다. PromQL 과 라벨(`prefer` · `policy`)은 `observe.py` 와 대조해
  맞췄고 쿼리는 오류 없이 돈다.
- **30일 보관.** 며칠 지나 봐야 아는 것이다.
