# 클라이언트 연동

> 신규 사용자/세션 연동은 [API 가이드](../../docs/API.md#0-신규-연동-실제-사용자와-추천-세션)를 사용합니다. 아래 `/users/{user_id}/decision...`은 호환용 세션 경로이며 신규 경로는 `/user/{user_id}/session/{session_id}/decision...`입니다. decision·metrics·summary 응답 필드는 같습니다.

기존 추천 카드 조회·스와이프 저장 흐름을 유지한다. 선택 제안과 판단 수치는 별도 조회한다.
운영 주소: http://api.example.com · [필드 설명/OpenAPI](http://api.example.com/docs)

## 선택 제안

`GET /user/{user_id}/session/{session_id}/decision?n=6` — 기본4장, 1~20장 지정.
기본 `mode=manual`이며 **점수나 스와이프 수와 관계없이** 사용자가 요청할 수 있다.
응답은 기존 `ready`, `status`, `proposal_id`, `message`, `cards` 다섯 필드다.

| 호출 | 용도 | 카드 반환 조건 |
|---|---|---|
| `GET …/decision?n=4` | 사용자가 지금 선택하기 | 현재 정보로 최선의 n곳. 개인화 검증 미완료도 허용 |
| `GET …/decision?mode=auto&n=4` | 서버가 선택 시점을 권유할지 조회 | 기존 개인화·적합도·다양성 조건 통과 |
| `POST …/preferences?include_decision=true&n=4` | 스와이프 직후 자동 권유 | 위 auto와 같은 조건. 수동 요청으로 바뀌지 않음 |

- `ready=true`: 요청한 n장을 제공했다는 뜻이다. **manual의 ready는 개인화 검증 통과가 아니다.**
- `ready=false`: `cards=[]`, `proposal_id=null`, `message=null`. 필터 안에 n곳이 없거나
  계속 둘러본 조합 외에 대안이 없는 경우 `insufficient_candidates`다.
- 반경 설정에 필요한 위치가 없으면 `location_required`, 추천 산출물이 없으면 `unavailable`이다.
  `learning`은 auto의 개인화 근거 부족 상태다. manual은 점수 때문에 learning으로 막지 않는다.
- 최종 후보는 기존 좋아요/싫어요/노출 여부로 제한하지 않는다. 모든 경우 사용자 필터·거리를 지킨다.
  n장을 확보하지 못하면 임의로 줄이거나 필터 밖 가게로 채우지 않는다.
- manual도 고차원 취향 점수와 불확실성, 태그·거리 보정을 사용한다. 적합하고 다양한 조합을 우선하며,
  엄격한 조합이 없을 때는 현재 후보에서 적합도와 중복을 고려해 n곳을 고른다. 벡터 유사도가
  높은 후보도 포함될 수 있고, 이는 auto 기준 통과를 의미하지 않는다. 같은 세부 업종인지는
  진단 정보이며, 조합의 중복은 실제 벡터로 비교한다.
- 반응과 이전 세션 기억이 모두 없으면 기존 기본 점수로 추천한다. 기본 추천임을 카드 이유에 표시한다.
- 카드 조회는 학습·스와이프 노출을 바꾸지 않는다. 결과 접수를 위한 제안 발급만 기록한다.

**클라이언트는 지금 선택하기 버튼을 점수와 무관하게 열고, 클릭 시 기본 decision을 요청한다.**
주기적인 자동 권유 조회는 `mode=auto`를 명시한다. 동일한 proposal_id로 중복 권유하지 않는다.
80/100점 도달 여부로 버튼을 잠그거나 취향 분석 완료를 선언하지 않는다.

## 선택하거나 스와이프 계속하기

`POST /users/{user_id}/decision/feedback`으로 실제 사용자 행동을 전달한다.
기존 decision 응답과 카드 스키마는 그대로다. 성공 응답은 `{"ok": true}`다.

| 행동 | 요청 본문 |
|---|---|
| 한 곳 선택 | `{"proposal_id":"응답에서 받은 ID","action":"select","card_id":12}` |
| 선택 없이 계속 둘러보기 | `{"proposal_id":"응답에서 받은 ID","action":"continue"}` |

계속 둘러보기 성공 후 기존 `/cards`·`/preferences`로 스와이프를 이어가고, 필요할 때
동일한 n으로 decision 또는 metrics/summary를 조회한다. 서버가 자동으로 사용자의
계속 둘러보기 의도를 추정하지 않으므로 이 POST 연결이 필요하다. 타이머나 단순 조회를
continue로 보내지 않는다. 클라이언트 코드는 이번 백엔드 변경에 포함하지 않는다.

- `continue`는 **동일한 제안 조합**을 다음 탐색에서 제외한다. 구성원 각각을 싫어요로
  처리하거나 영구 제외하지 않는다. 다음 조합은 적어도 한 곳이 달라지며 일부는 겹칠 수 있다.
- 이후 스와이프는 기존 취향 모델에 그대로 반영된다. auto는 새 조합도 같은 적합도·다양성 기준을
  통과해야 하며, manual은 현재 후보에서 대안을 찾는다. 대안이 없으면 `ready=false`,
  `status=insufficient_candidates`, `cards=[]`이다. 이 사유로 개인화 점수를 낮추지 않는다.
- `select`는 선택한 가게를 결과로 저장한다. 선택하지 않은 가게를 싫어요로 바꾸거나,
  선택 자체를 스와이프 검증 표본으로 넣지 않는다. 방문 여부는 기존 길찾기·설문 흐름을 쓴다.
- 결과는 서버 재시작 후에도 유지된다. 같은 결과 재전송은200, 이미 다른 결과를 기록했으면409다.
  select에서 card_id 누락/제안 밖 카드, continue에 card_id 첨부는422다. 타 사용자·없는 제안은404다.
  저장 실패는503이며 성공으로 응답하지 않는다.
  단, `/preferences?include_decision=true`에서 부가 제안 저장만 실패하면 이미 성공한
  스와이프는200을 유지하고 `decision=null`이다. 스와이프를 재전송하지 말고 decision을 재조회한다.
- 사용자별 최근100개 발급 제안을 보관한다. 더 오래된 제안 결과는404이므로 새로 조회한다.
  계속 둘러본 조합 제외는 제안 당시와 같은 필터에 적용된다. GPS 갱신만으로 잊지 않는다.
  현재 위치의 거리·반경 조건은 그대로 적용된다. n이 다르면 다른 조합이다.
- 실제로 반환한 제안만 별도 `decisions.jsonl`에 기록한다. 반복 GET은 같은 제안을
  중복 기록하지 않는다. 판단 수치 조회는 제안을 발급하거나 학습·노출을 기록하지 않는다.

카드의 `recommendation_reason`은 자기 자신을 근거에서 제외한 후, 양의 취향 기여가 있는
메뉴·소개·리뷰·음식사진 중 관측 근거를 한 줄로 설명한다. 예: “좋아요한 ○○의 메뉴 구성과
비슷한 점이 있어요.” 이는 복잡한 취향의 일부 근거이며 취향 전체나 특정 음식 선호를 단정하지 않는다.
설명할 개별 근거가 부족하면 auto는 종합 적합 설명을, manual은 현재 정보로 고른 후보라는
설명을 쓴다. manual에서 통과하지 않은 적합 기준을 통과했다고 안내하지 않는다.

## 판단 수치

`GET /users/{user_id}/decision/metrics/summary?n=4&card_ids=12&card_ids=34`

실제 카드 응답의 숫자 `card_id`를 반복 지정한다. 최대20개, 중복 제거. 카드 순서와 무관하게
같은 요약을 반환한다. 생략해도 개인화 점수·적합 가게 수를 측정하며,
지정 카드의 다양성 세 필드만 null이다. `n`은 자동 제안 분석 장수(기본4, 1~20)이며
decision 조회와 같은 값을 사용한다. 측정용 `card_ids` 개수와는 별개다.
추천 벡터가 없거나 알 수 없는 카드는422다. 지정 카드는 측정 대상이며 제안 목록이 아니다.

아래는 **필드 구조를 설명하는 예시**이며 실제 사용자 측정값이 아니다.

```json
{
  "status": "ok",
  "decision_readiness_score": 80,
  "personalization": {
    "ready": true,
    "readiness_score": 100,
    "discrimination_score": 80.0,
    "stability_score": 80.0
  },
  "fit_count": 12,
  "diversity": {
    "passed": true,
    "similarity_score": 65.0,
    "card_ids": [12, 34]
  }
}
```

| 필드 | 의미 |
|---|---|
| `status` | `ok` / `unavailable` / `location_required`. 조회 상태이며 제안 여부가 아님 |
| `decision_readiness_score` | **표시용 취향 파악 점수**. 실제 범위는0~80이고 기존 앱이0~100%로 환산. 답 보기 전 예측이 맞은 방향이면 오르고 반대면 내려가는 적중 누적(0~79), 연속 적중이 길수록 증가폭이 커짐. 빗나간 한 장은 누적의 절반까지만 깎고, 순적중 이후에는 0으로 돌아가지 않음. **80은 `personalization.ready`가 true일 때만** = 화면100%. 반복 조회로는 변하지 않음. 추천 진입 조건이 아니며 분석 불가는 null |
| `personalization.ready` | 평가 근거·예측 구분력·순위 안정성이 현재 개인화 기준을 모두 통과. 후보 부족과는 별개 |
| `personalization.readiness_score` | 취향 찾기 준비도0~100. 높을수록 현재 개인화 기준에 가까움. **순위 안정성은 제외**하므로100이어도 `ready`가 false일 수 있음. 근거 미확보는0, 분석 불가는 null |
| `discrimination_score` | AUC×100. 50은 무작위 수준(추천을 내주는 최소 기준은 70), 높을수록 답변 전 좋아요/싫어요 순위를 잘 구분. 검증 수 부족은 null |
| `stability_score` | 한 번 전·세 번 전 추천 상위 목록과 겹치는 최소 비율×100. 높을수록 안정적. 비교 근거 부족은 null |
| `fit_count` | 현재 필터·거리 안에서 취향 적합 기준을 통과한 가게 수. 다양성 검사 전. 계산 불가는 null, 계산했지만 없는 경우0 |
| `diversity.passed` | 지정 카드의 모든 쌍이 기존 다양성 규칙을 통과했는가. false에는 근거 부족도 포함. 2장 미만/분석 불가는 null |
| `similarity_score` | 가장 비슷한 쌍의 기존 성분 평균 유사도를 `50×(1+평균)`으로 표시. 50은 평균0, 100은 평균1. 높을수록 닮음 |
| `diversity.card_ids` | 해당 점수의 두 카드. 동점은 카드 ID 순. 점수 미측정이면 null |

유사도는 메뉴·요약·리뷰·음식사진 중 관측된 성분의 기존 평균을 사용한다. 성분마다 눈금이
다르므로 사람에게 느껴지는 유사성이나 만족/중복 확률이 아니다. 한 쌍이라도 관측 성분이
2개 미만이면 가장 비슷한 쌍을 확정할 수 없어 점수와 ID를 null로 반환한다.
유사도 점수만 보고 통과를 재판정하지 않는다. 브랜드·관측 근거·극단 유사도는 최소 조건이며,
세부 업종 일치는 진단 정보다. 서버는 적합 후보 안에서 성분별 백분위의 가장 큰 중복부터
줄이는 조합 비교를 추가 수행한다. summary의 기존 점수 의미는 바꾸지 않는다.
개인화 점수도 만족 확률이나 완료 퍼센트가 아니다. 서버의 ready/passed를 사용한다.

`decision_readiness_score`는 기존 필드명과 응답 구조를 유지하는 **표시용 취향 파악 점수**다.
기준이 얼마나 채워졌나(게이트 최솟값)가 아니라 **답을 보기 전 예측이 맞았나**를 누적한다.
한 장의 기여는 그 카드의 예측 순위 백분위(`personal_rank`)와 실제 응답으로 정한다 —
높게 본 카드에 좋아요, 낮게 본 카드에 싫어요면 오르고, 반대면 내려간다. **연속으로 맞히면
한 장의 증가폭이 커진다**(최대 2배). 빗나간 장에서는 내려가되 **한 번에 이제까지 쌓은 값의
절반보다 많이 깎이지는 않는다**(`MAX_MISS_SHARE`). 그래서 한 번이라도 순적중한 사용자의
화면은 다시 0%가 되지 않는다 — 0%는 "아직 아무것도 맞히지 못했다" 는 뜻으로만 남는다.

기존 앱은 API0~80을 화면0~100%로 환산하고 `>= 80`을 "준비됨"으로 쓴다. 그래서 **80은
`personalization.ready`가 true인 순간에만** 나온다. 그 전에는 최대79(화면98.8%)에서 멈추고,
`ready`가 다시 false가 되면(예: 최근 30장에서 싫어요가 밀려나 검증 수가 모자라면) 79 이하로
돌아간다. 화면의 100%와 서버의 `ready`가 정확히 같은 뜻이 되므로 둘을 따로 볼 필요가 없다.

반복 GET·필터·위치·n·card_ids 변경이나 continue 결과는 점수를 움직이지 않는다 —
학습으로 받아들인 스와이프에서만 한 번씩 접힌다(preferences 재생·스냅샷 복원도 같은 값).
새 결정 세션의 점수는 **항상 0에서 시작한다**(화면 0%). 이전 세션에서 물려받는 것은
점수가 아니라 **오르는 속도**다 — 이전에 많이 맞힌 사용자일수록 적중한 스와이프의
증가폭이 커져(최대 2배) 같은 답으로 더 빨리 올라간다. 빗나간 스와이프에는 이 배속이
붙지 않는다. 연속 적중수도 물려받지 않는다. 클라이언트가 할 일은 없다 — 세션을 새로
만든 직후 0%가 나오는 것이 정상이며, 그 뒤 증가 속도만 달라진다.

현재 개인화 기준 통과 여부는 항상 `personalization.ready`로 판단한다. 화면 점수는
**통계적으로 보정된 정확도나 만족 확률·학습 완료율이 아니다.** 많이 스와이프한다고
올라가지 않는다 — 맞혀야 올라간다. 기존 개인화·적합 가게 수·지정 카드 유사도 값은 유지한다.

**추천 가능 여부는 해당 decision 응답의 ready/cards를 사용한다.** 점수0인 사용자도 manual로
추천받을 수 있다. 자동 권유 여부는 `mode=auto` 또는 스와이프 응답의 decision으로 확인한다.
상세 metrics의 decision/gates/slate는 계속 **자동 권유 기준**을 진단한다. manual 카드의
유사도는 실제 반환한 card_ids를 summary에 지정해 조회한다.

`personalization.readiness_score`는 **개인화만** 나타내는 기존 점수다.
필수 개인화 기준별 측정값/기준값 중 최소 비율을100점 눈금으로 표시한다. 미측정 기준은 아직
준비 근거가 없는 것으로0, 미통과 값은 최대99다.
가장 부족한 기준이 준비도를 제한하므로 일부 학습이 진행됐어도0일 수 있다. 0이 취향 학습이나
예측 정확도가0이라는 뜻은 아니다. 피드백에 따라 내려갈 수 있으며 남은 스와이프 수를 예측하지 않는다.

**순위 안정성(`stability`)은 이 점수에 들어가지 않는다.** 그 값은 미평가 상위 목록을 한 번 전·
세 번 전 학습 상태와 비교해 겹침이 작은 쪽을 쓰므로 학습이 진행되는 동안에는 내려간다 —
"얼마나 남았나"가 아니라 "방금 얼마나 배웠나"를 재는 값이어서 진행 척도로 쓰지 않는다.
`ready` 조건에서는 그대로 요구하고, 값은 `stability_score`와 상세 metrics의 gates로 계속 준다.
그래서 **`readiness_score`가100이어도 `ready`는 false일 수 있다** — 안정성만 미달인 경우다.
개인화 통과 여부는 점수가 아니라 항상 `ready`로 판단한다.
클라이언트는 이 값을 개인화 상태 표시에 쓰고 추천 버튼 허용 여부와 구분한다.
후보 수·다양성·실제 제안 가능 여부는 기존 fit_count/diversity/decision으로 확인한다.

서버는 상세 분석과 동일한 전체 후보 채점·자기 참조 제외·개인화 검증·조합 탐색을 수행한다.
응답만 요약한다. 고정 설명·임계값·가중치·후보별 성분·전체 쌍 목록은 매 응답에 반복하지 않는다.
설명은 위 표와 OpenAPI에, 상세 수치는 기존 `GET /users/{user_id}/decision/metrics`에 있다.
상세 API와 기존 `include_decision_metrics` 옵션은 유지하며 상세 제안 장수도 `?n=6`으로 지정한다.

별도 GET은 조회 시점의 값이다. 이전 스와이프 응답과 동일 시점이라고 가정하지 않는다.
이번 정리로 제안 응답의 진단 필드5개와 이전 summary의 상세 중첩 필드를 제거했다.
해당 필드를 읽던 클라이언트는 위 필드 또는 [상세 분석 API](DECISION-METRICS.md)를 사용한다.
